# Argo CD Auto-Sync and Argo Rollouts Rollbacks: Avoiding Surprising Reconciliation

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Argo CD, Argo Rollouts, GitOps, Kubernetes, Auto-Sync, Rollback, Continuous Delivery

Description: Keep Argo CD's Git reconciliation and Argo Rollouts live traffic recovery aligned during aborts, rollbacks, router mutations, and emergency changes.

---

Argo CD and Argo Rollouts reconcile different layers of the same release:

- Argo CD makes the live `Rollout` specification match manifests rendered from Git.
- Argo Rollouts makes ReplicaSets, Services, traffic routes, and AnalysisRuns implement that live specification.

Most “auto-sync undid my rollback” incidents come from changing the wrong layer. An Argo Rollouts abort safely returns traffic to stable but leaves the desired pod template unchanged. A direct live patch changes the desired template in the cluster but conflicts with Git. Only a Git change gives Argo CD a new durable desired state.

## Understand the Normal Failed-Release State

Assume Git and the live Rollout both request image `2.0.0`. Analysis fails, so Argo Rollouts returns service to stable image `1.9.0`.

At that moment:

- Git still renders `.spec.template` with `2.0.0`;
- the live Rollout spec still requests `2.0.0`;
- stable `1.9.0` pods receive production traffic;
- the Rollout is `Degraded` because desired and serving revisions differ;
- Argo CD may still report the Rollout object as synced because its spec matches Git.

The Argo Rollouts FAQ explains that this does not create an endless loop. Rollouts changes its managed operational state, not the Git-backed pod template. Argo CD therefore has no different template to keep reapplying.

Finish the decision by committing either the old known-good template or a new fixed revision.

## Why a Live Image Patch Can Be Reversed

This emergency command changes only the live object:

```bash
kubectl argo rollouts set image payments \
  payments=registry.example.com/payments:1.9.0
```

If Git still specifies `2.0.0`, the application is now out of sync. Argo CD automatic self-healing is specifically designed to correct live drift even when Git has not changed, so it can reapply `2.0.0`. A later sync triggered by another repository change can also reconcile the resource.

The reliable GitOps rollback is a repository edit:

```bash
git revert <bad-release-commit>
git push
```

Or commit a fixed immutable image digest. The source change gives both controllers a state they can converge on.

## Auto-Sync Is Not Auto-Rollback

Automated sync means “apply the desired state from Git when synchronization conditions are met.” It does not mean “change Git to whichever ReplicaSet Argo Rollouts currently considers stable.”

Argo CD's documentation also states that its application rollback operation cannot be performed while automated sync is enabled. If your operating model uses Git as the source of truth, a normal revert commit or roll-forward commit is usually clearer than toggling auto-sync merely to invoke an imperative Argo CD rollback.

If an incident requires temporarily disabling auto-sync, record who owns re-enabling it and how the Git state will be repaired. For applications generated by an `ApplicationSet`, edit the controlling `ApplicationSet` or use its documented temporary-toggle mechanism; changing a generated `Application` field directly may be overwritten by its owner.

## Let Rollouts Own Its Runtime Fields

Traffic routing introduces a second reconciliation risk. Argo Rollouts may update an Istio `VirtualService`, NGINX Ingress, ALB action, or another provider-specific resource while Argo CD also tracks that resource from Git.

For Istio, the official Argo Rollouts guide documents ignoring Rollouts-managed route weights in Argo CD. A representative excerpt from an existing Application configuration is:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments
spec:
  ignoreDifferences:
    - group: networking.istio.io
      kind: VirtualService
      jqPathExpressions:
        - .spec.http[].route[].weight
  syncPolicy:
    automated:
      enabled: true
      selfHeal: true
    syncOptions:
      - ApplyOutOfSyncOnly=true
      - RespectIgnoreDifferences=true
```

`ignoreDifferences` controls diff calculation. `RespectIgnoreDifferences=true` makes the sync operation respect those exclusions for existing resources, and `ApplyOutOfSyncOnly=true` avoids applying resources Argo CD already considers synchronized. Use the provider's current integration guide; do not broadly ignore the entire routing resource, or Git could stop detecting unrelated unsafe drift.

Service selector hashes are also managed by Argo Rollouts. Keep stable labels and Service definitions declarative, but do not continuously force `rollouts-pod-template-hash` to a value from Git.

## A Rollback Runbook That Converges

1. Observe the current state:

   ```bash
   kubectl argo rollouts get rollout payments
   argocd app get payments
   ```

2. Abort if the desired revision is still receiving harmful traffic.
3. Verify traffic and capacity returned to stable.
4. Decide between reverting to a compatible previous template and rolling forward.
5. Commit the decision to the repository Argo CD actually tracks.
6. Let auto-sync apply the new rendered spec.
7. Watch the Rollout until healthy and confirm the Argo CD application is synced.
8. Check for unexpected diffs on provider routing objects.

For mutable chart inputs, record the image digest actually resolved at deployment time as well as the Git commit. A chart commit that still renders a mutable tag is not a dependable rollback target.

## Diagnose Surprising Reconciliation

When a value changes back, identify its field manager and source:

```bash
kubectl get rollout payments -o yaml --show-managed-fields
argocd app diff payments
kubectl argo rollouts get rollout payments
```

Ask three questions:

- Is the differing field part of Git-backed desired state or Rollouts-managed runtime state?
- Is self-heal, another Git commit, an ApplicationSet, or a manual sync applying it?
- Is an ignore rule narrow enough, and does the sync operation respect it?

Argo CD should own the declared release; Argo Rollouts should own progressive execution. Rollbacks become predictable when emergency containment and durable Git reconciliation are treated as two explicit steps.
