## Issues Found

### Issue 1: Incorrect CephX authentication flow (Step 1)
- **What was wrong:** The authentication flow stated "Client presents its secret key to the monitor." This directly contradicts the fundamental CephX design — the client never transmits its secret key over the network.
- **What was changed:** Corrected the entire 5-step authentication flow to accurately describe the protocol: the client sends its identity, the monitor responds with a session key encrypted with the client's secret, the client decrypts it to prove knowledge of the key, then requests a service ticket.
- **Why:** Per the Ceph architecture docs, CephX uses a challenge-response mechanism where the secret key is never transmitted. The original wording contradicted the post's own claim that "no passwords are ever transmitted over the network."

### Issue 2: Incorrect description of session key origin
- **What was wrong:** Session keys were described as "derived from the ticket exchange."
- **What was changed:** Corrected to state that session keys are "generated by the monitor" and "included in the encrypted ticket."
- **Why:** Per the Ceph protocol documentation, the monitor generates session keys and encrypts them within the ticket payload. They are not derived by the client or negotiated — they are created server-side and delivered encrypted.

### Issue 3: Misleading key rotation command
- **What was wrong:** The Rotating Keys section started with `ceph auth get-or-create-key client.myapp` with the comment "Generate a new key for a client." This command returns the existing key for an already-existing entity — it does not generate a new one.
- **What was changed:** Removed the misleading `get-or-create-key` command and clarified that deleting and recreating the entity is what generates the new key.
- **Why:** Per the Ceph user management docs, `get-or-create-key` "simply returns the key" if the user already exists. The actual rotation happens via delete + recreate.

## Review Notes
- The `kubectl exec -it rook-ceph-tools` command assumes a pod named exactly `rook-ceph-tools`. In practice, the Rook toolbox is typically a Deployment, so the pod name includes a random suffix. A more robust command would be `kubectl -n rook-ceph exec -it deploy/rook-ceph-tools -- bash`. This is a minor usability note, not a technical error.
- The CSI provisioner secret name `rook-csi-rbd-provisioner` follows Rook's standard naming conventions and is correct.
- All `ceph auth` commands use correct syntax and valid capability strings.
