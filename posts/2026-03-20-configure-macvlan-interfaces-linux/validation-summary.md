## Issues Found
- **Inaccurate MAC address claim in the introduction.** The original text stated that macvlan interfaces have MAC addresses "derived from the parent interface." This is incorrect — macvlan interfaces are assigned **randomly generated** MAC addresses by default (independent of the parent's MAC), and they can also be set manually. Updated the wording to: "each have their own unique MAC address (randomly generated by default, or assignable manually) sharing a single parent interface."

## Review Notes
- The four macvlan modes (`bridge`, `vepa`, `private`, `passthru`) and their descriptions are accurate.
- The `ip link add ... type macvlan mode bridge` syntax and surrounding `ip addr` / `ip link set` commands are correct.
- The network namespace example (`ip netns add`, `ip link set ... netns`, `ip netns exec ...`) is valid and complete (includes bringing up `lo` and adding a default route).
- The Docker `docker network create -d macvlan --subnet ... --gateway ... -o parent=eth0` syntax and the `docker run --network ... --ip ...` invocation are both valid against current Docker CLI usage.
- The well-known limitation that the host cannot directly communicate with its own macvlan child interfaces (due to how Linux's macvlan driver hooks into ingress) is correctly described.
- The `passthru` description ("Only one macvlan per parent; used for SR-IOV setups") is acceptable but slightly narrow — passthru is more broadly used for VM/container direct passthrough scenarios where the macvlan effectively takes over the parent. Not changed since the existing description is not wrong.
- The post does not mention IPv6 configuration on macvlan interfaces, which works the same way with `ip -6 addr add`. Not an error — just a possible future enhancement.
