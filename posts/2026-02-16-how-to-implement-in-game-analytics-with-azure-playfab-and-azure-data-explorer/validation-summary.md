## Issues Found
- The architecture incorrectly routed PlayFab events through Azure Event Hubs. PlayFab Data Connections support Azure Data Explorer directly, so the architecture diagram and explanation were updated to show PlayFab exporting directly to ADX.
- The setup commands created an Event Hub and used an obsolete Event Hubs retention flag. Since the corrected architecture does not use Event Hubs, those commands were removed.
- The `az kusto database create` example used `--soft-delete-period` and `--hot-cache-period` as top-level flags. Current Azure CLI expects those values inside `--read-write-database`, so the command was corrected.
- The ADX setup included an invalid KQL management command for creating an Event Hub data connection. ADX Event Hub data connections are Azure management resources, and PlayFab's ADX connection is configured from PlayFab Game Manager, so the invalid KQL command and JSON ingestion mapping were removed.
- The table and queries used `EventName` and `PlayerId` columns that do not match the PlayFab Data Explorer/ADX event shape documented by PlayFab. The examples now use `FullName_Name` for the event name and `Entity_Id` for player/entity identity.
- The retention query used an inner join for D1 retention, which would omit cohorts with no day-one returners. It now uses a left outer join and `coalesce`, matching the D7 and D30 handling.

## Review Notes
- The Azure CLI was not installed in the local environment, so command validation was performed against Microsoft Learn CLI reference documentation instead of local `az --help` output.
- The post remains a high-level implementation guide. A production implementation should still validate the exact ADX table schema generated by the PlayFab onboarding flow for the specific title and connection settings.
