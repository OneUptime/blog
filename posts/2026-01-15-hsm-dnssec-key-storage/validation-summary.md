## Issues Found
The BIND and AWS CloudHSM sections were built on removed/end-of-life tooling. The conceptual content (why HSMs, PKCS#11 model, ceremonies, HA, DR) was sound, but several commands would not run as written.

1. **BIND built with `--enable-native-pkcs11`/`--with-pkcs11` on 9.18.24** — Native PKCS#11 support was **removed in BIND 9.18**. Those configure flags no longer exist. Fixed the build to compile against OpenSSL (no PKCS#11 configure flag) and added installation of `libengine-pkcs11-openssl`/`opensc`, matching ISC's documented engine_pkcs11 approach for 9.18.

2. **Fabricated `key-store { pkcs11-lib; pkcs11-slot; pkcs11-pin-file; }` named.conf block** — No such statement/options exist in BIND 9.18 (the 9.20 `key-store` statement uses `directory`/`pkcs11-uri`, not these fields). Replaced with the correct engine_pkcs11 model: an OpenSSL `openssl.cnf` engine section plus standard key files generated by `dnssec-keyfromlabel`. Also removed the now-dangling `include "dnssec-keys.conf"` and added a `key-directory` instead.

3. **`pkcs11-keygen` / `pkcs11-list` / `pkcs11-tokens` / `pkcs11-destroy`** — These were BIND's *native* PKCS#11 utilities, removed in 9.18. Replaced all occurrences (key generation step, ZSK rollover, health-check script, backup/restore scripts, quick reference) with OpenSC `pkcs11-tool` equivalents (`--keypairgen --key-type rsa:2048 / EC:prime256v1`, `--list-objects`, `--list-token-slots`, `--delete-object`).

4. **`pkcs11-keyfromlabel` does not exist** — The real BIND tool is `dnssec-keyfromlabel`. Replaced it (key creation step, ceremony script, quick reference) with `dnssec-keyfromlabel -E pkcs11 -l "pkcs11:object=..."`, which writes the `.key`/`.private` files that reference the HSM key. Also removed the incorrect hand-written `.private` file (that file is produced by `dnssec-keyfromlabel`, not by `cat`).

5. **`dnssec-signzone` missing `-E pkcs11`** — Without the engine flag, signing would not use the HSM keys. Added `-E pkcs11` in the signing step and the quick reference.

6. **AWS CloudHSM section used Client SDK 3** (`cloudhsm_mgmt_util`, `loginHSM PRECO`, `changePswd`, `createUser CU`, the `cloudhsm-client` daemon, and `cloudhsmv2-software` S3 RPM URLs) — Client SDK 3 is **end of support** and those download URLs/tools are gone. Migrated user management to `cloudhsm-cli` (`cluster activate`, `interactive`, `login`, `user change-password`, `user create --role crypto-user`), switched installation to the SDK 5 `cloudhsm-cli` and `cloudhsm-pkcs11` packages from `pkgs.cloudhsm.amazonaws.com`, used `configure-cli`/`configure-pkcs11` for bootstrapping (no persistent daemon in SDK 5), and corrected the PIN env var to `CLOUDHSM_PIN`.

7. **1024-bit RSA ZSK** — 1024-bit RSA is below current minimums (NIST/ICANN guidance is ≥2048-bit RSA or ECDSA). Bumped ZSK generation examples to RSA 2048 (the post already recommends ECDSA as the modern alternative). Also dropped the "extractable for backup" flag on the ceremony KSK, since HSM keys should stay non-extractable (Luna HSM backup uses wrapped partition cloning, not extractable keys) — consistent with the post's own "keys never leave the HSM" claim.

## Review Notes
- **PowerDNS HSM section left as-is but flagged**: PowerDNS PKCS#11 support is an experimental build-time feature, and DNSSEC is normally enabled per-zone via `pdnsutil secure-zone` rather than a global `dnssec=yes` directive. The standalone `/etc/powerdns/pkcs11.conf` shown is illustrative; exact directives vary by PowerDNS build/version. Readers should confirm against the PowerDNS docs for their version before relying on it. Not rewritten because correct syntax is highly build-dependent.
- **engine_pkcs11 + OpenSSL 3.x caveat**: OpenSSL deprecated engines in 3.x. ISC notes engine_pkcs11 works cleanly with OpenSSL 1.1.x; on OpenSSL 3.x it requires `-DOPENSSL_API_COMPAT=10100`. The fixed build text targets OpenSSL 1.1.x; deployments on OpenSSL 3.x should account for this. (A newer PKCS#11 *provider* path also exists but is less mature.)
- **NSEC3 parameters**: The KASP example uses SHA-1 with 10 iterations. Per RFC 9276 (current best practice), NSEC3 should use 0 extra iterations and an empty/short salt. Not an error for the algorithm choice, but worth modernizing in a future revision.
- **OpenDNSSEC download URL**: The `github.com/opendnssec/opendnssec/releases/download/2.1.13/...tar.gz` URL was left as-is; OpenDNSSEC source tarballs are primarily distributed via dist.opendnssec.org. The `ods-enforcer`/`ods-hsmutil` commands and conf.xml/kasp.xml structure are correct for OpenDNSSEC 2.x.
- **YubiHSM 2 section** verified as plausible: `yubihsm-connector` default port 12345, `yubihsm-shell` `put authkey`/`delete` argument order, and package names are consistent with Yubico's tooling. Left unchanged.
