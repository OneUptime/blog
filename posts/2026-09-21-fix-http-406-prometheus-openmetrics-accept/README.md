# How to Fix HTTP 406 Errors When Prometheus Requests application/openmetrics-text

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Prometheus, HTTP, Monitoring, DevOps

Description: Diagnose 406 responses on metrics routes by reproducing Prometheus Accept headers and repairing negotiation in exporters, frameworks, and proxies.

---

An HTTP `406 Not Acceptable` during a Prometheus scrape usually means an HTTP component rejected the requested representation before Prometheus could parse metrics. Adding `# EOF` to a file will not repair a request that never reaches the exporter.

Prometheus can advertise several alternatives in one `Accept` header, including `application/openmetrics-text`. A server must inspect the complete list, including media-type parameters and quality weights. The [official negotiation documentation](https://prometheus.io/docs/instrumenting/content_negotiation/) describes this selection and its Prometheus-text fallback behavior.

## Reproduce three distinct requests

Use the exact URL shown on the Prometheus Targets page, including its path. Keep response headers and error bodies so that you can identify which component generated the 406.

```bash
curl -sS -D default.headers \
  http://exporter.internal:8000/metrics -o default.body

curl -sS -D text.headers \
  -H 'Accept: text/plain;version=0.0.4' \
  http://exporter.internal:8000/metrics -o text.body

curl -sS -D mixed.headers \
  -H 'Accept: application/openmetrics-text;version=1.0.0;q=0.9,text/plain;version=0.0.4;q=0.5' \
  http://exporter.internal:8000/metrics -o mixed.body
```

If plain text succeeds but the mixed request fails, the endpoint may compare the entire header with a single string. It may also reject OpenMetrics as an unknown media type before considering the acceptable text alternative. Repeat with the actual Prometheus request header from an authorized proxy capture or request log; the simplified example is only a starting point.

A request with `Accept: */*` succeeding does not prove that the metrics route implements negotiation correctly. Browser requests and ad hoc curl calls often exercise a much more permissive path than a scraper.

## Locate the component returning 406

Run the same header matrix directly against the application and then through its gateway. Preserve authentication requirements in both tests. Compare status, `Server`, `Via`, and the body, but use logs to confirm attribution because headers can be rewritten.

Common patterns are:

- A web framework declares that every route produces JSON, including `/metrics`.
- A response serializer recognizes `text/plain` but does not register the OpenMetrics media type.
- A proxy rule rejects semicolons, version parameters, or multiple accepted media ranges.
- An application manually splits the header incorrectly and treats the first unsupported range as fatal.

Make a narrow change to the metrics route. Keep its authentication and network restrictions while allowing the exporter handler to select the representation.

## Repair the producer

Prefer the framework integration supplied by the metrics client. For Go, [`promhttp.HandlerFor`](https://pkg.go.dev/github.com/prometheus/client_golang/prometheus/promhttp) supports OpenMetrics negotiation when `EnableOpenMetrics` is enabled. For Python, use the client's documented [HTTP, WSGI, or ASGI integrations](https://prometheus.github.io/client_python/exporting/http/) rather than wrapping generated bytes in a JSON response.

If the application intentionally supports only traditional text, return its correctly identified text representation using the supported fallback behavior. Do not advertise OpenMetrics while sending a legacy body. Conversely, do not add a static `text/plain` header in front of an encoder that sometimes returns OpenMetrics.

For hand-written negotiation, test whitespace, reordered parameters, explicit quality values, exclusions, and wildcard ranges. An unsupported higher-priority option does not eliminate a supported lower-priority option.

## Use a scoped compatibility setting when necessary

While repairing a legacy endpoint, a supported Prometheus release can request traditional text for that job:

```yaml
scrape_configs:
  - job_name: legacy-worker
    scrape_protocols:
      - PrometheusText0.0.4
    static_configs:
      - targets: ["exporter.internal:8000"]
```

The [`scrape_protocols` setting](https://prometheus.io/docs/prometheus/latest/configuration/configuration/) controls protocol preferences. Confirm that the installed Prometheus version supports the field and inspect the resulting behavior; do not assume that the request becomes a literal one-value header with no wildcard.

`fallback_scrape_protocol` solves a different problem: choosing a parser when a successful response has a blank or invalid content type. It cannot turn an HTTP 406 response into a successful scrape. Increasing a timeout also does not fix media-type rejection.

## Confirm the repair through Prometheus

Repeat the original failing request through the deployed route. Check the returned format, its matching content type, and the complete payload. Then verify `up{job="legacy-worker"}` and one expected application metric in Prometheus.

Keep a regression case containing the real scraper header, especially its `version`, `escaping`, and `q` parameters. Once the exporter supports normal negotiation, remove the temporary protocol restriction and verify both old and new representations again.
