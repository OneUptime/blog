# How to Test PCI DSS Idle-Session Reauthentication Across Workstations and Jump Hosts

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: PCI DSS, Authentication, Security

Description: Test 15-minute idle-session reauthentication across local workstations, RDP, SSH, browser consoles, and jump hosts without confusing network activity with user presence.

---

An idle-session control succeeds when an unattended session cannot be resumed without the required reauthentication. A configured timeout value is only part of that evidence. Screen locks, remote desktop reconnection, browser SSO, and SSH connection reuse can behave differently even on the same workstation.

Build the test around the person leaving the console and someone else trying to continue. That exposes gaps a configuration-only review can miss.

## Define the intended protection

[PCI DSS v4.0.1 Requirement 8.2.8](https://www.pcisecuritystandards.org/document_library/) requires reauthentication after a user session has been idle for more than 15 minutes. Its testing procedure examines settings for an idle limit of 15 minutes or less.

[PCI SSC FAQ 1147](https://www.pcisecuritystandards.org/faqs/1147/) explains that the purpose is to prevent unauthorized use of an unattended console. Legitimate processing may continue while the screen is locked. The requirement does not demand that every background job be terminated when its operator steps away.

The standard's guidance allows system-level reauthentication protecting sessions on a machine or application-level enforcement. Evaluate the protection actually provided. A centrally managed workstation lock can be part of the design; do not automatically require every server-side job to stop.

## Map the reachable sessions

For each access route, record the visible interface, enforcement point, idle definition, configured timeout, unlock method, and reconnection behavior:

| Route | Questions to test |
| --- | --- |
| Managed workstation | Does it lock without keyboard or pointer activity? |
| RDP to jump host | Does the remote desktop lock, disconnect, or terminate? |
| SSH terminal | Can an unattended terminal still issue commands? |
| Browser administration | Does an expired page regain access through existing SSO? |
| Cloud or hypervisor console | Can another console reopen the same privileged session? |

Include local consoles, shared operations desks, remote-support tools, nested jump hosts, and browser tabs on secondary monitors. Document why each relevant path is protected, even where several depend on one enforced workstation lock.

## Separate human inactivity from traffic

Network keepalives indicate that a peer is reachable. They do not establish that a person is present. OpenSSH's [sshd_config manual](https://man.openbsd.org/sshd_config) describes `ClientAliveInterval` and `ClientAliveCountMax` as checks involving client responses. A healthy unattended client can keep answering them.

Similarly, channel activity can come from output generated by a long-running command. Recent OpenSSH versions provide `ChannelTimeout`, but its traffic-based semantics and the ability to open another channel mean it is not automatically equivalent to user reauthentication. Inspect the version and the complete session design before choosing it as evidence.

A shell prompt timeout also has limits: behavior can differ while a foreground program runs, inside terminal multiplexers, or after changing shells. Treat such settings as components to test, not universal proof.

## Run a timed behavioral test

Use a test account with realistic permissions and synthetic data. Confirm time synchronization, record the effective policy, and begin from a freshly authenticated session.

1. Open the relevant administrative interfaces and perform a harmless authorized action.
2. Record the last deliberate user activity and leave the device untouched.
3. Observe whether the intended lock or session restriction occurs within the configured period.
4. Attempt to resume without supplying the user's authentication factor.
5. Complete the permitted reauthentication and verify that legitimate work can continue.
6. Capture the resulting authentication and session events.

Do not keep moving the pointer to take screenshots during the idle interval. Use external observation or logs that do not reset the timer. Test the boundary deliberately rather than rounding a 16-minute observed timeout down to “about 15 minutes.”

Repeat with a running command, continuous log output, a background browser refresh, and an idle remote desktop. These cases reveal whether automated activity incorrectly prevents the control from engaging.

## Test reconnection and bypass paths

Disconnect the remote client and reconnect. Try opening a second browser tab, using the back button, reopening the administrative URL, and attaching to an existing terminal-multiplexer session through the approved route.

If an application timeout is the claimed enforcement point, verify that silent SSO does not simply reactivate the unattended session. If the workstation lock is the enforcement point, verify that remote-control tools, alternate consoles, or unmanaged devices cannot bypass that protection.

Check whether ordinary users can extend the timeout or disable the lock. Test both the default policy and any approved exceptions. An exception should identify the actual operational need and its assessment treatment; it should not silently become the default for administrators.

## Preserve useful evidence

Keep the device and application versions, identity, effective settings, test timestamps, observed lock time, denied resume attempt, successful reauthentication, and any remaining gaps together.

Avoid screenshots containing full PAN. [FAQ 1071](https://www.pcisecuritystandards.org/faqs/1071/) also discusses preventing indefinite browser display of card numbers. Use a synthetic page when proving that displayed information is concealed after inactivity.

Assign remediation to the enforcement point that failed, then rerun that route and its nearby bypass cases. Revisit the matrix after endpoint-policy changes, new jump hosts, browser SSO changes, or remote-access upgrades.
