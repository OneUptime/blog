## Issues Found
1. **VMFS and NFS expansion were conflated.** The post applied the VMFS rescan-and-grow sequence to both a backing LUN and an NFS export. The recovery paragraph now separates VMFS LUN growth from storage-side NFS filesystem expansion and vCenter refresh. It also notes that a completely full VMFS datastore can need minimal headroom for the metadata update required by the grow operation.
2. **The consolidation-space statement was too absolute.** The original text implied that every consolidation needs additional working space. Powered-off consolidation into an already allocated thick base disk is an exception. The text now directs the operator to check the specific chain's space requirements and retains the accurate warning that online consolidation creates a growing helper delta.
3. **Swap-file relocation used an ambiguous “migration” instruction.** Storage vMotion does not move a `.vswp` file stored on a host swap datastore. The post now specifies a full power-off and power-on or a compute-only vMotion to a correctly configured host, and clarifies that a guest reboot is insufficient.
4. **The snapshot-chain diagnostic could report a false inconsistency.** Unqualified `vmkfstools -e` can fail on the expected lock of a powered-on VM and report that a healthy chain is inconsistent. It was replaced with Broadcom's current read-only `vmkfstools -qv10 <current-descriptor.vmdk>` check, run on the host currently running the VM.
5. **Snapshot lock and managed-VDI guidance needed qualification.** A running VM normally holds expected locks, so “unlocked snapshot chains” was changed to chains without conflicting file locks. A warning was added not to run standard vCenter Consolidate or Delete All Snapshots against broker-managed linked or instant clones; those must be remediated through the VDI management console.
6. **The orphan proof omitted managed VMDKs that need not appear in a VMX file.** The proof sequence now requires checking Content Libraries and First Class Disk / Cloud Native Storage inventory before declaring a VMDK orphaned. These objects can be valid and intentionally unattached to a VM.
7. **One Broadcom link used a noncanonical truncated slug.** Article 414077 still resolved by article ID, but its path ended in `disk-spa.html`. The link now uses Broadcom's canonical `disk-spac.html` path.

## Review Notes
- The remaining shell commands are syntactically valid and current on supported ESXi releases. The unescaped dot in `grep -i '.vmdk'` is slightly broader as a regular expression, but it matches Broadcom's documented command and works for the stated check.
- The `du` wildcard does not include dot-prefixed files at the datastore root, but the following recursive `find` command includes them. The post correctly warns that `ls` reports logical size while thin or sparse allocation can differ.
- No product version is hard-coded. The core guidance was checked against current Broadcom material covering ESXi 7.x/8.x and ESX 9.x where applicable. The post correctly sends vSAN and vVol investigations to their native object and capacity views.
- The deletion guidance is deliberately more conservative than some individual Broadcom knowledge-base examples: it rejects wildcard removal and treats migration results or absent locks only as supporting evidence, not proof by themselves.
