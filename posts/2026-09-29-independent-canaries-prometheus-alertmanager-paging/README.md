# How to Monitor the Monitor: Independent Canaries for Prometheus, Alertmanager, and Your Paging Provider

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Monitoring, Prometheus, Alertmanager, Reliability

Description: Build independent diagnostic canaries for query freshness, alert evaluation, notification routing and paging delivery with separate failure domains.

A monitoring system cannot reliably report its own complete failure through the components that just failed. Self-metrics are valuable for degradation, but total loss requires an observer with an independent execution and notification path.

Use several small canaries with clearly bounded claims. A readiness request, a fresh query result and a delivered page prove different things. Combining them gives a diagnosis when the end-to-end heartbeat stops, instead of only saying that something in monitoring is broken.

## Give each canary one claim

| Canary | What it proves | What it does not prove |
| --- | --- | --- |
| Prometheus readiness | Server reports ready to serve | Recent ingestion or correct rules |
| Fresh query-visible timestamp | Selected data path is current | Alert routing |
| Always-firing rule renewal | Rule evaluation and chosen receiver path | Every production route |
| Controlled provider event | Selected provider integration processes events | Application instrumentation |
| Destination receipt check | Selected delivery destination receives test events | Every responder's device |

Host the observer outside the production cluster and avoid reusing the same backend for its state. Keep a durable record of expected renewals so an observer restart does not silently grant unlimited grace.

## Check Prometheus beyond HTTP availability

The [Prometheus management API](https://prometheus.io/docs/prometheus/latest/management_api/) distinguishes health and readiness endpoints. Check readiness, then query a timestamp generated by a known producer through the actual ingestion path:

```bash
curl --fail --silent --show-error \
  'https://prometheus.example.net/-/ready'

curl --fail --silent --show-error --get \
  --data-urlencode 'query=monitoring_canary_last_success_timestamp_seconds{pipeline="prod-eu"}' \
  'https://prometheus.example.net/api/v1/query'
```

These URLs are placeholders. Use the approved authentication mechanism without logging credentials. The observer should require a successful API response, the expected single identity, a finite numeric value and an acceptable age. An HTTP 200 containing an empty result does not pass the freshness check.

Check excessive future timestamps too. Clock errors should not produce a green state that lasts until the observer's clock catches up.

## Exercise rule evaluation and Alertmanager routing

A continuously firing canary rule can renew a deadline at an external receiver. Give it stable labels and a dedicated route whose grouping and repeat intervals are measured. Its receiver should accept only the intended firing identity and record receipt time.

This canary identifies loss of rule evaluation or its notification path. A direct POST to Alertmanager tests a smaller segment because it bypasses Prometheus. Keep both tests if the distinction helps locate failures.

The [Alertmanager management API](https://prometheus.io/docs/alerting/latest/management_api/) exposes health and readiness, but those endpoints do not prove a particular route or provider integration works. Inspect route matching, silences and inhibition when a firing canary is visible but not delivered.

## Test the paging provider independently

Send a controlled synthetic event to a dedicated provider test service on a modest schedule. For PagerDuty, the [Events API documentation](https://docs.pagerduty.com/developer/send-alert-event) describes triggering, acknowledging and resolving events and their deduplication identity.

Use one key per test occurrence, reused for retries of that occurrence and its resolution. Reusing one key forever can merge a later test into a previous incident that is still open. Generating a new key for every retry can create many incidents for one test. Keep occurrence identifiers in the observer's state rather than creating unbounded metric labels.

Observe more than API acceptance: verify the incident or delivery record through the provider's supported interfaces, then confirm receipt at a controlled destination when that is the claim being tested. Run periodic supervised tests of real on-call delivery rules after schedule or contact changes.

## Preserve a notification escape path

If the paging provider is unavailable, reporting that failure through the same provider is insufficient. Choose an independent alternate destination appropriate to the organization and test it. Independence includes identity, network and account dependencies, not only different API URLs.

Avoid a canary that sends a normal page every minute. Continuous renewals should go to a machine observer; only expiry or a meaningful failed test should notify responders. Coordinate the less frequent human-delivery exercise so it remains useful evidence rather than habitual noise.

## Diagnose failures from the pattern

Readiness failure plus missing query freshness points toward server availability. Readiness success with stale data points toward ingestion or the producer. Fresh query data with missing rule renewal narrows the path to evaluation and alert delivery. A successful direct provider test alongside failed Alertmanager delivery suggests routing or integration configuration.

These are hypotheses, not mathematical proofs: the canaries may cover different credentials or paths. Confirm the configuration equivalence before declaring a component innocent.

## Conclusion

Independent canaries make monitoring failure observable and diagnosable. Test readiness, freshness, rule renewal and delivery as separate claims, and retain an alternate notification path. Together they provide evidence that the system can still detect a failure and reach someone when its own dependencies break.
