# Return a Correlation ID in Every HTTP Response

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Correlation ID, HTTP, Express, Logging, Observability

Description: Add a public support ID before HTTP handling begins, preserve it through application errors, and verify gateway, cache, and browser behavior.

---

A user reporting “the checkout failed” often cannot provide enough information to find the request. Returning an opaque correlation ID gives the browser, mobile application, or support form a precise value to capture alongside the time and error message.

The practical contract is to include the ID on every HTTP response your application can produce, including validation errors, authentication failures, missing routes, and unexpected exceptions. Failures before HTTP exists, such as TLS negotiation errors, cannot carry an HTTP response header. Cover those with edge connection diagnostics instead of promising an impossible guarantee. Node can also generate HTTP errors before Express runs, such as parser rejections and request timeouts; those need server-level handling or edge coverage because application middleware cannot attach their IDs.

## Assign the ID before middleware can reject a request

Here is a complete Express 5 example. Save it as `server.mjs` in a small project with `express@5` installed:

```javascript
import express from 'express';
import { randomUUID } from 'node:crypto';

const app = express();

app.use((req, res, next) => {
  const correlationId = randomUUID();
  res.locals.correlationId = correlationId;
  res.setHeader('X-Correlation-ID', correlationId);

  res.on('finish', () => {
    console.log(JSON.stringify({
      event: 'http.completed',
      correlation_id: correlationId,
      method: req.method,
      status: res.statusCode,
    }));
  });
  next();
});

app.use(express.json());

app.get('/ok', (req, res) => res.json({ status: 'ok' }));
app.post('/echo', (req, res) => res.json(req.body));
app.get('/fail', async () => {
  throw new Error('Example dependency failure');
});

app.use((req, res) => {
  res.status(404).json({
    error: 'not_found',
    correlation_id: res.locals.correlationId,
  });
});

app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);
  const candidateStatus = err.status ?? err.statusCode;
  const status = Number.isInteger(candidateStatus)
    && candidateStatus >= 400 && candidateStatus <= 599
    ? candidateStatus : 500;
  console.error(JSON.stringify({
    event: 'http.failed',
    correlation_id: res.locals.correlationId,
    error_type: err.name,
  }));
  res.status(status).json({
    error: err.type === 'entity.parse.failed' ? 'invalid_json'
      : status < 500 ? 'request_error' : 'internal_error',
    correlation_id: res.locals.correlationId,
  });
});

app.listen(3000);
```

The middleware runs before the JSON parser, so malformed JSON still receives a correlation ID. It also runs before route matching and any authentication middleware you add afterward. The error handler comes last and keeps the same ID instead of generating a replacement.

Express 5 forwards rejected promises from route handlers to error handling. For Express 4, use the documented explicit `next(error)` pattern or a supported async wrapper. The [Express error handling guide](https://expressjs.com/en/guide/error-handling/) also explains why an error after headers are sent must be delegated rather than attempting a second response.

## Make the edge and application agree

The example generates the ID in the application and ignores incoming values. If a trusted gateway already owns ID generation, replace that one line with strict validation of its authenticated internal header. Do not enable unrestricted trust in client headers merely because a gateway usually exists.

For responses generated by the gateway itself, configure the gateway to attach its own ID and record it in access logs. The application cannot add a header to a request that never reached it. Check rate limiting, body-size rejection, maintenance responses, upstream timeouts, and gateway authentication failures.

There should be one public field with one authoritative value. If the gateway returns a different ID from the application, record an explicit mapping or change the policy so both use the same value. Two identically named response headers are a poor support contract because client libraries may expose them differently.

## Include a body field where users need it

A response header works for APIs, but an error screen usually reads the response body. Returning `correlation_id` in the error JSON makes the UI straightforward:

```javascript
const response = await fetch('/fail');
const body = await response.json();
if (!response.ok) {
  const id = response.headers.get('X-Correlation-ID')
    ?? body.correlation_id;
  document.querySelector('#error').textContent =
    `Request failed. Support reference: ${id ?? 'unavailable'}`;
}
```

Use text rendering rather than HTML interpolation. For cross-origin requests, expose the response header with `Access-Control-Expose-Headers: X-Correlation-ID` and configure the complete CORS policy. A header visible in developer tools is not necessarily readable by JavaScript.

The body and header should match on errors. Keep sensitive details, exception messages, database identifiers, and internal trace state out of the support message. The reference itself should be opaque and should never act as a credential for retrieving logs.

## Account for caching and streaming

A cache can replay a response header containing the ID of the request that originally populated the cache. Decide whether the public ID refers to the cached representation or to the current delivery. For per-delivery support IDs, generate or replace the header at the serving edge and log cache hit status with it. If a cached body includes `correlation_id`, replacing only the header leaves the two values inconsistent; update the body field as well or avoid caching those error responses.

Do not add the correlation ID to the cache key just to obtain uniqueness; that can eliminate cache reuse. For personalized error responses, use the application's normal cache-control policy.

For streaming responses, assign the header before the first bytes are sent. If a stream fails later, preserve the original ID in server logs. Once headers have been transmitted, a new error handler cannot retroactively change them or reliably replace the response body.

## Verify success and failure paths

Run the server and exercise independent response paths:

```bash
curl -i http://localhost:3000/ok
curl -i http://localhost:3000/missing
curl -i http://localhost:3000/fail
curl -i -H 'Content-Type: application/json' \
  --data '{' http://localhost:3000/echo
```

For each response, find exactly one `X-Correlation-ID`, then find its completion or failure record. Send concurrent requests to check that IDs do not leak between requests. Repeat the same checks through the deployed gateway and from a browser when cross-origin access is involved.

## Conclusion

Create the support ID before request processing begins and preserve it through the full response lifecycle. Add equivalent coverage at the gateway, make errors display the same value, and test cache and streaming behavior so the reference a user reports actually leads to the correct records.
