# How Groundcover Smart Sampling Works and When to Force-Sample Traces

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Groundcover, eBPF, Distributed Tracing, Sampling, OpenTelemetry, Kubernetes, APM

Description: Understand Groundcover smart sampling, its statistical limits, and safe ways to force-sample a request or Kubernetes workload.

---

Groundcover's eBPF trace pipeline separates observing a request from storing its trace. Its official documentation says the sensor processes every request for supported services, then smart sampling stores a fraction selected to represent errors, unusual latency, and normal behavior.

That design reduces storage while retaining useful examples, but it creates an important operational rule: "the sensor saw it" does not mean "an individual trace for it is queryable." Force sampling is the escape hatch for a narrow diagnostic case, not a replacement for capacity planning or metrics.

The controls below reflect Groundcover documentation reviewed on July 21, 2026. They apply specifically to eBPF traces generated by Groundcover sensors unless stated otherwise.

## What Smart Sampling Selects

Groundcover documents three broad selection groups for eBPF traces:

- requests with unusually high or low latency, evaluated per resource;
- requests returning an error response, such as an HTTP 500;
- normal requests that establish a baseline for the resource.

It says sampling decisions occur on the node through stream processing, so redundant traces do not need to be sent to storage. The result is intentionally enriched toward diagnostically useful cases.

Groundcover does not publish the full algorithm, exact sample proportions, lookback windows, or tie-breaking behavior. Do not invent those details or assume the mechanism is identical to an OpenTelemetry tail-sampling processor. OpenTelemetry describes head and tail sampling as general models; Groundcover's eBPF implementation is product-specific.

## Observation, Metrics, and Stored Traces Are Different

Use three distinct terms in dashboards and incident reviews:

1. **Observed requests** are requests the sensor processed for a supported protocol and workload.
2. **Aggregated application signals** summarize request rate, errors, and latency.
3. **Stored traces** are the selected request examples available for detailed inspection.

The stored trace set is not a simple random sample. Because errors and latency outliers are deliberately favored, counting stored traces does not estimate total request volume or an error rate. Use application metrics and golden signals for population-level rates. Use traces to explain representative requests.

The same selection bias affects comparisons. A service with ten stored slow traces is not necessarily worse than one with five. Different traffic, resources, and sampling decisions can produce those counts.

## Force One HTTP or gRPC Request

Groundcover documents a request header for HTTP and gRPC:

```http
x-groundcover-force-sample: true
```

This is the most precise option for a synthetic check, support reproduction, or a user journey with a known correlation ID. Add it to the specific request, reproduce the problem, then search for the request's time, service, route, and identifier.

Treat this header as an observability control. If arbitrary internet clients can send it unchanged, they may increase trace volume or cause sensitive request payloads to be retained. Groundcover's trace documentation says eBPF traces can contain headers, query parameters, and request and response bodies. Allow or inject the force-sample header at a trusted gateway for authorized diagnostics, strip untrusted copies, and apply Groundcover's documented payload obfuscation controls.

Also confirm that proxies and service meshes forward the header to the workload the sensor observes. Do not assume it force-samples unrelated background jobs or non-HTTP protocols.

## Force a Kubernetes Workload

For broader debugging, Groundcover documents this label or annotation on a pod:

```yaml
groundcover/force-sample: "true"
```

All traces for matching pods are then sampled. This is useful when a request cannot carry a header or when a short diagnostic window must cover every eBPF trace from a canary deployment.

Pod-wide force sampling can produce a sudden volume increase. Apply it to a low-traffic canary or a small replica set, define an expiry time and owner, watch storage and ingestion health, and remove it as soon as the test ends. Use a deployment mechanism that makes the rollback visible in source control.

For example, a temporary pod-template annotation can be applied through the normal deployment configuration:

```yaml
spec:
  template:
    metadata:
      annotations:
        groundcover/force-sample: "true"
```

Changing a pod template normally creates replacement pods. Account for that rollout in the experiment, and remove the annotation through the same deployment workflow.

## Understand the Global Limiter

Groundcover also documents `GC_GLOBALLIMITER_MAXQUEUE` under the sensor environment. Its value is a number of traces allowed per 100 milliseconds. The documentation's example value of `10` corresponds to 100 traces per second, and traces marked as issues are not affected by that limiter.

```yaml
agent:
  sensor:
    env:
      - name: GC_GLOBALLIMITER_MAXQUEUE
        value: 10
```

This setting controls overall production pressure. It is not a guarantee that every non-issue trace below the numerical rate is retained, nor is it a substitute for a targeted force-sample control. Confirm how your Groundcover version combines the limiter and force-sampling rules before changing production behavior.

## Third-Party Traces Use Different Controls

Groundcover explicitly separates eBPF sampling from traces produced by external libraries. An `x-groundcover-force-sample` header should not be assumed to override an OpenTelemetry SDK, Collector, or Datadog SDK decision.

For Datadog SDK traces sent to Groundcover in Kubernetes, Groundcover documents a separate `agent.sensor.apmIngestor.dataDog.samplingRatio` value from `0` to `1`, with a default of 5 percent. A value of `1` requests 100 percent ingestion for that path. Assess the volume impact before changing it.

OpenTelemetry sampling has its own boundaries. A head sampler usually decides near the trace's start and propagates that decision. A tail-sampling Collector waits for spans and must receive all spans for a trace; in a scaled gateway deployment, spans for the same trace need consistent routing. Configure those components according to OpenTelemetry documentation, not Groundcover's eBPF controls.

## A Safe Force-Sampling Runbook

Use a bounded experiment:

1. Define the question and the exact route, user flow, or canary pod.
2. Add a non-sensitive correlation ID that can also be found in logs.
3. Estimate peak requests per second and payload volume.
4. Prefer the request header over a pod-wide rule when possible.
5. Confirm ingress and proxies preserve the intended header only for trusted traffic.
6. Start the experiment and verify one known trace appears.
7. Reproduce the issue during a short, recorded time window.
8. Watch ingestion, ClickHouse storage, and sensor resources.
9. Remove the control and prove ordinary sampling resumed.
10. Record whether the diagnostic evidence was sufficient.

If the trace is still absent, check protocol support, workload selection, proxy behavior, payload obfuscation, time range, retention, and backend ingestion health. A force-sample directive cannot recover a request that occurred before the rule or header was present.

## Choose the Control That Matches the Question

Use ordinary smart sampling for continuous production visibility. Use a forced request for a single reproducible interaction. Use a forced canary pod for a bounded workload investigation. Adjust third-party sampling at that third-party path.

Most importantly, keep rate questions separate from example questions. Metrics tell you how often a condition occurs. Smart-sampled traces show what selected instances looked like. Force sampling deliberately captures the precise instance you need to inspect.
