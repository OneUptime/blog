## Issues Found

1. **Incorrect config option `rgw_ldap_bindpw`** (was line 37): The option `rgw_ldap_bindpw` does not exist in Ceph. The correct option is `rgw_ldap_secret`, which takes a file path to a file containing the bind password (default: `/etc/openldap/secret`). Changed to `rgw_ldap_secret = /etc/ceph/ldap_secret` and added a note that the file should contain the password in plaintext.

2. **Incorrect version "10.0.1"** (was line 19): LDAP support was introduced in Ceph Jewel (10.2.0), not 10.0.1. Version 10.0.x was a development pre-release series. Changed to "Ceph Jewel (10.2.0) or later".

3. **Misleading LDAP support check command** (was lines 26-27): `radosgw -v 2>&1 | grep -i ldap` does not reliably indicate LDAP support — the version output does not list build features. Removed this unreliable command, keeping only `radosgw --version`.

4. **Wrong authentication mechanism described as "bearer tokens"** (was lines 13, 100): RGW LDAP does NOT use HTTP Bearer token authentication. It uses standard S3 v2/v4 signature authentication where the LDAP token (generated by `radosgw-token`) is used as the S3 access key. Fixed the overview and Step 5 descriptions.

5. **Fabricated Python token generation code** (was lines 102-113): The post showed manual base64 encoding of a JSON structure `{"credentials": {"uid": ..., "password": ...}}` — this is not how RGW LDAP tokens work. The actual token format is `{"RGW_TOKEN": {"version": 1, "type": "ldap", "id": ..., "key": ...}}` and is generated by the `radosgw-token --encode --ttype=ldap` utility. Replaced with the correct `radosgw-token` workflow using `RGW_ACCESS_KEY_ID` and `RGW_SECRET_ACCESS_KEY` environment variables.

6. **Invalid `Authorization: Bearer` curl command** (was lines 117-118): S3/RGW does not accept Bearer token headers. The correct approach is to use standard S3 signature authentication via the AWS CLI or an S3-compatible SDK. Replaced with an `aws s3 ls` example using the generated token as `AWS_ACCESS_KEY_ID`.

7. **Invalid `?list_buckets` query parameter** (was line 118): There is no `?list_buckets` S3 API parameter. Listing buckets is done via `GET /` with standard S3 authentication. Fixed by replacing with the AWS CLI `s3 ls` command.

8. **Missing `rgw_ldap_secret` in Rook kubectl commands** (was lines 45-56): The Rook config override commands did not include `rgw_ldap_secret`, which is required for RGW to authenticate against LDAP. Added the missing command.

9. **Incorrect ceph.conf syntax highlighting** (was line 31): Changed code block language from `bash` to `ini` for the ceph.conf configuration block.

10. **Invalid `externalRgwEndpoints: []` field in CephObjectStore YAML** (was line 80): This field is not part of the standard CephObjectStore spec for a non-external store. Removed it.

11. **Kubernetes secret key name** (was line 63): Changed `--from-literal=bindpw=...` to `--from-literal=ldap-secret=...` and added explanation that the secret must be mounted as a file at the `rgw_ldap_secret` path.

## Review Notes
- The TLS configuration section (Step 4) shows creating a ConfigMap for the CA certificate but does not show how to mount it into the RGW pod or configure RGW to use it. This is a completeness gap but not a technical error — the exact mounting mechanism depends on the Rook version and deployment specifics.
- The `debug_rgw 20` setting in Step 6 is correct but produces very verbose output. A value of 10-15 may be more practical for targeted LDAP debugging.
- The `ldapsearch` command in Step 6 passes the password via `-w` flag on the command line, which exposes it in process listings. Using `-W` (prompt for password) or `-y passwordfile` would be more secure, though this is acceptable for a troubleshooting example.
