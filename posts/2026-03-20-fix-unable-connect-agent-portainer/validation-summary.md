## Issues Found
- The post described the Portainer Server to Agent link as raw TCP. I changed the diagram and explanation to HTTPS on port `9001` because current Portainer documentation states the Server communicates with the Agent over HTTPS using certificates generated by the Agent.
- The opening explanation said the error occurs when the server cannot reach the agent and cited TLS mismatches. I changed this to unsuccessful communication and agent authentication mismatches, because Portainer can reach the Agent at the network level and still fail due to `AGENT_SECRET` authentication.
- The `docker logs` example used option ordering that did not match the current Docker CLI reference form. I changed `docker logs portainer_agent --tail 50` to `docker logs --tail 50 portainer_agent`.
- The connectivity check implied that a successful TCP test fully validated the agent connection. I clarified that `telnet` and `nc` only confirm basic port reachability and do not validate Portainer's HTTPS and agent authentication steps.
- The Portainer Server secret example was incorrect. I replaced `--agent-secret mysecrettoken` with `-e AGENT_SECRET=mysecrettoken`, matching the official Portainer documentation for configuring a custom agent secret on the Portainer Server container.
- The explanation of a secret mismatch was too specific about the TLS handshake. I changed it to state that the HTTPS connection may succeed while agent authentication still fails, which matches Portainer's documented authentication model.
- The port-listening check used `docker exec ... netstat ...`, which is brittle and not the best match for the problem being diagnosed. I changed it to `docker port portainer_agent 9001`, which directly verifies that Docker published port `9001` on a reachable host address.
- The Portainer UI path for re-adding the environment was outdated. I updated it to the current flow documented by Portainer: **Environments > Add environment > Docker Standalone > Start Wizard > More options > Agent**.

## Review Notes
- Portainer currently documents the Docker Standalone Agent as a legacy option and recommends the Edge Agent for most new standalone deployments. The post remains technically relevant for existing Agent-based setups.
- Docker port publishing can interact unexpectedly with host firewalls because Docker manages its own iptables rules. In some environments, upstream network controls such as cloud security groups may matter as much as local firewall rules.
