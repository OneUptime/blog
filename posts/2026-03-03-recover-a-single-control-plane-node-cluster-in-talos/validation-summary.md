## Review Notes
- `talosctl services` (plural) is a valid cobra alias for `talosctl service`, defined in the Talos source. Both forms work identically, so the usages in this post are correct.
- `talosctl etcd status` exists as a subcommand in Talos v1.6+ and is documented in the v1.10 CLI reference.
- `talosctl bootstrap --recover-from <snapshot>` is the documented mechanism for restoring etcd from a snapshot during initial bootstrap.
- `talosctl reset --system-labels-to-wipe EPHEMERAL --graceful=false` is the correct way to wipe etcd data on a single-node cluster while preserving the OS install and machine config; `--graceful=false` is required because a single-node graceful reset would fail (no other members to hand off to).
- `talosctl health --wait-timeout` is documented (default `20m0s`).
- `talosctl get machineconfig -o yaml` produces a valid backup of the applied machine config including secrets, suitable for restore. Note for readers: the original `controlplane.yaml`/`worker.yaml`/`talosconfig` generated by `talosctl gen config` are also worth keeping, since they include the secret bundle in original form.
- The recovery flow (`talosctl reset` to wipe EPHEMERAL, then `talosctl bootstrap --recover-from`) matches the documented Talos disaster recovery procedure for restoring from an etcd snapshot.
- Minor caveat for future readers: in Scenario 3 ("Changed IP Addresses"), updating `cluster.controlPlane.endpoint` in a recovered config is only safe if the certificate SANs still cover the new endpoint; if they do not, the kubeconfig/cert flow may need additional regeneration. The post stops short of going into that, which is reasonable for scope.
