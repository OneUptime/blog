## Issues Found
- The `SET mykey "value" XX GET EXAT ...` example was described as "set only if key has expiration." `XX` on `SET` means "only if the key already exists," not "only if it has an expiration." Updated the comment and corrected the Redis version note to Redis 6.2+ for `GET` and `EXAT`.
- Python examples used `setex`, which Redis documentation marks as deprecated in favor of `SET ... EX`. Updated redis-py examples to use `r.set(..., ex=...)` and pipeline `set(..., ex=...)`.
- The `GETSET` replacement used separate `GET` and `SET KEEPTTL` calls, which is not an atomic replacement for `GETSET`. Updated it to use `SET` with `get=True` and `keepttl=True`.
- The early refresh snippet imported `time` but used `json` without importing it. Replaced the unused import with `import json`.
- The active expiration configuration note implied Redis 7+ has a memory limit specifically for expired keys. Reworded it to clarify that memory limits and eviction policies are separate from expiration cleanup.
- The post stated that hash fields cannot expire individually. This is outdated for Redis 7.4+, which added hash field expiration commands such as `HEXPIRE`. Updated the section to explain version-specific behavior and show a Redis 7.4+ `HEXPIRE` example, while keeping the separate-key workaround for older Redis versions.

## Review Notes
- Keyspace notification examples are technically correct for keyevent expired notifications, but production consumers should remember Redis generates `expired` events when keys are actually deleted, not exactly when their TTL reaches zero.
- The cache refresh examples are illustrative and do not implement distributed locking; high-concurrency production systems may need a Redis-backed lock or single-flight mechanism to avoid duplicate refresh work across processes.
