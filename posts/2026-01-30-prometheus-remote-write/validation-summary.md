## Issues Found
1. **Incorrect `MetricMetadata.MetricType` enum values in the protobuf snippet.** The post listed `SUMMARY = 3` and `HISTOGRAM = 4`, which does not match the upstream Prometheus `prompb/types.proto`. Replaced with the official enum ordering: `UNKNOWN=0, COUNTER=1, GAUGE=2, HISTOGRAM=3, GAUGEHISTOGRAM=4, SUMMARY=5, INFO=6, STATESET=7`.
2. **Wrong protobuf library import for prompb types.** The post imported `google.golang.org/protobuf/proto` and called `proto.Unmarshal` on a `prompb.WriteRequest`. The prompb package is generated by gogo-protobuf, so its types do not satisfy the APIv2 `proto.Message` interface — this call would fail at runtime. Replaced with `github.com/gogo/protobuf/proto`, which matches the approach used in Prometheus's own `storage/remote/write_handler.go`.
3. **Incorrect Prometheus remote storage metric names.** The post used the `<verb>_samples_total` naming pattern (e.g., `prometheus_remote_storage_dropped_samples_total`), but the actual metrics exported by Prometheus use the `samples_<verb>_total` pattern. Fixed:
   - `prometheus_remote_storage_dropped_samples_total` → `prometheus_remote_storage_samples_dropped_total`
   - `prometheus_remote_storage_failed_samples_total` → `prometheus_remote_storage_samples_failed_total`
   - `prometheus_remote_storage_retried_samples_total` → `prometheus_remote_storage_samples_retried_total`
   - `prometheus_remote_storage_pending_samples` → `prometheus_remote_storage_samples_pending`
   (`prometheus_remote_storage_samples_total` and `prometheus_remote_storage_sent_batch_duration_seconds` and `prometheus_remote_storage_queue_highest_sent_timestamp_seconds` were already correct.)

## Review Notes
- The `Histogram` protobuf message is intentionally elided ("fields omitted for brevity") which is acceptable for a tutorial, though readers integrating with real Prometheus native histograms will need the full schema from `prompb/types.proto`.
- The post returns `204 No Content` on successful writes. The Prometheus remote write 1.0 spec allows any 2xx response; both `200` and `204` are accepted. This is technically correct.
- The "process synchronously as fallback" comment in `flushLocked` is slightly misleading — the fallback path spawns a goroutine, which is actually asynchronous. Not a correctness issue, just a stale comment.
- The `defer reader.Close()` ordering in `GzipDecompressor.Decompress` is correct: `io.ReadAll` runs before the deferred close because the return value must be computed first.
- The `queue_config` fields (`capacity`, `max_shards`, `min_shards`, `max_samples_per_send`, `batch_send_deadline`, `min_backoff`, `max_backoff`, `retry_on_http_429`) and the top-level fields `send_exemplars` / `send_native_histograms` all match the current Prometheus configuration schema.
- The HPA `autoscaling/v2` API version is current (v2beta1/v2beta2 were removed in Kubernetes 1.26+); using `v2` is the right choice.
- The Prometheus prompb package may transition fully to standard `google.golang.org/protobuf` in the future (work is in progress in upstream Prometheus around Remote Write 2.0); readers building against newer Prometheus releases should re-check the import.
