# How to Pass Generated Values Between Drone Steps and Pipelines Without Dynamic Environment Variables

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Drone, CI/CD, Docker, YAML, DevOps

Description: Transfer generated Drone build values through workspace files within a pipeline and explicit artifacts across pipelines, with runtime validation and stable identifiers.

Exporting a variable in one Drone step does not update the environment of a later container. A top-level `environment` block also cannot run shell commands to discover values generated during the build.

Treat a generated version, digest, or release identifier as data. Write it to a file and load it explicitly in the consumer. Drone's Docker workspace persists between steps of the same pipeline, but separate pipelines have separate state. [Drone workspace](https://docs.drone.io/pipeline/docker/syntax/workspace/), [multi-pipeline isolation](https://docs.drone.io/pipeline/configuration/)

## Pass one value through a workspace file

This complete example derives a release label from the build's commit and current UTC date, then validates it in a separate step:

```yaml
kind: pipeline
type: docker
name: generated-value

steps:
  - name: produce
    image: alpine:3
    commands:
      - |
        set -eu
        mkdir -p .ci-output
        short_sha=$(printf '%s' "$${DRONE_COMMIT_SHA}" | cut -c1-12)
        release_day=$(date -u +%Y%m%d)
        printf '%s-%s\n' "$release_day" "$short_sha" > .ci-output/release-id.txt.tmp
        mv .ci-output/release-id.txt.tmp .ci-output/release-id.txt

  - name: consume
    image: alpine:3
    commands:
      - |
        set -eu
        test -s .ci-output/release-id.txt
        release_id=$(cat .ci-output/release-id.txt)
        case "$release_id" in
          ''|*[!A-Za-z0-9._-]*)
            echo "Invalid release identifier" >&2
            exit 1
            ;;
        esac
        export RELEASE_ID="$release_id"
        printf 'Consumer received release %s\n' "$RELEASE_ID"
```

The temporary-file rename avoids exposing a partly written file to a potential reader. The default sequential step order makes the producer finish before the consumer starts. If you later introduce a dependency graph, keep an explicit dependency between them.

This value is intentionally non-secret. For several fields, use a structured JSON artifact with an explicit schema and parse it with a JSON parser. Do not turn arbitrary downloaded content into shell code with `eval` or by sourcing an untrusted environment file.

## Keep runtime expansion out of configuration-time substitution

Drone performs parameter substitution before YAML parsing. A value generated by a command is not available at that earlier phase. The `$${DRONE_COMMIT_SHA}` expression above leaves expansion to the runtime shell. [Drone substitution rules](https://docs.drone.io/pipeline/environment/substitution/)

Likewise, this does not execute a command:

```yaml
environment:
  RELEASE_ID: "$(cat .ci-output/release-id.txt)"
```

It is a literal environment value. Construct the value in `commands` or a checked-in script after the file exists. Drone's environment documentation explicitly distinguishes environment declarations from shell evaluation. [Drone environment syntax](https://docs.drone.io/pipeline/environment/syntax/)

A plugin setting is also configuration supplied to a container, not a late-binding reference to a file produced by an earlier step. Use the plugin's documented file input if it has one, or call a suitable client from a command step after reading the value. Do not assume every plugin supports a shared dotenv convention.

## Transfer data explicitly between pipelines

Top-level `depends_on` can make a consumer pipeline wait for a producer, but it does not share their workspace. Store the generated file in an artifact service using a key that identifies the repository, build, and producer.

For example, on a tool image with AWS CLI installed and an appropriately scoped identity, the producer can upload:

```bash
artifact_prefix="s3://ci-artifacts-example/$DRONE_REPO/$DRONE_BUILD_NUMBER/package/$DRONE_COMMIT_SHA"
aws s3 cp .ci-output/release-id.txt "$artifact_prefix/release-id.txt"
```

The consumer, after its pipeline dependency completes, retrieves the same object:

```bash
artifact_prefix="s3://ci-artifacts-example/$DRONE_REPO/$DRONE_BUILD_NUMBER/package/$DRONE_COMMIT_SHA"
mkdir -p .ci-input
aws s3 cp "$artifact_prefix/release-id.txt" .ci-input/release-id.txt
test -s .ci-input/release-id.txt
```

Replace the bucket with an existing private artifact bucket and provision access separately. These are ordinary shell-script examples, so they use ordinary dollar expansion; double runtime parameter expressions if placing them directly in Drone YAML. [AWS CLI object copy](https://docs.aws.amazon.com/cli/latest/reference/s3/cp.html)

Run the same content validation before consuming the downloaded value. Missing required artifacts should fail the consumer, not fall back to a branch-wide `latest` file.

## Define retry and retention behavior

The example key identifies a build and commit, but a restarted build can regenerate a time-dependent value. Decide whether retries must reuse the first artifact or create a separate attempt identifier. Use immutable object versions or a content digest when overwriting would make a release ambiguous.

Restrict artifact writers to the intended producer and readers to the required consumers. A checksum detects corruption but does not establish trustworthy provenance when the same attacker can replace both file and checksum.

Verify the design by running two builds concurrently and checking that neither consumes the other's value. Then remove the required artifact in a test environment and confirm the consumer fails clearly. Those checks test the actual data contract instead of relying on a shared path name or a successful environment export.
