# Parse and Normalize Nonstandard Log Timestamps with OTTL

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OpenTelemetry, OTTL, Logging, Observability, Troubleshooting

Description: Parse custom timestamp strings with OTTL Time, preserve the original event time on failure, and format normalized output with an explicit offset.

A log can contain a useful event timestamp while its OTLP timestamp still reflects when a receiver read the record. OTTL can parse the application value into the log's event time, but it must handle malformed input without pretending that an old timestamp was successfully parsed.

This guide targets OpenTelemetry Collector Contrib **0.160.0**. It uses `Time` to parse, an integer cache value to track success, and `FormatTime` to create a readable normalized attribute.

## Identify the Source Format and Time Zone

Assume a producer emits this attribute:

```text
event.timestamp = 10/Sep/2026:09:15:30 +0100
```

The corresponding format is `%d/%b/%Y:%H:%M:%S %z`. `%b` parses an abbreviated month, and `%z` parses a numeric offset. The explicit `+0100` makes the instant unambiguous.

The [Time function documentation](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/pkg/ottl/ottlfuncs/README.md#time) describes ctime-like format substitutions, optional location, and optional locale. Do not assume every `strftime` token from another tool has identical behavior here.

In particular, OTTL's `%s` substitution represents nanoseconds in this formatting system; it is not a general Unix-seconds parser. Epoch values should use the appropriate Unix conversion rather than a guessed format string.

## Parse into Cache Before Updating the Record

Store the parsed instant as integer nanoseconds, which the cache can represent:

```yaml
processors:
  transform/event_time:
    error_mode: ignore
    log_statements:
      - context: log
        statements:
          - set(log.cache["event_time_nano"], UnixNano(Time(log.attributes["event.timestamp"], "%d/%b/%Y:%H:%M:%S %z"))) where IsString(log.attributes["event.timestamp"])
          - set(log.time_unix_nano, log.cache["event_time_nano"]) where IsInt(log.cache["event_time_nano"])
          - set(log.attributes["example.timestamp_normalized"], FormatTime(log.time, "%Y-%m-%dT%H:%M:%S%z")) where IsInt(log.cache["event_time_nano"])
          - set(log.attributes["example.timestamp_parse_failed"], true) where log.attributes["event.timestamp"] != nil and log.cache["event_time_nano"] == nil
```

If parsing fails, `ignore` logs the error and continues. The cache key remains absent, so the original log timestamp is preserved and no normalized value is generated by this group.

The success guard matters. An unconditional `FormatTime(log.time, ...)` after a failed parse could format the preexisting timestamp and make the record look successfully normalized.

The cache holds an integer rather than a Go `time.Time` object. The [log context reference](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/pkg/ottl/contexts/ottllog/README.md) lists supported cache value types and provides the separate time and nanosecond paths.

Use pipeline-owned output keys, or clear preexisting diagnostic keys before this group if producers can supply conflicting values. A marker already present on an input should not be mistaken for evidence generated by the current parse.

## Distinguish Event Time from Observed Time

`log.time` and `log.time_unix_nano` represent the event timestamp. The observed-time fields describe when the collection system observed the event. Changing one does not automatically change the other.

Retaining observed time can help diagnose ingestion delay. Do not overwrite it with the event time just to make two timestamps agree. A delayed or replayed log legitimately has different event and observation times.

Likewise, formatting a string attribute does not change the timestamp the backend uses for ordering. The explicit assignment to `log.time_unix_nano` is the step that updates the event timestamp.

## Handle Timestamps Without an Offset

For a known source zone, pass an IANA location:

```yaml
processors:
  transform/london_time:
    error_mode: ignore
    log_statements:
      - set(log.time, Time(log.attributes["event.local_time"], "%Y-%m-%d %H:%M:%S", "Europe/London")) where IsString(log.attributes["event.local_time"])
```

The Collector needs access to the relevant time-zone database through its runtime environment or embedded data. Test the actual container image rather than assuming the workstation's zone database matches it.

A local timestamp during a daylight-saving transition can be ambiguous or nonexistent. A parser cannot recover an offset that the producer omitted. Prefer source timestamps containing numeric offsets, and document the policy for legacy local times.

If month or weekday names are localized, specify the appropriate supported locale. A language change in a log formatter can otherwise break a format that previously worked.

## Verify the Parsed Instant and Failure Behavior

Send valid input, malformed text, a missing timestamp, a nonstring value, and an input with another numeric offset. The sample instant should correspond to `2026-09-10T08:15:30Z` regardless of the Collector host's local zone.

```bash
otelcol-contrib validate --config collector.yaml
otelcol-contrib --config collector.yaml
```

Inspect the exported event nanoseconds as well as the normalized string. Its format includes an offset rather than a hard-coded `Z`, so the output does not falsely label an arbitrary local time as UTC.

Also test fractional seconds if the producer emits them and decide how much precision the display attribute should retain. Formatting to whole seconds must not accidentally truncate the actual event timestamp used for ordering.

## Conclusion

Parse a known format and zone, track success before updating dependent fields, and preserve the original timestamp on failure. Event time, observed time, and formatted display text serve different purposes. Test all three with malformed inputs and offset-sensitive fixtures.
