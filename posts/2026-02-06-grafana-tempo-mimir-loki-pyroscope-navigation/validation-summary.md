## Issues Found
- The prerequisites did not mention that trace-to-profile correlation requires application instrumentation with the OpenTelemetry span profiling bridge and spans carrying `pyroscope.profile.id`. Added that prerequisite so readers know why the Profiles button may not appear.
- The `tracesToProfiles` custom query used a braced selector form. Grafana's trace-to-profiles provisioning example uses the label matcher expression form for custom queries, so the query was changed to `service_name="$${__span.tags["service.name"]}"`.
- The dashboard TraceQL example used `select(duration, status)`. TraceQL supports `select(...)`, but the documented field names are scoped fields or intrinsics, and a simple recent-traces table does not need that projection. Changed the query to `{resource.service.name = "$service"}` to match Grafana's documented TraceQL examples for service filtering.
- The verification step referred generically to a "Profiles" click. Updated it to expand a span with `pyroscope.profile.id` and click "Profiles for this span", matching Grafana's documented behavior.

## Review Notes
The data source provisioning blocks for Prometheus/Mimir exemplars, Tempo trace-to-logs, trace-to-metrics, service map, node graph, Loki derived fields, and Pyroscope data source type are consistent with current Grafana documentation. Service Graph rendering still depends on span metrics or service graph metrics being generated by Tempo metrics-generator or Grafana Alloy and written to the linked Prometheus-compatible backend.
