# How to Create OpenSearch Alert Messages That Include Matching Log Fields and a Dashboard Link

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OpenSearch, Alerting, Logging, Observability

Description: Return bounded source fields from an OpenSearch monitor, render them safely with Mustache, and include a stable investigation dashboard link.

---

An OpenSearch alert action can only render data present in its execution context. If a query-level monitor uses `"size": 0`, its aggregation can trigger correctly but `ctx.results.0.hits.hits` contains no log documents. Return a small, explicitly filtered set of hits and iterate over it with Mustache.

Keep the notification an investigation summary, not a log export. A few source fields plus monitor timing and a stable dashboard URL are safer and more readable than dumping `ctx.results.0`.

## Build a bounded extraction query

This query checks a five-minute window, filters errors, and returns the newest three examples:

```json
{
  "size": 3,
  "track_total_hits": true,
  "_source": [
    "@timestamp",
    "service.name",
    "log.level",
    "message",
    "trace_id"
  ],
  "sort": [
    {"@timestamp": {"order": "desc"}}
  ],
  "query": {
    "bool": {
      "filter": [
        {
          "range": {
            "@timestamp": {
              "from": "{{period_end}}||-5m",
              "to": "{{period_end}}",
              "include_lower": true,
              "include_upper": true
            }
          }
        },
        {"term": {"log.level": "ERROR"}}
      ]
    }
  }
}
```

Use field names and query variables generated by the monitor editor for your OpenSearch version. If `log.level` is mapped as text with a keyword subfield, target that exact-value field instead.

The trigger condition can use the total hit count:

```painless
return ctx.results[0].hits.total.value >= 5;
```

Test the query and trigger with **Run** before adding an action. The Alerting API can also execute a saved monitor with `dryrun=true`, which evaluates it without sending actions.

## Render matching fields with Mustache

Mustache uses dot notation for arrays in OpenSearch action templates. `ctx.results[0]` in Painless becomes `ctx.results.0` in the message:

```mustache
{{ctx.monitor.name}} is alerting
Trigger: {{ctx.trigger.name}} (severity {{ctx.trigger.severity}})
Window: {{ctx.periodStart}} to {{ctx.periodEnd}}
Matches: {{ctx.results.0.hits.total.value}}

Newest examples:
{{#ctx.results.0.hits.hits}}
- {{_source.@timestamp}} {{_source.service.name}} {{_source.log.level}}
  {{_source.message}}
  trace={{_source.trace_id}} index={{_index}} id={{_id}}
{{/ctx.results.0.hits.hits}}

Investigate: https://dashboards.example.com/app/dashboards#/view/REVIEWED_DASHBOARD_ID
```

Mustache sections iterate over the hit array. When no hits are returned, the section emits nothing.

Field names containing dots are stored as nested objects in many mappings, so `{{_source.service.name}}` is appropriate only when `_source` is nested that way. If your document contains a literal dotted key or another schema, use the structure shown by a dry run rather than guessing.

## Use a reviewed dashboard URL

Open the investigation dashboard in the same tenant or workspace used by responders, set its normal default filters, and copy its shareable URL. Prefer a stable saved-dashboard link over manually constructing internal `_a` and `_g` state parameters; those URLs are long, version-sensitive, and easy to break through incorrect escaping.

Put the monitor's start/end timestamps in the alert even if the link uses a relative default window. The responder can reproduce the exact interval without relying on notification delivery time.

If you need a dynamic deep link, generate it in a tested notification gateway that understands your deployed Dashboards version, base path, tenant/workspace, and URL encoding. Treat that as application code with tests—not as an improvised Mustache string.

## Handle webhook formatting safely

A custom webhook body must match its `Content-Type`. This simple payload is valid only if interpolated values cannot introduce quotes, newlines, or backslashes that invalidate JSON:

```json
{
  "text": "Monitor {{ctx.monitor.name}} triggered; open https://dashboards.example.com/app/dashboards#/view/REVIEWED_DASHBOARD_ID"
}
```

OpenSearch Mustache interpolation is not a general-purpose JSON encoder. For arbitrary log messages, use a notification channel that accepts plain text or send structured, allow-listed fields to an intermediary that performs correct JSON escaping.

## Security and data minimization

Monitors run with the permissions of their creator. The notification then leaves OpenSearch's access-control boundary, so a field readable by the monitor owner may be inappropriate for a chat room or ticket.

- Use `_source` filtering to include only operational fields.
- Never include credentials, tokens, full request bodies, or sensitive user data.
- Limit hit count and message size.
- Verify the notification channel audience.
- Ensure the dashboard enforces its own index and tenant permissions; possession of a link must not grant data access.

## Troubleshooting blank fields

- `ctx.results` is empty: inspect `ctx.error` and the monitor creator's permissions.
- Total count is nonzero but no examples: increase `size` from zero.
- `_source` is absent: check source filtering and whether `_source` is disabled.
- Mustache prints nothing: use `ctx.results.0`, not bracket notation, and verify the exact path in a dry run.
- Dashboard opens without data: align tenant/workspace, index pattern, filters, and time range.
