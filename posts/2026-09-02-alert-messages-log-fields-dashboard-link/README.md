# How to Create OpenSearch Alert Messages That Include Matching Log Fields and a Dashboard Link

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OpenSearch, Alerting, Logging, Observability

Description: Return bounded source fields from an OpenSearch monitor, render them safely with Mustache, and include a stable investigation dashboard link.

---

An OpenSearch alert action can only render data present in its execution context. If a query-level monitor uses `"size": 0`, its aggregation can trigger correctly but the search result's `hits.hits` array contains no log documents. Return a small, explicitly filtered set of hits and iterate over it with Mustache.

Keep the notification an investigation summary, not a log export. A few source fields plus monitor timing and a stable dashboard URL are safer and more readable than dumping `ctx.results`.

## Build a bounded extraction query

This query checks a five-minute window, filters errors, and returns the newest three examples:

```json
{
  "size": 3,
  "track_total_hits": true,
  "_source": [
    "@timestamp",
    "service.name",
    "log.level",
    "message",
    "trace_id"
  ],
  "sort": [
    {"@timestamp": {"order": "desc"}}
  ],
  "query": {
    "bool": {
      "filter": [
        {
          "range": {
            "@timestamp": {
              "gte": "{{period_end}}||-5m",
              "lte": "{{period_end}}",
              "format": "epoch_millis"
            }
          }
        },
        {"term": {"log.level": "ERROR"}}
      ]
    }
  }
}
```

Use field names and query variables generated by the monitor editor for your OpenSearch version. If `log.level` is mapped as text with a keyword subfield, use that exact-value subfield in the `term` query, but keep the original `log.level` path in `_source` because multi-fields are not part of `_source`.

The trigger condition can use the total hit count:

```painless
return ctx.results[0].hits.total.value >= 5;
```

Test the query and trigger with **Run** before adding an action. The Alerting API can also execute a saved monitor with `dryrun=true`, which evaluates it without sending actions.

## Render matching fields with Mustache

OpenSearch documents `ctx.results.0` as the action-template equivalent of `ctx.results[0]` in Painless. However, OpenSearch 3.8's optional `plugins.alerting.multi_tenancy_enabled` rendering path uses upstream Mustache directly and does not add numeric list lookup. Iterate the single-element `ctx.results` array instead; sections work with both renderers:

```mustache
{{ctx.monitor.name}} is alerting
Trigger: {{ctx.trigger.name}} (severity {{ctx.trigger.severity}})
Search window: five minutes ending at {{ctx.periodEnd}}
{{#ctx.results}}
Matches: {{hits.total.value}}

Newest examples:
{{#hits.hits}}
- {{_source.@timestamp}} {{_source.service.name}} {{_source.log.level}}
  {{_source.message}}
  trace={{_source.trace_id}} index={{_index}} id={{_id}}
{{/hits.hits}}
{{/ctx.results}}

Investigate: REVIEWED_DASHBOARD_URL
```

Mustache sections iterate over arrays. The outer section enters the search response, and the inner section iterates over its hits. When either array is empty, its section emits nothing.

Field paths such as `service.name` are commonly represented in `_source` as nested JSON, but `_source` follows the original indexed document's JSON structure. `{{_source.service.name}}` works only when that structure is nested. Mustache treats dots as path separators, so the expression cannot address a literal `service.name` key under `_source`; expose such a value under a dot-free alias before templating. For any other schema, use the structure shown by a dry run rather than guessing.

## Use a reviewed dashboard URL

Open the investigation dashboard in the same tenant or workspace used by responders, set its normal default filters, and copy its entire shareable URL, including any tenant or workspace context. Prefer a stable saved-dashboard link over manually constructing internal `_a` and `_g` state parameters; those URLs are long, version-sensitive, and easy to break through incorrect escaping.

Put the query's duration and ending timestamp in the alert even if the link uses a relative default window. The responder can reproduce the exact interval without relying on notification delivery time.

If you need a dynamic deep link, generate it in a tested notification gateway that understands your deployed Dashboards version, base path, tenant/workspace, and URL encoding. Treat that as application code with tests-not as an improvised Mustache string.

## Handle webhook formatting safely

A custom webhook body must match its `Content-Type`. The normal OpenSearch `ScriptService` renderer JSON-escapes ordinary `{{...}}` substitutions by default. In OpenSearch 3.8, enabling Alerting's optional `plugins.alerting.multi_tenancy_enabled` path bypasses that renderer and uses upstream Mustache's HTML escaping, which does not make arbitrary values safe as JSON strings. Test the rendered body with representative quotes, newlines, and backslashes:

```json
{
  "text": "Monitor {{ctx.monitor.name}} triggered; open REVIEWED_DASHBOARD_URL"
}
```

Mustache is not a general-purpose JSON serializer for objects or arrays. For arbitrary log messages, use a notification channel that accepts plain text or send structured, allow-listed fields to an intermediary that performs correct JSON escaping.

## Security and data minimization

When the Security plugin is enabled, monitors run with the permissions of the user who created or last modified them. The notification then leaves OpenSearch's access-control boundary, so a field readable by that user may be inappropriate for a chat room or ticket.

- Use `_source` filtering to include only operational fields.
- Never include credentials, tokens, full request bodies, or sensitive user data.
- Limit hit count and message size.
- Verify the notification channel audience.
- Ensure the dashboard enforces its own index and tenant/workspace permissions; possession of a link must not grant data access.

## Troubleshooting blank fields

- `ctx.results` is empty: inspect `ctx.error` and, when the Security plugin is enabled, the permissions of the user who created or last modified the monitor.
- Total count is nonzero but no examples: increase `size` from zero.
- `_source` is absent: check source filtering and whether `_source` is disabled.
- Mustache prints nothing: iterate with `{{#ctx.results}}...{{/ctx.results}}` and verify the exact result structure in a dry run.
- Dashboard opens without data: align tenant/workspace, index pattern, filters, and time range.
