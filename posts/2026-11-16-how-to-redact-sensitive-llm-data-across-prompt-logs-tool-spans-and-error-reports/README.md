# How to Redact Sensitive LLM Data in Prompt Logs, Tool Spans, and Errors

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: LLM, OpenTelemetry, Security, Privacy

Description: Prevent sensitive LLM content from leaking through prompt logging, tool instrumentation, and exception reporting with explicit telemetry boundaries.

A prompt can disappear from your application logs and still appear in a tool span, an HTTP debug message, or an error report. Redaction succeeds only when every exported representation follows the same data policy. Start by deciding which operational facts you need, then build telemetry from those facts instead of copying a request and removing a few fields.

This article focuses on observability data. Whether the original content may be sent to a model is a separate outbound-request policy.

## Map the three capture surfaces

Record where content becomes telemetry, including automatic integrations:

| Surface | Common accidental content | Useful replacement |
|---|---|---|
| Prompt logs | Messages, conversation history, uploaded text | Template version, input size, request ID |
| Tool spans | Arguments, SQL values, retrieved documents | Tool name, duration, result count, outcome |
| Error reports | Exception text, request bodies, breadcrumbs, frame locals | Error class, safe error code, release version |

Also inspect HTTP query strings, resource attributes, span events, and log bodies. An attribute redactor cannot sanitize content copied into a different field. OpenTelemetry recommends minimizing collection and explicitly reviewing what instrumentation libraries emit; it cannot identify your organization's sensitive data automatically. [Handling sensitive data in OpenTelemetry](https://opentelemetry.io/docs/security/handling-sensitive-data/).

Assign each surface an owner. The application team controls explicit logging, but framework instrumentation and an error-reporting integration might require different configuration. Document the configuration version alongside the application release so a later SDK upgrade does not silently restore payload capture.

## Export a small, typed event

Use a new telemetry object built from trusted enums and numeric values. This runnable Python example deliberately excludes all user-controlled strings from its output:

```python
import json

OPERATIONS = {"chat", "retrieve", "tool"}
OUTCOMES = {"ok", "timeout", "rejected", "failed"}

def telemetry_event(operation, outcome, elapsed_ms, input_chars):
    if operation not in OPERATIONS or outcome not in OUTCOMES:
        raise ValueError("unsupported telemetry label")
    if elapsed_ms < 0 or input_chars < 0:
        raise ValueError("invalid telemetry measurement")
    return {
        "operation": operation,
        "outcome": outcome,
        "elapsed_ms": round(float(elapsed_ms), 2),
        "input_chars": int(input_chars),
        "schema_version": "llm-telemetry-v1",
    }

raw = {"prompt": "Contact test.person@example.com", "api_key": "fixture-only"}
event = telemetry_event("chat", "failed", 125.8, len(raw["prompt"]))
encoded = json.dumps(event)
assert "test.person@example.com" not in encoded
assert "fixture-only" not in encoded
print(encoded)
```

This is a data-minimization example, not a general PII detector. For correlation, add an opaque request ID generated by your application. Keep it in traces and logs rather than as a high-cardinality metric label. Never use an email address as the request ID.

If approved debugging requires excerpts, place the detector before serialization and export. Specify supported languages, entity types, nested fields, and failure behavior. A detector error should suppress the excerpt and emit a safe status code, not fall back to the original text. Presidio's documentation explicitly says automated detection cannot guarantee that every sensitive item will be found. [Presidio overview and limitations](https://data-privacy-stack.github.io/presidio/).

## Treat exception reporting as a separate pipeline

Avoid recording `str(error)` when an upstream client embeds a request or response in the exception. Classify known exception types into a bounded set such as `provider_timeout` or `tool_validation_failed`. Unknown exceptions can use `unexpected_error` plus an opaque incident ID.

For Sentry's Python SDK, `before_send` can modify or discard error events. Transactions and streamed spans have separate controls, so configuring that callback alone does not cover performance data. Review breadcrumbs, request capture, and frame-local capture too. [Sentry Python event and span filtering](https://docs.sentry.io/platforms/python/configuration/filtering/).

Do not recursively log a redaction failure with the input attached. That creates a leak precisely when the protection is unavailable. Keep the error path small enough to test with the detector completely disabled or throwing an exception.

## Verify the bytes at each destination

Create synthetic fixtures containing recognizable markers in the prompt, nested tool arguments, tool output, and exception text. Include a simulated HTTP failure that echoes its request. Exercise normal completion, retry, timeout, cancellation, and background processing.

Capture exported logs, spans, and error envelopes in a local test sink. Search the serialized payloads for the markers. Inspect the final receiving systems as well: an exporter can sanitize one destination while an additional integration ships raw data elsewhere. Check attributes, event bodies, attachments, and breadcrumbs independently.

A Collector is useful as another control, but it cannot remove data already written to process stdout, a local disk queue, or a directly connected error service. Position protection before the first persistence boundary and keep Collector rules as defense in depth.

## Make regressions observable

Track safe counters for suppressed payloads, detector failures, and unknown telemetry fields. A sudden increase in suppression deserves investigation, but a zero count does not prove privacy: the code path might no longer invoke the detector.

After an instrumentation upgrade, repeat the synthetic export test and compare the event schema. When a leak is found, stop the offending capture path, inventory the destinations and retention copies, and use their supported deletion mechanisms. Fixing a formatter only protects future events. Preserve diagnostic value through durations, statuses, versions, and correlation IDs while limiting the sensitive content that can ever reach storage.
