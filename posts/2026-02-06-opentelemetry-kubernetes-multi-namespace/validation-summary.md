## Issues Found
- The `OpenTelemetryCollector` examples used processors such as `k8sattributes` and `tail_sampling` without specifying a collector distribution that includes Kubernetes/contrib components. Added `image: otel/opentelemetry-collector-k8s:latest` to the gateway and agent examples so the referenced processors are available.
- The custom gateway `Service` selector used only `app.kubernetes.io/name: otel-gateway-collector`, which is not the selector shape generated by the OpenTelemetry Operator. Updated the selector to match the operator-managed collector labels for the `observability/otel-gateway` instance.
- The namespace-specific filtering example claimed production and staging pipelines, but the staging pipeline was not filtered to staging spans. Updated the filter expressions so the production pipeline keeps only `production` namespace spans and the staging pipeline keeps only `staging` namespace spans before tail sampling.
- The application environment variable example pointed `OTEL_EXPORTER_OTLP_ENDPOINT` at port `4317` without pinning the OTLP protocol. Added `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` so SDKs that default to OTLP/HTTP do not send HTTP traffic to the gRPC receiver.
- The multi-language `Instrumentation` example used port `4317`, but Java and Python auto-instrumentation default to OTLP/HTTP in current operator documentation. Changed the endpoint to port `4318` and configured Node.js to use `http/protobuf` so the shared endpoint is valid for all listed languages.

## Review Notes
- The article intentionally uses example backend hostnames and API key placeholders; these are acceptable placeholders, not validated service endpoints.
- The tail sampling example is technically valid as a configuration pattern, but production deployments with multiple gateway replicas should ensure all spans for a trace reach the same collector instance, usually by using an appropriate load-balancing design.
