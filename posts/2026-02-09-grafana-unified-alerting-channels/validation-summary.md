## Issues Found
- The post claimed Grafana Alerting can query any datasource. Grafana-managed alerting requires alerting-enabled backend data sources, so the wording was narrowed to supported alerting-enabled datasources.
- The kube-prometheus-stack Grafana configuration included an `alerting.enabled: false` legacy alerting setting. Current Grafana uses `[unified_alerting]` with `enabled` defaulting to true, so the obsolete legacy stanza was removed.
- The high CPU alert treated CPU cores as a percentage. The PromQL query now multiplies by 100, the threshold changed from `0.8` to `80`, and the annotation reads the reduced expression value.
- Regex notification policy matchers were unquoted. They were updated to quoted matcher values, matching Grafana's documented provisioning examples.
- The API example for testing notifications used an incorrect/stale Alertmanager endpoint. It was updated to the current Kubernetes-style receiver test endpoint under `/apis/notifications.alerting.grafana.app/v1beta1/.../receivers/{uid}/test`.
- The meta-monitoring metric examples used non-current or undocumented metric names for current Grafana. They were replaced with documented scheduler and notification latency metrics.

## Review Notes
The alert rule provisioning examples remain representative examples. Grafana documentation recommends exporting alert rules from the UI or API when possible because the `data[].model` field is datasource-specific and easiest to keep correct when generated by Grafana.
