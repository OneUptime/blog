## Issues Found

### 1. Incorrect key storage mechanism description (Major)
**What was wrong:** The "How BlueStore Encryption Works" section stated that OSD encryption keys are stored in the "Ceph Monitor's key-value store." This describes native Ceph behavior (using `ceph-volume --dmcrypt`), but the post is about Rook. In Rook, OSD encryption keys are stored as Kubernetes Secrets in the Rook namespace by default.
**What was changed:** Rewrote the section to correctly describe Rook's key management: keys are generated by the Rook operator and stored as Kubernetes Secrets. Updated the bullet points to reflect Kubernetes Secrets (or external KMS) as the key store.

### 2. Incorrect Vault KMS configuration field names (Major)
**What was wrong:** The Vault KMS YAML example used `VAULT_BACKEND: v2` and `VAULT_SECRET_PATH: rook/osd-encryption`, neither of which are valid Rook configuration fields. It also included `tokenSecretName` alongside `VAULT_AUTH_METHOD: kubernetes`, which is contradictory — Kubernetes auth uses service account tokens, not a separate token secret.
**What was changed:** Replaced `VAULT_BACKEND: v2` with `VAULT_BACKEND_PATH: rook` (the Vault KV engine mount path). Removed `VAULT_SECRET_PATH` (not a valid field — Rook constructs the secret path automatically). Added `VAULT_SECRET_ENGINE: kv` (required field). Removed `tokenSecretName` since Kubernetes auth does not use it.

### 3. Incorrect backup procedure (Major)
**What was wrong:** The backup section instructed users to run `ceph config-key dump` to export encryption keys from the Monitor's KV store. While `ceph config-key dump` is a valid Ceph command, Rook does not store OSD encryption keys there — they are in Kubernetes Secrets. This command would not back up any encryption keys in a Rook deployment.
**What was changed:** Replaced with the correct `kubectl` command to export OSD encryption key secrets: `kubectl -n rook-ceph get secrets -l rook.io/type=osd-encryption -o yaml`. Updated the surrounding text to reference Kubernetes Secrets.

### 4. Incorrect summary and KMS section references to Monitor key store
**What was wrong:** The summary and KMS section intro text referenced the "Monitor cluster" and "Monitor key-value store" as the default key storage.
**What was changed:** Updated to reference "Kubernetes Secrets" and "encryption key secrets" consistently.

## Review Notes
- The `encrypted: true` field in `storageClassDeviceSets` is correct and well-documented in Rook.
- The verification commands (`ceph osd metadata`, `lsblk | grep dm`) are reasonable approaches to confirm encryption is active.
- The `rados bench` commands for performance comparison are syntactically correct.
- The post correctly notes that encryption must be enabled at OSD provisioning time and cannot be retroactively applied.
- The YAML structure for `CephCluster` CRD (`apiVersion: ceph.rook.io/v1`) is correct.
- AES-XTS as the default LUKS cipher and AES-NI acceleration claims are accurate.
