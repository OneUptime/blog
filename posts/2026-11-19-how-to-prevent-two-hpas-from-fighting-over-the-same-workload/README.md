# How to Prevent Two HPAs from Fighting Over the Same Workload

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Kubernetes, HPA, Autoscaling, Troubleshooting

Description: Find duplicate and overlapping HPA targets, consolidate metrics under one autoscaler, and prevent competing controllers from managing the same replica count.

---

Two teams can create different HPA objects for the same Deployment without noticing: one scales on CPU and another on queue depth. Both appear reasonable in isolation, but they cannot independently own the same workload scale.

Depending on the Kubernetes version and observed selectors, the symptom can include conflicting replica changes or an `AmbiguousSelector` warning that stops normal metric-based scaling. Do not rely on a duplicate configuration failing in one predictable way.

## Inventory targets across namespaces

Start with a read-only report:

```bash
kubectl get hpa -A -o json | jq -r '
  .items[] |
  [.metadata.namespace, .spec.scaleTargetRef.kind,
   .spec.scaleTargetRef.name, .metadata.name,
   .spec.scaleTargetRef.apiVersion] | @tsv'
```

An HPA targets a resource in its own namespace. Group by namespace, API group, kind, and name. API version strings can differ while referring to the same underlying resource, so grouping only by the full `apiVersion` can miss a duplicate.

This script reports duplicate target identities from a saved inventory:

```bash
kubectl get hpa -A -o json > hpas.json
```

```python
import json
from collections import defaultdict

owners = defaultdict(list)
with open("hpas.json") as stream:
    for hpa in json.load(stream)["items"]:
        ref = hpa["spec"]["scaleTargetRef"]
        version = ref.get("apiVersion", "")
        group = version.split("/")[0] if "/" in version else ""
        key = (hpa["metadata"]["namespace"], group,
               ref["kind"], ref["name"])
        owners[key].append(hpa["metadata"]["name"])
for target, names in sorted(owners.items()):
    if len(names) > 1:
        print(target, names)
```

Resolve omitted API versions and custom scale targets during review. This inventory catches exact target duplication; it does not prove that different targets select disjoint Pods.

## Check overlapping Pod selectors too

Read the scale subresource and selector for every suspicious target. Two different workload objects with overlapping selectors can expose the same Pods to multiple HPAs.

```bash
kubectl get --raw \
  '/apis/apps/v1/namespaces/production/deployments/checkout/scale'
kubectl describe hpa checkout-cpu -n production
kubectl describe hpa checkout-queue -n production
```

The [Kubernetes 1.35 controller](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/controller/podautoscaler/horizontal.go) checks whether selected Pods are controlled by multiple HPAs and can set `ScalingActive=False` with reason `AmbiguousSelector`. This is runtime detection based on observed selectors and Pods, not an API-level uniqueness guarantee for creating HPA objects.

Also inspect owner references. An HPA generated by an operator may be recreated after manual deletion. Correct its source configuration before attempting a permanent cleanup.

## Put multiple metrics in one HPA

The [HPA multiple-metrics behavior](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#scaling-on-multiple-metrics) provides the intended combination: one controller evaluates all configured metrics and uses the largest recommendation.

For example, retain CPU and queue depth in one object:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout
  minReplicas: 4
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
    - type: External
      external:
        metric:
          name: queue_pending_jobs
          selector:
            matchLabels:
              queue: checkout
        target:
          type: AverageValue
          averageValue: "40"
```

The queue adapter and metric must exist. Reconcile the old HPAs' bounds, rate policies, stabilization, and metric selectors deliberately; copying only their metric names can change behavior.

Prepare the consolidated manifest, validate it with server dry-run, and remove the redundant HPA through its managing system during a controlled change. Observe current capacity while transferring ownership. Merely renaming one HPA leaves the duplicate target intact.

## Prevent recurrence at the configuration boundary

Add a repository or deployment-pipeline check for duplicate target identities in rendered manifests. Include generated HPAs in the inventory and assign one owner for each workload's autoscaling configuration.

An admission policy that only sees one incoming object cannot automatically discover every other HPA without an inventory mechanism. If using admission enforcement, verify how its controller maintains cross-object state and handles concurrent creations. A periodic read-only inventory remains useful even with policy enforcement.

## Verify a single control loop remains

After cleanup, confirm that one intended HPA targets the workload, overlapping selectors are absent, warning events stop, and metrics produce expected recommendations. Test both demand growth and load removal.

Finally inspect Deployment replica writers such as GitOps tools, release scripts, and manual scale commands. Removing a duplicate HPA solves one source of conflict; stable autoscaling also requires the workload's replica field to have a clear operational owner.
