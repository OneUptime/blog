# ActiveMQ Failover: Reconnect, Backup Priority, and Transaction Replay

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: ActiveMQ, ActiveMQ Classic, Failover Transport, JMS Transactions, High Availability

Description: Configure ActiveMQ Classic failover reconnect behavior, preferred brokers, send timeouts, and transaction recovery without assuming exactly-once outcomes.

---

ActiveMQ Classic's `failover:` transport is a client reconnection layer. It can select another URI, reconnect sessions and consumers, and track some in-flight commands. It does not turn independent brokers into a replicated store, and it cannot remove the ambiguity of a connection failing while a send or commit reply is in flight.

Design the broker high-availability topology first. Then configure the client to fail over within that topology's guarantees.

## Start with a valid composite URI

```text
failover:(tcp://broker-a:61616,tcp://broker-b:61616)
  ?randomize=false
  &initialReconnectDelay=100
  &useExponentialBackOff=true
  &reconnectDelayExponent=2.0
  &maxReconnectDelay=30000
  &startupMaxReconnectAttempts=20
  &maxReconnectAttempts=-1
  &timeout=5000
```

Shown on multiple lines for readability, this must normally be passed as one URI. Encode `&` as `&amp;` inside XML.

The options after the closing parenthesis belong to the failover transport. Options for each nested TCP transport belong inside its URI, or can use the `nested.` prefix in Classic 5.9 and later:

```text
failover:(tcp://broker-a:61616,tcp://broker-b:61616)
  ?nested.wireFormat.maxInactivityDuration=30000
```

Do not assume a setting was accepted. Enable client diagnostics in a test and inspect the connection factory generated by your framework.

## Choose startup and reconnect behavior separately

`startupMaxReconnectAttempts` applies before the client has connected successfully. `maxReconnectAttempts` applies after a successful connection.

The Classic reference documents these important semantics:

- since 5.6, `maxReconnectAttempts=-1` means retry forever;
- `maxReconnectAttempts=0` disables reconnection;
- a positive value caps attempts;
- `initialReconnectDelay` controls the first wait;
- exponential backoff grows later waits up to `maxReconnectDelay`;
- `warnAfterReconnectAttempts` controls reconnect warning frequency, not behavior.

An infinite retry is appropriate only if the application exposes “not ready” and its callers can tolerate waiting. Otherwise a process can remain alive but unable to do useful work. A finite startup limit often helps orchestration fail fast, while bounded or indefinite post-connection recovery may be reasonable for a long-lived worker.

## Random selection and preferred backups are different

`randomize=true` is the default and spreads initial connections across the listed URIs. Set `randomize=false` when list order represents primary then secondary:

```text
failover:(tcp://primary:61616,tcp://secondary:61616)?randomize=false
```

`backup=true` asks the client to establish a second transport connection in advance for faster failover. It consumes another broker connection and does not replicate messages.

`priorityBackup=true` means the client prefers designated local URI(s) and will move back when one becomes available. With `randomize=false`, the first URI is prioritized by default; `priorityURIs` can name several preferred URIs.

Moving back to a preferred broker is another disruption. Use it only when locality or cost is worth the connection churn.

## Do not let sends block forever accidentally

Under failover, a send can block while no broker is connected. The `timeout` option bounds how long a message send waits for the failover transport to reconnect without terminating the reconnect process. It is not a general broker-response timeout and does not apply to `commit()`:

```text
failover:(tcp://broker-a:61616,tcp://broker-b:61616)?timeout=5000
```

After that timeout, the connection may later recover. If the send only waited for a connection, it did not reach a broker. If a transmission was attempted as the connection failed, the broker may have accepted it before the failure reached the client, so do not assume every send exception proves non-delivery. Include a business idempotency key in the message and make the consumer deduplicate side effects.

Install a `TransportListener` on the `ActiveMQConnectionFactory` before operations that may perform network work. Use transport events for readiness and observability, not as proof that an in-flight command did or did not commit.

## Understand transaction replay

The failover transport tracks transactions by default and can replay in-flight transaction commands after reconnect. The Classic documentation explicitly describes the hard case:

```text
client sends COMMIT
broker commits
connection fails before reply
client cannot know whether COMMIT arrived
```

From Classic 5.3.1, redelivery order is tracked and commit fails with `TransactionRolledBackException` if outstanding messages are not redelivered as expected. The application must treat that unit of work as rolled back and replay it.

That protects consistency better than pretending the commit succeeded, but it does not provide exactly-once external side effects. If a transaction includes a database or HTTP call outside the JMS transaction, reconcile it independently.

For consumers:

- expect a previously received message to be redelivered;
- use a stable business operation ID;
- commit state and deduplication atomically where possible;
- handle `TransactionRolledBackException` explicitly;
- never commit a replacement delivery while still applying the stale transaction's result.

For producers:

- a send failure after transmission begins can leave the outcome unknown at the network boundary;
- do not generate a new business ID for each retry;
- monitor duplicate business operations; broker destination auditing has no business-level deduplication guarantee;
- prefer an outbox when publishing must be atomic with a database update.

## Dynamic URI updates need trust boundaries

With `updateClusterClients=true`, a broker transport connector can tell clients about brokers added to the network. To send removal updates too, set `updateClusterClientsOnRemove=true`; its default is `false`. Clients accept updates by default through `updateURIsSupported=true`.

This reduces static configuration but makes broker-provided topology part of the client's trust boundary. Restrict broker administration, protect the transport with authentication/TLS, and use `updateClusterFilter` so unrelated network brokers are not advertised.

## Test the failure points that matter

A meaningful failover test matrix includes:

1. no broker available at process startup;
2. active broker lost between messages;
3. connection lost during persistent send;
4. connection lost before consumer acknowledgement;
5. connection lost while `commit()` is in flight;
6. preferred broker returning while on a backup;
7. every URI unavailable longer than `maxReconnectDelay`;
8. stale DNS or a TLS certificate valid for only one hostname.

Verify queue state and business outcomes, not just “client reconnected.” Measure reconnect duration, redeliveries, transaction rollbacks, duplicate business operations, and time spent not ready.
