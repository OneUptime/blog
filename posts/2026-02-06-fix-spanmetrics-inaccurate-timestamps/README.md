# How to Fix the spanmetrics Processor Producing Inaccurate Timestamps

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OpenTelemetry, Spanmetrics, Processor, Metric

Description: Fix inaccurate timestamps on metrics generated by the spanmetrics processor caused by aggregation timing misalignment.

The older `spanmetrics` processor (or the `span_metrics` connector, in newer Collector versions) generates metrics from spans, giving you RED metrics (Rate, Errors, Duration) without additional instrumentation. But you notice the timestamps on these derived metrics do not align with the actual span timestamps. Metrics might show a spike after the actual spike in traffic, or metric start times are wrong, causing backends to reject or misinterpret the data.

## Understanding the Problem

The spanmetrics processor and span metrics connector aggregate spans into metrics over time intervals. The timestamp on the resulting metric is determined by the aggregation interval, not by the individual span timestamps. This creates a few issues:

1. **Metric timestamps lag behind span timestamps** by up to one aggregation interval
2. **Start times can be incorrect** when the processor or connector first starts, causing cumulative metrics to show wrong rates
3. **Backends reject metrics** when timestamps appear to go backwards or have gaps

## Diagnosing the Issue

Check the Collector logs for timestamp-related warnings:

```bash
kubectl logs -n observability deployment/otel-collector | grep -i "timestamp\|time\|spanmetrics"

# Common messages:

# "dropping data point with start time before previous data point"
# "metric timestamp is before the start timestamp"
```

Compare span timestamps with metric timestamps in your backend:

```promql
# Check when the metric was actually recorded vs when spans arrived
# The difference shows the lag introduced by the processor
```

## The spanmetrics Configuration

Here is a typical spanmetrics setup that may produce timestamp issues:

```yaml
# Older configuration (processor - deprecated)
processors:
  spanmetrics:
    metrics_exporter: prometheus
    dimensions:
      - name: http.method
      - name: http.status_code
    histogram:
      explicit:
        buckets: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s]

# Newer configuration (connector)
connectors:
  span_metrics:
    histogram:
      explicit:
        buckets: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s]
    dimensions:
      - name: http.method
      - name: http.status_code
    metrics_flush_interval: 15s  # Default is 60s; this affects timestamp lag
```

## Fix 1: Reduce the Flush Interval

A shorter flush interval means metrics are exported more frequently, reducing the timestamp lag:

```yaml
connectors:
  span_metrics:
    metrics_flush_interval: 5s  # Reduce from the default 60s to 5s
    histogram:
      explicit:
        buckets: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s]
```

The trade-off is more frequent exports and slightly higher resource usage. But the metric timestamps will be much closer to the actual span timestamps.

## Fix 2: Use Delta Temporality

Cumulative temporality metrics track values from a fixed start time, which makes timestamp issues more visible. Switching to delta temporality can reduce problems:

```yaml
connectors:
  span_metrics:
    metrics_flush_interval: 15s
    aggregation_temporality: "AGGREGATION_TEMPORALITY_DELTA"
    histogram:
      explicit:
        buckets: [5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 5s, 10s]
```

Note that your backend and exporter path must support delta temporality. Prometheus Remote Write expects cumulative monotonic sums and histograms from the Collector exporter, while OTLP backends typically support both.

## Fix 3: Tune the Batch Processor

If the batch processor holds spans for too long before they reach the span metrics connector, the connector will aggregate late-arriving spans on a later flush. Keep the trace batch timeout short relative to the span metrics flush interval:

```yaml
processors:
  batch:
    send_batch_size: 512
    timeout: 1s  # Keep this short enough to avoid delayed aggregation

connectors:
  span_metrics:
    metrics_flush_interval: 5s
```

## Fix 4: Handle Start Time Correctly

When the Collector restarts, the spanmetrics processor loses its state. The first metric export after a restart might have a start time of "now," which creates a discontinuity in cumulative metrics:

```yaml
connectors:
  span_metrics:
    # Use resource_metrics_key_attributes to maintain consistent metric identity
    resource_metrics_key_attributes:
      - service.name
      - service.namespace
    metrics_flush_interval: 15s
```

Some backends handle this by detecting resets in cumulative counters. Make sure your backend is configured for this:

```yaml
# For Prometheus remote-write backends
exporters:
  prometheus_remote_write:
    endpoint: "https://prometheus.example.com/api/v1/write"
    # Keep span metrics cumulative for this exporter
```

## Fix 5: Use the Correct Pipeline Wiring

Make sure the traces pipeline exports to the `span_metrics` connector and that a metrics pipeline receives from it:

```yaml
service:
  pipelines:
    # Spans come in here
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [span_metrics, otlp/traces]  # span_metrics as connector

    # Metrics generated by span_metrics go here
    metrics/span_metrics:
      receivers: [span_metrics]
      processors: [batch]
      exporters: [otlp/metrics]
```

A common mistake is batching traces for too long before they reach the span metrics connector, which creates buffering delays before aggregation.

## Fix 6: Use Exponential Histograms

Exponential histograms are more efficient for some latency distributions because they adapt their buckets automatically, but they do not change flush timing:

```yaml
connectors:
  span_metrics:
    histogram:
      exponential:
        max_size: 160  # Number of buckets
    metrics_flush_interval: 15s
```

## Verification

After making changes, verify the metrics look correct:

```bash
# Export metrics to the debug exporter to inspect timestamps
exporters:
  debug:
    verbosity: detailed

# Check that metric timestamps are within the expected range
# Metric timestamp should be close to the current time
# Start timestamp should be the time the Collector started (for cumulative)
# or the start of the current interval (for delta)
```

The spanmetrics processor and span metrics connector are powerful tools for generating RED metrics from traces, but they introduce an inherent lag due to aggregation. Reduce the flush interval and keep trace batching short to minimize timestamp inaccuracy. For OTLP backends that are sensitive to timestamp ordering, delta temporality can be useful when the backend supports it.
