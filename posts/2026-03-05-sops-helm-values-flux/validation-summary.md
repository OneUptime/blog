## Issues Found
- The post used `HelmRelease.spec.dependsOn` to depend on a Flux Kustomization. Flux HelmRelease dependencies are for other HelmRelease objects, while Flux Kustomization dependencies belong under `Kustomization.spec.dependsOn`. I removed the invalid HelmRelease dependency and updated the example so the HelmRelease is applied from the same Flux Kustomization path as the generated Secret.
- The post stated that `valuesFrom` overrides inline `values` when keys overlap. Flux documents the opposite default merge order: referenced values are merged first, then inline values override them. I corrected the explanation.
- The post broadly said Flux decrypts any SOPS-encrypted files before applying them. Flux documents SOPS decryption for encrypted Secret data in a Kustomization, including Secret data generated by Kustomize. I narrowed the wording to avoid implying arbitrary file decryption.
- The common-pitfalls section said Flux applies encrypted data as-is without the decryption block. I adjusted this to say Flux cannot decrypt the generated Secret data and the HelmRelease will not receive usable plaintext values.

## Review Notes
The tutorial disables Kustomize's generated Secret name hash so the HelmRelease can reference a stable Secret name. This is valid, but future improvements could show the official Flux `kustomizeconfig.yaml` nameReference pattern instead, which allows hashed generated Secret names to be propagated into HelmRelease `valuesFrom` references.
