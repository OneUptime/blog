# Find Which Driver or Subsystem Created a sysfs Attribute

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Linux, Sysfs, Kernel, Troubleshooting, C

Description: Resolve class aliases, locate attribute registration, and trace generic subsystem callbacks into the hardware driver.

A file under `/sys/class` is not necessarily created by the hardware driver named in a nearby link. Generic device code, a bus, a class subsystem, or a hardware driver can register attributes. Finding the implementation requires following both the device hierarchy and the registration path.

The most useful result is a chain: visible filename, canonical device, registration owner, callback, and any hardware operation invoked by that callback.

## Resolve the class entry first

Suppose you are investigating the brightness attribute of a dedicated LED. Start with the device directory, not an assumed parent relationship:

```bash
class_device=/sys/class/leds/example:green:status
device=$(readlink -f "$class_device") || exit 1
printf '%s\n' "$device"
ls -l "$device/brightness"
readlink -e "$device/subsystem"
readlink -e "$device/driver"
```

The example LED name must be replaced with an observed entry. A missing `driver` link at this exact device is valid evidence; do not silently substitute a parent's driver as though the link existed.

The canonical path identifies the current object in `/sys/devices`. Walk actual ancestors and inspect their subsystem and driver links when more hardware context is needed. Do not depend on a fixed number of parent steps or a class-specific `device` shortcut. [Kernel sysfs access rules](https://docs.kernel.org/admin-guide/sysfs-rules.html)

## Search the ABI before the source

Search the kernel's ABI documentation for the filename and its surrounding path pattern. A short name such as `state` or `enable` is used by many unrelated interfaces; the subsystem and directory structure disambiguate it.

In a matching kernel source checkout:

```bash
rg -n 'brightness|/sys/class/leds' Documentation/ABI Documentation/leds
rg -n 'brightness_show|brightness_store|DEVICE_ATTR.*brightness' drivers/leds
```

Read the documented units, range, read/write behavior, and any conditions governing presence. For LEDs, the class documentation describes brightness relative to `max_brightness` and the interaction with triggers. Those semantics belong to the LED interface, not simply to one board's hardware driver. [Kernel LED class documentation](https://docs.kernel.org/leds/leds-class.html)

Use the source corresponding to the running distribution kernel for the final diagnosis. Upstream master is useful for orientation and comparison, but vendor patches and backports can change the implementation you are actually executing.

## Follow declaration into registration

Finding a callback is only half the trace. Determine how that callback becomes visible on this object. Look for declaration macros and the group arrays that reference them:

```bash
rg -n 'DEVICE_ATTR|__ATTR|attribute_group|groups' drivers/leds/led-class.c
rg -n 'dev_groups|device_add|device_register' drivers/leds/led-class.c
```

A filename may be generated by `DEVICE_ATTR_RW`, a custom `__ATTR`, or a subsystem-specific macro. A group may be attached through class defaults, device defaults, driver groups, or an explicit registration call. That explains why searching only the hardware module's source can miss the implementation.

For the LED example, the class implementation provides generic brightness attribute handling and connects it with the LED class object's operations. The hardware driver supplies callbacks through the subsystem's data structures. [Upstream LED class implementation](https://github.com/torvalds/linux/blob/master/drivers/leds/led-class.c)

## Trace the operation beyond the generic callback

Read the generic `store()` or `show()` callback and follow each helper that can affect the observed result. Parsing might happen in the class, synchronization in another helper, and register access in the hardware-specific callback.

Write a small trace in your notes:

```text
/sys/class/leds/<observed-name>/brightness
  -> canonical LED device
  -> LED class attribute group
  -> generic brightness store callback
  -> LED subsystem helper
  -> registered hardware brightness operation
```

The exact helper names depend on the kernel version and driver. This is a trace format, not a claim that every LED uses the same synchronous path.

For a failed write, identify where the returned error originates. For an unexpected readback, determine whether the callback returns cached policy, cached hardware state, or a fresh register read. A generic callback can be correct while a hardware callback fails, and the reverse is also possible.

## Check conditional creation

If the filename appears only on some devices, inspect group visibility callbacks, Kconfig guards, device capabilities, and runtime registration conditions. An attribute might exist only when a trigger is selected or hardware advertises a specific feature.

Do not assume the callback was removed merely because the file is absent. The code can be compiled and registered for other devices while remaining intentionally hidden for this one. Search the group and its visibility function, not only the filename's declaration. [Device infrastructure and attribute groups](https://docs.kernel.org/driver-api/infrastructure.html)

## Produce a reproducible report

Record the canonical devpath, subsystem, driver at each relevant level, module metadata, kernel release, source revision, and the exact input or readback. Include the registration chain and the lowest helper relevant to the symptom.

Avoid reporting that a parent driver owns all files beneath its directory. Device trees can contain children implemented by other frameworks. Distinguishing ownership from ancestry helps a maintainer route the bug to the correct subsystem and reproduce it without guessing your hardware layout.

## Conclusion

Finding a sysfs file's implementation requires both path resolution and registration tracing. Resolve the real device, use the ABI to identify its contract, and follow attribute groups into generic and hardware callbacks. That produces a precise explanation of who created the interface and who performs its operation.
