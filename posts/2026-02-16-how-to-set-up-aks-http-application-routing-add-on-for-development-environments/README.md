# How to Set Up AKS HTTP Application Routing Add-On for Development Environments

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: AKS, Kubernetes, HTTP Routing, Ingresses, Azure, Development, DNS

Description: Learn how to set up the AKS HTTP application routing add-on to quickly expose services with automatic DNS in development environments.

---

When you are building and testing applications on AKS, one of the first things you need is a way to reach your services from outside the cluster. Setting up a proper ingress controller with TLS certificates and DNS records is the right move for production, but for development environments it is overkill. You just want a URL that works.

The application routing add-on for AKS solves exactly this problem. It deploys a managed NGINX ingress controller and can create a default domain for quickly testing ingress routes. You set the ingress class on your ingress resources, and within a couple of minutes you have a working URL pointing to your service. No manual ingress controller installation, no certificate management headaches - just fast, functional routing for dev and test.

## Important Caveat

Before we get into the setup, a clear warning: the older HTTP application routing add-on was retired on March 3, 2025 and should not be used for new clusters. Use the current application routing add-on instead. The NGINX-based application routing add-on remains supported for production workloads through November 2026, but Microsoft recommends planning a move to the Gateway API-based application routing implementation for the longer term. For production, review the current AKS ingress guidance and use your own DNS, certificate, and hardening requirements.

## Enabling the Add-On

You can enable application routing when creating a new cluster or on an existing one. Here is how to do both.

```bash
# Install or update the AKS preview extension for default domain commands
az extension add --name aks-preview --upgrade

# Enable on a new AKS cluster

az aks create \
  --resource-group dev-rg \
  --name dev-cluster \
  --node-count 2 \
  --enable-app-routing \
  --enable-default-domain \
  --generate-ssh-keys

# Or enable on an existing cluster
az aks approuting enable \
  --resource-group dev-rg \
  --name dev-cluster \
  --enable-default-domain
```

When the add-on is enabled, AKS deploys a managed NGINX ingress controller in the `app-routing-system` namespace. If you enable the default domain, AKS also assigns an autogenerated domain name that you can use for development routing.

## Finding Your Default Domain

After enabling the add-on with the default domain, you need to know what domain was assigned. This is the domain you will use for your ingress rules.

```bash
# Get the default domain assigned by the add-on
az aks approuting defaultdomain show \
  --resource-group dev-rg \
  --name dev-cluster \
  -o table
```

Save the domain value from the output - you will use it in every ingress resource you create.

## Deploying a Sample Application

Let us walk through a complete example. We will deploy a simple web application and expose it through the application routing add-on.

First, create a deployment and service.

```yaml
# app-deployment.yaml
# Simple nginx deployment for testing the routing add-on
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
---
# Service that exposes the deployment internally
apiVersion: v1
kind: Service
metadata:
  name: web-app-svc
spec:
  type: ClusterIP
  ports:
    - port: 80
      targetPort: 80
  selector:
    app: web-app
```

Now create the ingress resource. This is where the add-on magic happens.

```yaml
# app-ingress.yaml
# Ingress resource that uses the application routing add-on
# Replace <DEFAULT_DOMAIN> with your actual domain from the az aks approuting defaultdomain show command
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-ingress
spec:
  ingressClassName: webapprouting.kubernetes.azure.com
  rules:
    - host: web-app.<DEFAULT_DOMAIN>
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app-svc
                port:
                  number: 80
```

Apply both files.

```bash
# Deploy the application and ingress
kubectl apply -f app-deployment.yaml
kubectl apply -f app-ingress.yaml
```

Within a few minutes, the application routing add-on picks up the ingress resource and your application becomes reachable at `web-app.<DEFAULT_DOMAIN>`.

## Verifying the Setup

After deploying, check that everything is working correctly.

```bash
# Verify the ingress controller pods are running
kubectl get pods -n app-routing-system

# Verify your ingress resource has an address assigned
kubectl get ingress web-app-ingress

# Get the ingress controller public IP address
kubectl get service -n app-routing-system nginx -o jsonpath="{.status.loadBalancer.ingress[0].ip}"

# Check DNS resolution
dig web-app.<DEFAULT_DOMAIN> +short
```

If the ingress shows an address but the DNS is not resolving yet, give it a few more minutes. DNS propagation can take a little time depending on TTL settings and resolver caching.

## Troubleshooting Common Issues

### Ingress Has No Address

If your ingress resource stays without an address for more than five minutes, check the ingress controller logs.

```bash
# Check ingress controller logs for errors
kubectl logs -n app-routing-system deploy/nginx --tail=50
```

Common causes include the ingress class being wrong (it must be exactly `webapprouting.kubernetes.azure.com`), the service name in the ingress not matching the actual service, or the add-on not being enabled successfully.

### DNS Not Resolving

If the ingress has an address but you cannot resolve the hostname from your machine, it is likely a propagation delay. You can verify the assigned default domain and then query the hostname directly.

```bash
# Show the default domain assigned to the cluster
az aks approuting defaultdomain show \
  --resource-group dev-rg \
  --name dev-cluster \
  -o table

# Use dig to check resolution
dig web-app.<DEFAULT_DOMAIN> +short
```

### Multiple Services on the Same Host

You can route different paths on the same hostname to different services.

```yaml
# multi-path-ingress.yaml
# Route different paths to different backend services
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-service-ingress
  annotations:
    # Rewrite target so /api requests are forwarded to / on the backend
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: webapprouting.kubernetes.azure.com
  rules:
    - host: myapp.<DEFAULT_DOMAIN>
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```

## Using with Namespaced Environments

A common pattern in development is to have one namespace per developer or per feature branch. The application routing add-on works across namespaces, so each developer can have their own hostname.

```bash
# Create a namespace for a developer
kubectl create namespace dev-alice

# Deploy the app in Alice's namespace
kubectl apply -f app-deployment.yaml -n dev-alice

# Create an ingress with Alice's subdomain
# The host would be: alice-web-app.<DEFAULT_DOMAIN>
```

Here is a script that automates creating a developer environment with its own routing.

```bash
#!/bin/bash
# create-dev-env.sh
# Creates a namespaced development environment with application routing
# Usage: ./create-dev-env.sh <developer-name> <default-domain>

DEV_NAME=$1
DEFAULT_DOMAIN=$2
NAMESPACE="dev-${DEV_NAME}"

# Create the namespace
kubectl create namespace "${NAMESPACE}" --dry-run=client -o yaml | kubectl apply -f -

# Deploy the application
kubectl apply -f app-deployment.yaml -n "${NAMESPACE}"

# Generate and apply the ingress with the developer-specific hostname
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ${DEV_NAME}-ingress
  namespace: ${NAMESPACE}
spec:
  ingressClassName: webapprouting.kubernetes.azure.com
  rules:
    - host: ${DEV_NAME}.\${DEFAULT_DOMAIN}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app-svc
                port:
                  number: 80
EOF

echo "Application will be available at: http://${DEV_NAME}.${DEFAULT_DOMAIN}"
```

## Migrating from the Old HTTP Application Routing Add-On

Microsoft retired the older HTTP application routing add-on on March 3, 2025. If you still have an older cluster using it, migrate to the current application routing add-on by enabling App Routing and updating your ingress resources to use `ingressClassName: webapprouting.kubernetes.azure.com` instead of the old `kubernetes.io/ingress.class: addon-http-application-routing` annotation.

```bash
# Enable the current application routing add-on
az aks approuting enable \
  --resource-group dev-rg \
  --name dev-cluster \
  --enable-default-domain
```

The current add-on integrates with the `IngressClass` resource properly and can also integrate with Azure DNS and Azure Key Vault when you need custom domains and certificates.

## Disabling the Add-On

When you no longer need the application routing add-on, you can disable it cleanly.

```bash
# Disable the add-on
az aks approuting disable \
  --resource-group dev-rg \
  --name dev-cluster
```

Some Kubernetes resources can remain in the `app-routing-system` namespace after the add-on is disabled to avoid traffic disruption. You can remove that namespace manually if you no longer need those resources.

```bash
# Delete remaining app routing resources if no longer needed
kubectl delete ns app-routing-system
```

## Wrapping Up

The application routing add-on is a quick and effective way to get external access to your AKS services during development. It removes the friction of setting up ingress controllers manually, letting you focus on building and testing your application. For production, review the current AKS ingress guidance, TLS requirements, rate limiting, and all the other features your users deserve. The add-on gets you moving fast when speed matters most - during the development cycle.
