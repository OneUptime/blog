# Python Multi-Stage Builds: Copy Wheels, a Virtualenv, or `site-packages`?

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Python, Docker, Multi-Stage Builds, Wheels, Virtual Environments, pip, Python Packaging

Description: Choose a Python artifact boundary based on native extensions, interpreter compatibility, console scripts, installation paths, repeatability, and runtime-image constraints.

---

A Python multi-stage build needs a deliberate boundary between build tooling and runtime files. Three common boundaries are a wheelhouse, a complete virtual environment, and a directory installed with pip's `--target`. They are not interchangeable filesystem-copy tricks.

For most services, build wheels in one stage and install them with the runtime interpreter in the final stage. Copying a virtual environment can be faster and simpler when both stages use the same interpreter, libc, architecture, and absolute environment path. A targeted package directory is useful for import-only applications or serverless-style layouts, but it needs manual path and entry-point handling.

## Option 1: Build and Install Wheels

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS wheel-builder
RUN apt-get update \
    && apt-get install -y --no-install-recommends build-essential \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    python -m pip wheel \
      --wheel-dir=/wheelhouse \
      --requirement requirements.txt

FROM python:3.14-slim AS runtime
WORKDIR /app
COPY requirements.txt ./
COPY --from=wheel-builder /wheelhouse /wheelhouse
RUN python -m pip install \
      --no-cache-dir \
      --no-index \
      --find-links=/wheelhouse \
      --requirement requirements.txt \
    && rm -rf /wheelhouse
COPY app/ ./app/
USER 10001:10001
CMD ["python", "-m", "app"]
```

PyPA documents `pip wheel` for building a directory of wheels and `pip install --no-index --find-links=...` for installing only from that directory. Installation happens with the runtime interpreter, so console-script shebangs and installation paths are created for the final environment.

Wheels containing native extensions are still platform artifacts. Build them for the runtime's Python implementation, ABI, operating system, libc family, and CPU architecture. Using the same pinned Python image family for both stages is the simple path. A wheel tagged `manylinux` targets a glibc compatibility policy; a `musllinux` wheel targets musl. Neither label makes one wheel interchangeable with the other libc.

Use a fully resolved, reviewed requirements file and hashes when the deployment needs bit-for-bit dependency control. The wheelhouse prevents an sdist compiler from being needed in the final image, but it does not by itself lock versions or prove artifact integrity.

## Option 2: Copy a Virtual Environment

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder
ENV VIRTUAL_ENV=/opt/venv
RUN python -m venv "$VIRTUAL_ENV"
ENV PATH="$VIRTUAL_ENV/bin:$PATH"
COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    python -m pip install --requirement requirements.txt

FROM python:3.14-slim AS runtime
ENV VIRTUAL_ENV=/opt/venv
ENV PATH="$VIRTUAL_ENV/bin:$PATH"
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
COPY app/ ./app/
USER 10001:10001
CMD ["python", "-m", "app"]
```

This pattern avoids a second install and transfers packages, metadata, and console scripts together. It is safe only under a strict contract:

- the environment remains at `/opt/venv` in both stages;
- the runtime supplies a compatible Python interpreter at the paths referenced by the environment;
- Python major/minor version, implementation, ABI, OS, CPU, and libc are compatible;
- any required shared libraries are installed in the runtime image.

Python's `venv` documentation says environments are inherently non-portable in the general case because installed scripts use absolute interpreter paths. A virtual environment is not a relocatable deployment archive. Copying it within one controlled Docker build works because the path and platform contract are deliberately held constant.

## Option 3: Install into an Import Directory

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder
COPY requirements.txt ./
RUN python -m pip install \
      --target=/opt/python \
      --requirement requirements.txt

FROM python:3.14-slim AS runtime
ENV PYTHONPATH=/opt/python
COPY --from=builder /opt/python /opt/python
WORKDIR /app
COPY app/ ./app/
USER 10001:10001
CMD ["python", "-m", "app"]
```

pip's `--target` installs packages into a chosen directory. This avoids hard-coding a versioned system `site-packages` path and makes imports work once `PYTHONPATH` is configured.

It is not a full virtual environment. Do not assume console scripts land on the runtime `PATH`, and remember that packages may carry data files or native extensions. Starting the application with `python -m ...` avoids relying on copied entry-point wrappers, but the same ABI and libc compatibility rules still apply.

Raw copying from a guessed path such as `/usr/local/lib/python3.14/site-packages` is the weakest option. It can omit scripts, installation metadata, files installed outside that directory, and path configuration. If a target directory is desired, have pip create it explicitly.

## A Practical Decision Rule

Choose wheels when you want the cleanest packaging boundary, runtime-correct script generation, or an auditable intermediate artifact. Choose a copied virtual environment when build and runtime are deliberately identical in all compatibility dimensions and build speed matters. Choose `--target` when the application is import-driven and you control `PYTHONPATH` and startup.

Whichever pattern you use, add a final-stage smoke test in CI:

```bash
docker run --rm python-service:dev \
  python -c 'import app; print(app.__file__)'
```

Also import every dependency with a native extension and run the real console entrypoint. Image construction succeeding proves that files copied, not that Python can load them.
