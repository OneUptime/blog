# How to Fix Prometheus 3 Scrapes Rejected for a Missing or Incorrect Content-Type

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Prometheus, HTTP, Monitoring, Observability

Description: Restore Prometheus 3 scrapes by matching endpoint Content-Type headers to their actual payload and using a narrowly scoped fallback when needed.

---

An exporter can return HTTP 200 and readable metrics while Prometheus 3 marks its scrape as failed. One common cause is a missing, unrecognized, or unparsable `Content-Type` header.

This is an intentional compatibility change. The [Prometheus 3 migration guide](https://prometheus.io/docs/prometheus/latest/migration/#scrape-protocols) explains that Prometheus 2 often defaulted to traditional text in these cases; Prometheus 3 rejects the scrape unless an appropriate fallback is configured. The durable fix is to make the endpoint identify the bytes it actually sends.

## Capture headers and body separately

Run a request from the same network path as the scraper:

```bash
curl -sS --fail-with-body -D response.headers \
  -H 'Accept: application/openmetrics-text;version=1.0.0,text/plain;version=0.0.4;q=0.5' \
  https://metrics.example.com/metrics -o response.body
```

Avoid using `curl -I`: that sends HEAD, which may follow a different application route. Do not combine headers and body into one metrics file, because an HTTP status line is not a metric sample.

Check the final response after redirects. A login page, proxy error, or JSON error object can still carry status 200. If the body is HTML, repairing its content type will not produce metrics; fix routing or authentication first.

## Match the representation to the header

For traditional Prometheus text 0.0.4, the response can use:

```http
Content-Type: text/plain; version=0.0.4; charset=utf-8
```

For OpenMetrics 1.0:

```http
Content-Type: application/openmetrics-text; version=1.0.0; charset=utf-8
```

OpenMetrics requires its corresponding structure, including the final `# EOF`. Its counter family metadata also differs from traditional text. These contracts are documented in [exposition formats](https://prometheus.io/docs/instrumenting/exposition_formats/) and the [OpenMetrics specification](https://prometheus.io/docs/specs/om/open_metrics_spec/).

A UTF-8-capable negotiated implementation may include an `escaping` parameter too. Preserve the header generated by that encoder instead of rebuilding it from an incomplete constant in middleware.

Typical header faults include `application/json`, an omitted header, a malformed version parameter, and multiple conflicting content-type headers. Inspect the application response directly and compare it with the response through ingress. If only the ingress path fails, investigate header rewrite rules and response transformations there.

## Fix the response at its source

A metrics handler should return the serializer's bytes directly and use the serializer's matching content type. A framework helper intended for strings may silently default to HTML. A helper intended for JSON may quote or escape the entire exposition.

For Python's OpenMetrics encoder, the relationship looks like this inside a suitable framework route:

```python
from prometheus_client import REGISTRY
from prometheus_client.openmetrics.exposition import (
    CONTENT_TYPE_LATEST,
    generate_latest,
)

body = generate_latest(REGISTRY)
content_type = CONTENT_TYPE_LATEST
# Return body as bytes with content_type in the framework response.
```

This fragment illustrates a fixed OpenMetrics representation; a route serving multiple formats should use the client's negotiated HTTP integration. The [client's exposition implementation](https://github.com/prometheus/client_python/blob/master/prometheus_client/openmetrics/exposition.py) supplies both the encoder and its content-type constant.

If a reverse proxy must repair a fixed legacy endpoint temporarily, first verify the complete payload format and ensure it never switches formats based on `Accept`. A blanket response-header override is unsafe for a negotiated endpoint.

## Apply a narrowly scoped fallback

When you cannot immediately change a known legacy exporter, configure the parser fallback on that job:

```yaml
scrape_configs:
  - job_name: legacy-worker
    fallback_scrape_protocol: PrometheusText0.0.4
    static_configs:
      - targets: ["worker.internal:8000"]
```

Choose `OpenMetricsText1.0.0` instead only when the body actually satisfies that format. The [configuration reference](https://prometheus.io/docs/prometheus/latest/configuration/configuration/) defines the fallback for blank, unparsable, or otherwise invalid content types.

This is not a universal override. A response with a recognized but incorrect media type can select the wrong parser and fail parsing; repair the mismatched producer header rather than expecting fallback to rescue it. Fallback also does not repair HTTP error statuses or malformed samples.

## Verify recovery and remove the workaround

Check the configuration using the promtool version shipped with your Prometheus release, reload through your normal deployment process, and inspect the target's most recent error. Confirm both `up` and a known application series after several scrape intervals.

When the exporter is fixed, remove the fallback and repeat the test. Keep a small integration assertion for status, media type, and format-specific parsing so that a framework or ingress upgrade cannot silently recreate the problem.
