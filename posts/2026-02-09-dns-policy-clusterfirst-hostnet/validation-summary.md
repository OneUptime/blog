## Issues Found
- The introduction said `hostNetwork: true` includes the host's DNS configuration. I changed this to explain that the default `ClusterFirst` policy falls back to `Default` behavior for host network pods, which uses node DNS configuration, matching Kubernetes documentation.
- The HostNetwork DNS challenges list said host network pods always use the node's `/etc/resolv.conf`. I changed this to clarify that this is true unless `dnsPolicy: ClusterFirstWithHostNet` is set.
- The DNS policy summary described `ClusterFirst` as simply using cluster DNS. I changed it to note the documented exception for `hostNetwork: true`.
- The ingress controller section said ingress controllers typically require host network. I changed this to say they can be configured to use host network when direct node-port binding is needed.
- The CNI section said CNI components need cluster DNS. I narrowed this to say `ClusterFirstWithHostNet` should be used when such components need to resolve cluster services.
- The Calico example comment said `KUBERNETES_SERVICE_HOST` uses cluster DNS. I changed this to clarify that a DNS name there requires working cluster DNS.
- The monitoring agent comment said ConfigMaps can be accessed via cluster DNS. I changed this to say the pod can resolve a cluster Service name, since ConfigMaps are Kubernetes API resources rather than DNS records.
- The expected `/etc/resolv.conf` block implied a fixed cluster DNS IP and search path. I changed it to an example because the nameserver and search domains vary by cluster and namespace.
- The custom DNS section now explicitly states that `dnsConfig` values are merged with the base DNS configuration generated by the selected DNS policy.
- The first best practice said to always use `ClusterFirstWithHostNet` for host network pods. I narrowed it to host network pods that need Kubernetes DNS.

## Review Notes
- The Kubernetes manifests use current API versions and valid Pod fields. For `hostNetwork: true`, the shown `hostPort` values match `containerPort`, which is required when `hostPort` is specified.
- `ClusterFirstWithHostNet` is not supported for Windows Pods according to Kubernetes documentation. The post is written around Linux-oriented examples, but a future revision could call out that caveat explicitly.
- The example images use pinned versions in most places, but `prom/node-exporter:latest` is still present in one example. This is technically valid, though pinning a version is usually preferable for production manifests.
