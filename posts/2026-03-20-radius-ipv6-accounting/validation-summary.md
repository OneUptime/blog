## Issues Found
- The sample IPv6 literals were invalid (`2001:db8::radius`, `2001:db8:nas::1`, and `2001:db8:home:a::/56`). I replaced them with valid documentation-prefix examples.
- The packet example incorrectly showed `Acct-Unique-Session-Id` as if it were sent by the NAS. In FreeRADIUS this value is generated by the `acct_unique` module, so I removed it from the on-wire sample and kept it only in the FreeRADIUS SQL context.
- The FreeRADIUS SQL snippet used outdated or incorrect FreeRADIUS 3.0 syntax (`accounting_start_query`) and implied the stock 3.0 schema lacked `framedipv6prefix` and `delegatedipv6prefix`. I replaced it with a valid `queries.conf` excerpt and corrected the schema note so only a custom `nasipv6address` column is presented as optional.
- The detail module example used `NAS-IPv6-Address` / `NAS-IP-Address` in the filename. The upstream FreeRADIUS 3.0 default uses the packet source address instead, so I corrected the example and clarified what `log_packet_header` does.
- The `radclient` accounting tests used octet values larger than a 32-bit RADIUS counter. I corrected the examples to use valid `Acct-Input-Octets` / `Acct-Output-Octets` values with `Acct-Input-Gigawords` / `Acct-Output-Gigawords` where required.
- The daily usage query referenced `acctinputgigawords` and `acctoutputgigawords`, which are not part of the stock FreeRADIUS 3.0 `radacct` schema because the shipped queries fold Gigawords into 64-bit octet columns. I rewrote the query to use `acctinputoctets` and `acctoutputoctets` directly and fixed the `GROUP BY`.
- The “last 24h” bandwidth query actually returned total session bytes for sessions that started in the last 24 hours. I narrowed the wording and filter so the query is honest about using sessions updated in the last 24 hours.
- The accounting-gap query referenced nonstandard or stale columns (`acctinteriminterval`, `acclastupdatetime`) and a custom `nasipv6address` field that is not present in the stock schema. I updated it to use the stock FreeRADIUS 3.0 `acctupdatetime` field and compatible columns.
- The Cisco section used unsupported or unverified `radius-server attribute 97` and `radius-server attribute 123` commands. I replaced that with a base RADIUS accounting configuration that matches Cisco documentation and made the IPv6-attribute note platform-scoped.

## Review Notes
- The post is now technically consistent with FreeRADIUS 3.0 and the relevant RADIUS RFCs.
- Some Cisco AAA/RADIUS behavior remains platform-specific; the post now reflects that by avoiding platform-agnostic claims about forced inclusion of IPv6 attributes.
- The reporting queries are still examples built on `radacct`. Exact per-day usage for long-lived sessions usually requires periodic rollups or detail-file processing rather than simple grouping on session rows.
