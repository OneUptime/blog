## Issues Found

### 1. Description mentioned "transactional outbox pattern" (not covered in the post)
- **What was wrong:** The post description claimed coverage of the "transactional outbox pattern," but the post never discusses or implements this Dapr feature. The outbox pattern in Dapr is a specific feature that atomically publishes events when state changes.
- **What was changed:** Updated description to say "transactional state operations" instead, which accurately reflects the content.

### 2. Unused `uuid` import in JavaScript example
- **What was wrong:** The publisher code imported `const { v4: uuidv4 } = require('uuid')` but never used it. The code correctly uses a deterministic ID instead of a random UUID, making the import dead code.
- **What was changed:** Removed the unused `uuid` import line.

### 3. Python `save_state` API called incorrectly
- **What was wrong:** The code used `dapr.save_state(store_name="statestore", states=[{...}])` passing a `states` list parameter. The Python SDK's `save_state()` method accepts single key-value pairs (`key`, `value`), not a list. For bulk operations, `save_bulk_state()` with `StateItem` objects is the correct method. Additionally, TTL metadata was nested inside `options.metadata` which is not the correct Python SDK structure.
- **What was changed:** Replaced with `dapr.save_state(store_name="statestore", key=dedup_key, value=..., state_metadata={"ttlInSeconds": "86400"})` using the correct single-state API and proper TTL metadata parameter.

### 4. Go section claimed "transactional state operations" but used separate calls
- **What was wrong:** The section was titled "Using Dapr Transactions for Atomic Processing" and described using "transactional state operations," but the code performed separate `GetState` and `SaveState` calls which are not atomic. Dapr provides `ExecuteStateTransaction` for actual atomic multi-key state operations.
- **What was changed:** Rewrote the Go example to use `client.ExecuteStateTransaction()` with `[]*dapr.StateOperation` to demonstrate actual transactional state operations, atomically saving both a dedup marker and a business result.

## Review Notes
- The check-then-act pattern (get state, check if exists, then process) has an inherent race condition window between the check and the save. This is a known limitation of this approach. For most use cases with at-least-once delivery, this window is acceptable, but the post could mention this caveat in a future update.
- The CloudEvents `id` field is automatically generated by Dapr and is unique per publish call. If the publisher retries, a new `id` is generated, so using the CloudEvents `id` alone does not deduplicate publisher retries. The post correctly recommends deterministic message IDs for publisher-side deduplication, but the CloudEvents section could clarify this distinction more explicitly.
- The `keyPrefix: name` value in the Redis component YAML uses the component name as key prefix. Common values are `appid` (default), `name`, or `none`. This is correct but worth noting for readers who may want `appid`-scoped keys.
