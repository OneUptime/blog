## Issues Found
- The first Watcher example used a `value_count` aggregation on `_id`. Elasticsearch restricts `_id` from aggregations, sorting, and scripting, so I changed the watch to use `ctx.payload.hits.total.value` from the search result instead.
- The Python polling example used deprecated `datetime.utcnow()` and older `body`-style search calls. I changed it to timezone-aware `datetime.now(timezone.utc)` and current Python client keyword arguments.
- The ingest pipeline section claimed a webhook could be triggered directly during indexing. Elasticsearch ingest processors transform documents and do not provide a built-in outbound webhook processor, so I changed the section to timestamp/marker enrichment for downstream Watcher, Kibana alerting, or polling.
- The ingest pipeline script tried to copy `ctx._id` into a notification field. `_id` is not a reliable ingest-pipeline notification identifier, especially with autogenerated IDs, so I removed that script and kept supported `set` processors.
- The reliable polling section claimed to use Point-in-Time but did not open or use a PIT, and it sorted by `_id`, which is restricted. I changed it to a `search_after` example using a stable keyword tie-breaker field.
- The Kibana `.es-query` rule example omitted required time window parameters. I added `timeWindowSize`, `timeWindowUnit`, and `searchType`, and moved the high-value order condition into the DSL query.

## Review Notes
- The examples assume timestamp fields such as `@timestamp` represent indexing or event arrival time. In production, users should store cursor state persistently and use a monotonic ingestion timestamp when they need exact "newly indexed" semantics.
- The `search_after` example requires the tie-breaker field, such as `event_id`, to be unique and mapped as a keyword/doc-values-backed field.
