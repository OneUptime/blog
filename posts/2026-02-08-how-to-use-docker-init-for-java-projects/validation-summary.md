## Issues Found
- The post claimed `docker init` detects Java projects by looking for `pom.xml` or `build.gradle` and generates Dockerfiles for both Maven and Gradle. Docker's official `docker init` reference documents the Java template as suitable for Maven projects packaged as an uber JAR, so the wording was narrowed to Maven and the Gradle section was changed to an adaptation of the same pattern.
- The `docker init` Java prompt example used an unsupported `./target` wording for the app directory and implied automatic project detection. Docker's official Java prompt asks for the relative app directory with a leading dot, so the prompt was corrected to `./src`, ordered consistently with the documented prompt, and described as the flow after choosing the Java template.
- The post described `eclipse-temurin` as the recommended OpenJDK distribution for containers. The wording was softened to a widely used official OpenJDK image because the official docs verify the image but do not make that exact recommendation.
- The JVM section said Java 17+ detects container memory limits automatically. `UseContainerSupport` is on by default since Java 10, so the version-specific claim was corrected.
- The Spring Boot layered JAR Dockerfile used the older `layertools` jarmode. Current Spring Boot documentation uses `-Djarmode=tools`, `extract --layers --destination`, and starts the extracted layout with `java -jar application.jar`, so the Dockerfile was updated.
- The Compose section overstated JVM behavior without a service memory limit. The wording was changed to explain that the JVM sizes itself against the memory visible to the container process rather than a service-specific budget.

## Review Notes
The Gradle Dockerfile remains a valid example pattern, but it is not presented as generated by Docker Init. The Compose `depends_on` health condition, `deploy.resources.limits.memory`, BuildKit cache mounts, Maven Wrapper usage, and Gradle `--no-daemon` flag were consistent with official documentation.
