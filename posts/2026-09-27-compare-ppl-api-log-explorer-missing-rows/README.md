# How to Compare OpenSearch PPL API Results with Log Explorer When Rows Disappear

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OpenSearch, Observability, Logging

Description: Isolate disappearing OpenSearch log rows by comparing the PPL API with Log Explorer using identical sources, timestamps, query stages, and result limits.

When PPL returns rows through the API but Log Explorer shows fewer results, the difference is not automatically an ingestion failure. The two interfaces may send different source expressions, time constraints, projections, or result limits. An aggregation can also replace thousands of events with a handful of groups by design.

Compare one controlled query at a time. The goal is to identify the first stage at which the API response and the UI's request or rendering diverge.

## Record the interface and version

OpenSearch has more than one log exploration experience. The dataset-based **Discover > Logs** interface is documented as introduced in Dashboards 3.5. Older Observability interfaces use different controls and saved objects.

In the newer interface, the dataset selector supplies the source context, and aggregation switches the display toward visualization. Do not assume an example showing only `| WHERE ...` is a complete REST API query. The [Discover Logs documentation](https://docs.opensearch.org/latest/observing-your-data/exploring-observability-data/discover-logs/) describes that interface.

Record the OpenSearch and Dashboards versions, selected data source, dataset or index expression, time field, absolute time range, and user identity. Using an administrator token for the API while the UI uses a restricted role is not a controlled comparison.

## Establish a minimal API baseline

In Dev Tools, use an explicit source and a fixed interval:

```http
POST /_plugins/_ppl
{
  "query": "source=`logs-prod` | where `@timestamp` >= timestamp('2026-09-27 09:00:00') and `@timestamp` < timestamp('2026-09-27 09:10:00') | stats count() as event_count"
}
```

Assume a UTC session and a date-mapped `@timestamp`. Replace the source and field with the dataset's actual choices. This count measures the selected population without depending on how many raw rows the UI can display.

Then retrieve a small ordered sample:

```http
POST /_plugins/_ppl
{
  "query": "source=`logs-prod` | where `@timestamp` >= timestamp('2026-09-27 09:00:00') and `@timestamp` < timestamp('2026-09-27 09:10:00') | sort + `@timestamp` | fields `@timestamp`, body | head 20"
}
```

If timestamps tie, several different samples can be valid. Include a stable, mapped event identifier as a secondary sort key when you need to compare exact rows.

## Read the actual response

The default tabular response contains `schema` and `datarows`. The schema describes column order and types; each data row follows that order. Save the response before interpreting a UI table that may format or hide columns.

Do not assume every row count represents total matching documents. A `stats` query returns groups, a `head` query returns a limited sample, and a UI may render only a portion of the returned data. The [SQL and PPL API reference](https://docs.opensearch.org/latest/sql-and-ppl/sql-and-ppl-api/index/) documents response formats and the query envelope.

That same reference documents `fetch_size` pagination for SQL with the JDBC format. Do not paste SQL cursor examples into `_ppl` as a generic cure for missing rows. Check the supported PPL capabilities for the deployed release.

## Compare the UI's request

Set the UI to the same absolute interval, source, and time field. Remove extra filters and rerun the minimal query. Use available request inspection or the browser's network panel to capture the request and response generated by that action.

Compare these facts directly:

| Difference | What to investigate |
| --- | --- |
| Different source or cluster | Dataset selection and data-source connection |
| Extra time condition | Time picker, selected time field, and zone conversion |
| Extra filters | Saved search state or active UI filters |
| Same request, different authorization | Role, document-level security, or tenant context |
| Same response, fewer displayed rows | Presentation limits, selected columns, or rendering error |

Protect captured requests because they can contain log content or authentication context. For a bug report, retain only the minimal sanitized query, mapping, fixture, response, and version information needed to reproduce the difference.

## Add query stages until the result changes

Build from the baseline in this order: field selection, value filter, parsing, numeric conversion, aggregation, sorting, and final limit. Compare both interfaces after each addition.

For parsing, check the original body and capture together before filtering unmatched values. The [parse reference](https://docs.opensearch.org/latest/sql-and-ppl/ppl/commands/parse/) documents limitations involving overwritten fields and parsed fields used after `stats`. A query that drops rows after such a stage needs query investigation before UI investigation.

For aggregations, compare numeric totals and grouping keys rather than expecting one row per event. An error table with five rows may summarize five thousand log documents correctly.

## Inspect limits without changing them blindly

Review the deployment's SQL/PPL settings and the query's explicit `head` or sort limit. The [SQL settings reference](https://docs.opensearch.org/latest/sql-and-ppl/settings/) documents result-window and resource controls. Raising a global limit can increase memory use and does not fix a wrong dataset or an extra time filter.

If a complex API query itself behaves unexpectedly, request its `_explain` plan. If the same successful API response is present in the browser but the UI fails to render it, preserve that evidence and investigate the matching Dashboards release.

## Conclusion

Compare source, identity, absolute time bounds, query text, and response before changing ingestion. A count baseline and a small ordered sample separate missing documents from aggregation behavior, query restrictions, and UI presentation problems.
