# Woodpecker Pipeline Never Starts After a Push: Trace the Forge Webhook, Repository Sync, and Config Path

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Woodpecker CI, CI/CD, Webhooks, Troubleshooting, Git

Description: Trace a missing Woodpecker pipeline from the forge webhook through repository activation and workflow configuration discovery.

---

A push that produces no Woodpecker pipeline is usually failing before an agent is involved. The useful mental model is a chain: the forge emits a webhook, the Woodpecker server accepts and interprets it, the server loads workflow files from the pushed revision, and only then does it queue workflows for agents. Check that chain in order. Restarting agents while the server has never created a pipeline only hides the real failure.

This guide targets Woodpecker 3.x. Older installations can have different hook paths and configuration defaults, so consult the migration notes before applying current examples to a 2.x server.

## First Determine Whether a Pipeline Exists

Open the repository's Pipelines page immediately after a test push.

- If there is no new pipeline number, concentrate on repository activation, the webhook, event selection, commit skip markers, workflow-level `when` filters, and configuration discovery.
- If an error pipeline exists but has no workflows, inspect its configuration-fetch, YAML-parsing, and schema diagnostics.
- If a workflow exists and is `pending`, the webhook already worked. Move to agent labels, platform, capacity, and backend health instead.
- If the clone step fails, the event and scheduler worked; investigate clone credentials and network access.

That classification prevents four unrelated failure domains from being treated as one “Woodpecker did nothing” problem.

## 1. Confirm That the Repository Is Activated

Woodpecker does not listen to every repository visible through OAuth automatically. A user with repository administrator rights activates it from **Add repository**. Activation is important because Woodpecker needs permission to create the forge webhook.

If the repository is absent or looks stale:

1. Sign in as a user who still has admin permission on the forge repository.
2. Refresh or reload the repository list in Woodpecker.
3. Activate the correct repository, taking care with renamed organizations and repositories.
4. Open Project settings and verify that the project is active and points to the expected forge identity.

Refreshing the repository list and repairing a webhook solve different problems. A refresh updates repository visibility and permissions. Repair recreates or updates the hook for a repository that Woodpecker already knows. Do not assume a successful refresh proves that hook delivery works.

## 2. Inspect the Forge's Webhook Delivery

Make one small push with a neutral commit message, then open the webhook delivery history in GitHub, GitLab, Gitea, Forgejo, or Bitbucket. Look for the Woodpecker-owned hook and the delivery generated by that push.

Check all of the following:

- the hook is enabled;
- push events are selected;
- its destination is the public Woodpecker server, including any required path prefix;
- DNS resolves to the intended ingress or reverse proxy;
- the TLS certificate is valid from the forge's point of view;
- the response is a successful HTTP status rather than a timeout, redirect loop, `404`, or `502`;
- the delivery timestamp corresponds to the new push.

If there is no Woodpecker hook, use **Repair repository** in the repository settings, the administrator's repair-all action when appropriate, or run `woodpecker-cli repo repair <repo-id|repo-full-name>`. Repair is particularly important after migrations that changed webhook paths or tokens.

A response from a login page is not success. Reverse proxies must send the hook request to the Woodpecker server, not an interactive authentication gateway. Likewise, a `301` from HTTP to HTTPS may work for a browser yet fail for a forge that does not follow the redirect as expected. Configure the hook with its final HTTPS URL.

## 3. Verify Woodpecker's Public Webhook Address

`WOODPECKER_HOST` describes the public Woodpecker URL. In unusual proxy or split-DNS deployments, `WOODPECKER_EXPERT_WEBHOOK_HOST` can set the fully qualified URL that Woodpecker gives to forge webhooks. The expert value must include the scheme, host, and any prefix path.

For a conventional deployment, prefer one correct public URL rather than an expert override. From outside the Woodpecker network, test the same DNS name and TLS chain that the forge uses:

~~~bash
curl -I https://ci.example.com/
openssl s_client -connect ci.example.com:443 -servername ci.example.com </dev/null
~~~

These commands do not validate the secret webhook request itself, but they expose DNS, routing, and certificate problems. Check the Woodpecker server and proxy logs at the delivery timestamp. A forge timeout with no corresponding ingress log means the request never reached your edge. An ingress log with no Woodpecker log points to routing. A Woodpecker rejection points to the hook token, payload, or event handling.

For Gitea or Forgejo on a private address, also review the forge's outbound-webhook policy. Their official setup guidance notes that local connections may need to be explicitly allowed. Test connectivity from the forge container or host, not just from your laptop.

## 4. Check Repository Hook and Event Settings

Confirm that the Woodpecker-owned webhook at the forge still subscribes to `push`. **Repair repository** recreates the hook with Woodpecker's standard event subscriptions. Also check for a global workflow condition that excludes pushes.

A minimal push workflow for Woodpecker 3.x is:

~~~yaml
when:
  event: push
  branch: main

steps:
  - name: verify-event
    image: alpine:3.22
    commands:
      - echo "event=$CI_PIPELINE_EVENT"
      - echo "branch=$CI_COMMIT_BRANCH"
      - echo "ref=$CI_COMMIT_REF"
~~~

At workflow level, the keys in the `when` map must all match. This example runs only for a push whose branch is `main`. A pull request targeting `main` is not included because the event is also constrained.

Remember that Woodpecker honors `[SKIP CI]` and `[CI SKIP]` in commit messages, case-insensitively. Use a fresh test commit without either marker. A merge or squash commit can inherit text that unexpectedly contains one.

## 5. Validate the Pipeline Configuration Path

When the Project settings pipeline path is empty and the server uses its stock pipeline-config defaults, Woodpecker resolves configuration in this order:

1. workflow files matching `.woodpecker/*.{yaml,yml}`;
2. `.woodpecker.yaml`;
3. `.woodpecker.yml`.

Directory discovery reads matching YAML files only from that directory; it does not recurse into nested subdirectories. If you configure a custom file or directory, Woodpecker stops using the default search. A custom directory path must end in `/` when it is intended to contain multiple workflows.

Common mistakes include:

- configuring `.woodpecker/` but committing `.woodpecker.yml`;
- setting `.ci/woodpecker` as a directory without the trailing slash;
- using `.yaml` in settings while the repository contains `.yml`;
- placing workflows in `.woodpecker/services/api.yml`, which is nested too deeply;
- fixing the file only on another branch;
- changing case on a case-insensitive workstation but not recording that case change in Git.

Inspect the exact pushed revision rather than the working tree:

~~~bash
git show HEAD:.woodpecker.yaml
git ls-tree -r --name-only HEAD | grep -E '(^|/)\.woodpecker'
~~~

The server fetches configuration for the event's commit. A correct file on your local disk or on `main` cannot repair an event for a commit that does not contain it.

## 6. Separate “No Configuration” from “Filtered Configuration”

A syntactically valid workflow may be omitted by a global `when` condition. For example, this workflow is omitted for a push. If it is the only discovered workflow, no new pipeline remains visible:

~~~yaml
when:
  event: pull_request

steps:
  - name: test
    image: golang:1.26
    commands:
      - go test ./...
~~~

Step-level `when` filters behave differently: the workflow can be created and cloned, but individual steps are skipped. During diagnosis, temporarily add one small workflow with only an `event: push` condition. Once it starts, restore branch and path restrictions one at a time.

Also lint the configuration with a CLI version matching the server. A YAML parser failure, a removed 2.x key, or an invalid schema can stop the pipeline before any agent log appears. In Woodpecker 3.x, environment variables are maps, legacy top-level `pipeline:` is invalid, and secrets use `environment` plus `from_secret`.

## A Reliable Triage Checklist

Use this order for each controlled test push:

1. Confirm the repository is activated under the expected forge.
2. Confirm the forge created a delivery.
3. Confirm the delivery reached the final HTTPS hook URL successfully.
4. Correlate forge, proxy, and Woodpecker server logs by timestamp.
5. Repair the repository hook if it is absent or has an obsolete token.
6. Confirm `push` is selected on the forge webhook.
7. Remove CI-skip markers from the test commit.
8. Inspect the config path and exact pushed tree.
9. Reduce global conditions to `event: push`.
10. Only after a workflow is pending, inspect agents.

Record the pipeline number, commit SHA, delivery ID, and server version while testing. Those four identifiers make repeated attempts comparable.

## Conclusion

A pipeline that never appears is a server-side event-ingestion or configuration-discovery problem, not an agent execution problem. Prove each transition—forge delivery, proxy routing, server acceptance, repository event settings, and config lookup—using one known commit. Once Woodpecker creates a workflow, move downstream to scheduling and agents; until then, keep the investigation at the webhook and server layers.
