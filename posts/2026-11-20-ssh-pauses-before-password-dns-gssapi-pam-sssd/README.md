# SSH Pauses Before the Password Prompt: Isolate Reverse DNS, GSSAPI, PAM, and SSSD Delays

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: SSH, OpenSSH, DNS, PAM, SSSD, Troubleshooting

Description: Locate SSH login delays with timed client and server evidence, separating destination DNS, reverse DNS, GSSAPI, NSS identity lookup, and PAM processing.

A long wait before a password prompt does not identify the slow component. The client might be resolving a destination, negotiating authentication, or waiting while the server looks up an account. Start by locating the interval, then test its dependencies.

These examples target Ubuntu 24.04 LTS, its OpenSSH 9.6p1 package family, and SSSD 2.9.4 where installed. Use an existing authorized server session for inspections. Substitute the actual account, addresses, and connection route.

## Measure the gap before interpreting it

First inspect an existing transcript. For a fresh, authorized reproduction, this Bash example timestamps received debug lines without starting a remote shell:

```bash
# Requires GNU coreutils timeout and Python 3.
set -o pipefail
timeout --foreground --kill-after=2s 30s \
  ssh -vvv -N -T -S none -o ClearAllForwardings=yes \
  -o PermitLocalCommand=no -o ForkAfterAuthentication=no \
  -o ConnectTimeout=8 alice@server.example.net 2>&1 |
  python3 -u -c 'import datetime, sys, time
start = time.monotonic()
for line in sys.stdin:
    stamp = datetime.datetime.now(datetime.timezone.utc).isoformat(timespec="milliseconds")
    print(f"{stamp} +{time.monotonic()-start:.3f}s {line}", end="")'
```

`-S none` prevents connection reuse for this client; `-N` avoids a remote session command, including a configured `RemoteCommand`. `PermitLocalCommand=no` suppresses a configured post-authentication `LocalCommand`. `ClearAllForwardings=yes` clears port forwards and [disables tunnel forwarding in this version](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_6_P1/readconf.c). Other configured helpers, such as proxy commands, may still run. Retain host verification and the original identity/route. Stop at the relevant prompt without submitting a password. Prompts written directly to the terminal bypass this filter, so note their arrival separately. These are receipt timestamps, not timings inside sshd. See [ssh(1)](https://manpages.ubuntu.com/manpages/noble/man1/ssh.1.html).

The 30-second limit supervises the foreground `ssh` process; `ForkAfterAuthentication=no` prevents a configured background fork after authentication. Reaching the budget does not prove authentication failed, because `-N` can stay connected after success. GNU [timeout](https://manpages.ubuntu.com/manpages/noble/man1/timeout.1.html) sends TERM, then KILL after another two seconds if necessary. Its status is 124 on expiry or 137 after KILL; `pipefail` preserves that nonzero status if the reader succeeds. Its `--foreground` mode allows terminal access but does not time out child processes; proxy helpers need their own bounds. The Python reader is also outside the timeout, and a surviving helper can keep its input pipe open. `ConnectTimeout` covers connection establishment and initial handshake/key exchange, not the entire login. See [ssh_config(5)](https://manpages.ubuntu.com/manpages/noble/man5/ssh_config.5.html).

Use landmarks to choose the next investigation, not to declare a cause:

| Observed interval | Next evidence to collect |
|---|---|
| Before connecting to the destination address | Client configuration, name resolution, proxy startup |
| TCP connected, before user authentication | Banner/key exchange and matching server activity |
| During `gssapi-with-mic` | Client Kerberos/DNS dependencies and server authentication records |
| Waiting for initial authentication methods or a keyboard-interactive challenge | Server identity lookup, access checks, PAM conversation |
| After credentials or authentication success | Account/session processing; distinguish this from a pre-prompt delay |

A private-key passphrase prompt is local. A password-looking keyboard-interactive prompt comes from the server conversation; the ordinary SSH password prompt is generated by the client. [OpenSSH's authentication implementation](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_6_P1/sshconnect2.c) shows these distinct paths. The last printed debug line identifies the latest reported stage; some messages announce an operation before it starts. Read the surrounding messages to locate the gap.

Correlate the attempt's UTC window, username, source address/port, and sshd PID with server logs:

```bash
journalctl -u ssh.service --since '10 minutes ago' \
  --no-pager -o short-iso-precise
```

Use an explicit start/end window for a known attempt. Check clock alignment and the configured authentication log if the unit filter misses records. [journalctl](https://manpages.ubuntu.com/manpages/noble/man1/journalctl.1.html) documents these filters. Redact identities and internal infrastructure before sharing output.

## Separate destination DNS from server reverse DNS

On the client, time the system's lookup of the actual destination hostname:

```bash
time timeout --kill-after=2s 5s getent ahosts server.example.net
```

[getent](https://manpages.ubuntu.com/manpages/noble/man1/getent.1.html) uses NSS, including configured sources beyond DNS. With a jump host, destination resolution can happen there. Connecting to a numeric address also changes configuration matching, host-key lookup, and possibly the Kerberos service name, so it is not an otherwise identical comparison.

On the server, test reverse DNS for the **source address sshd sees**, which may belong to a NAT gateway or bastion:

```bash
time timeout --kill-after=2s 5s \
  dig -r -x 198.51.100.27 +timeout=2 +tries=1
```

If a PTR name is returned, check its forward A/AAAA records. Inspect response status and timing: a fast negative answer differs from a resolver timeout. [dig](https://manpages.ubuntu.com/manpages/noble/man1/dig.1.html) queries DNS, not the full NSS path; its per-query timeout is not an overall runtime guarantee, hence the outer bound. It requires the optional `bind9-dnsutils` package.

Have the administrator inspect effective sshd configuration using [sshd test mode](https://manpages.ubuntu.com/manpages/noble/man8/sshd.8.html):

```bash
/usr/sbin/sshd -T -f /etc/ssh/sshd_config \
  -C user=alice,addr=198.51.100.27,host=198.51.100.27,laddr=192.0.2.10,lport=22
```

Substitute the actual connection. With `UseDNS no`, use the numeric source address for `host`, as above; with `UseDNS yes`, supply the verified source hostname sshd uses, or the address if resolution fails. Test mode uses the supplied value for `Match Host`. Match the running service's configuration path and overrides. This requires appropriate read permissions and exits without performing a login. `UseDNS` defaults to `no` in this version. When enabled, it resolves the remote address and checks the resulting name maps back. Setting it to `no` restricts hostname-based `authorized_keys from` and `Match Host` rules; it does not disable DNS used by PAM, SSSD, or Kerberos. Do not change it without checking those access rules. See [UseDNS](https://manpages.ubuntu.com/manpages/noble/man5/sshd_config.5.html).

## Compare GSSAPI for one invocation

If the timed trace enters GSSAPI and policy permits another existing authentication method, repeat the same probe with this additional client option before the destination:

```text
-o GSSAPIAuthentication=no
```

A shorter gap narrows the investigation; it does not prove that GSSAPI itself is defective. Preserve SSO policy. Ubuntu's client configuration can enable GSSAPI despite the upstream default. `GSSAPIKeyExchange` is a separate option in this packaged version: disabling GSSAPI user authentication does not disable that exchange. Check the installed [client manual](https://manpages.ubuntu.com/manpages/noble/man5/ssh_config.5.html) before extending the comparison.

Inspect existing ticket validity with [klist](https://web.mit.edu/kerberos/krb5-1.21/doc/user/user_commands/klist.html). Check the selected service name, realm/KDC discovery, DNS canonicalization, and time synchronization with the identity team. MIT Kerberos documents separate [KDC and reverse-DNS settings](https://web.mit.edu/kerberos/krb5-1.21/doc/admin/conf_files/krb5_conf.html). A faster second attempt can reflect cached DNS or tickets; alternate a small number of permitted comparisons and corroborate the same interval in logs. Do not destroy credentials to manufacture a cold test.

## Split identity lookup from PAM processing

On the SSH server, time targeted lookups using the exact configured username form:

```bash
time timeout --kill-after=2s 5s getent passwd 'alice@example.net'
time timeout --kill-after=2s 5s id 'alice@example.net'
```

`getent passwd` tests identity retrieval; `id` also requests group information. Neither validates a password or the complete PAM stack. OpenSSH resolves the account [early in authentication](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_6_P1/auth2.c), so directory lookup can delay the first prompt. Inspect the `passwd`, `group`, and optional `initgroups` entries in `/etc/nsswitch.conf`.

Trace `/etc/pam.d/sshd` and its includes by phase: `auth` handles authentication/conversation, `account` checks access, and `session` prepares the session. With `UsePAM yes`, account and session processing also applies to key/GSSAPI authentication. Session delays belong later than the first authentication prompt. See [PAM stack semantics](https://manpages.ubuntu.com/manpages/noble/man5/pam.conf.5.html) and [UsePAM](https://manpages.ubuntu.com/manpages/noble/man5/sshd_config.5.html).

Where `sss`/`pam_sss` participates, correlate existing NSS responder, PAM responder, domain backend, and Kerberos helper logs with the measured request. [SSSD's troubleshooting guide](https://sssd.io/troubleshooting/basics.html) separates these paths. A quick cached identity lookup does not prove live authentication or access checks are healthy. Avoid deleting caches, restarting SSSD to mask the delay, or bypassing PAM/access policy.

Follow backend evidence to the actual dependency: DNS service discovery, directory connectivity or searches, KDC access, or failover to an unavailable server. [SSSD's backend guide](https://sssd.io/troubleshooting/backend.html) explains that sequence. Repair the demonstrated dependency, then repeat the original login with its normal authentication policy and verify that the same measured gap has disappeared.
