# How to Detect LLM Quality Regressions That Still Pass JSON Schema Checks

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: LLM, Evaluation, Testing, Data Quality

Description: Catch semantically wrong LLM answers that remain schema-valid by adding evidence checks, task invariants, and targeted regression mutations.

A schema-valid answer can still be wrong. An agent might return an integer refund amount, a valid status enum, and a correctly shaped citation list while choosing the wrong customer or inventing eligibility. Structure validates the representation. Your evaluation must also validate the meaning against the task and evidence.

OpenAI explicitly documents that Structured Outputs can contain mistakes. Treat successful parsing as one stage in the pipeline, then check the facts and decisions that your product depends on.

## Build separate format and quality signals

Define independent outcomes for transport completion, schema validity, deterministic business checks, evidence support, and task completion. Preserve refusal and incomplete-generation states instead of trying to parse every response as a successful business answer.

A useful result record might say that parsing passed, the order identity check passed, the refund amount check failed, and semantic grading was not needed. That is much easier to act on than one quality score whose meaning changes with the failure.

For a refund assistant, the schema can constrain the output shape:

```json
{
  "type": "object",
  "properties": {
    "order_id": {"type": "string"},
    "refund_cents": {"type": "integer"},
    "decision": {"type": "string", "enum": ["approve", "deny", "review"]}
  },
  "required": ["order_id", "refund_cents", "decision"],
  "additionalProperties": false
}
```

This schema is an example output contract. It does not know which order the user owns, whether a refund was already issued, or what the return policy permits. Validate it with your chosen JSON Schema library, then apply business checks against an authoritative fixture or readback.

## Check relationships that schemas do not establish

The following standalone Python example assumes schema validation already succeeded. It demonstrates a deliberately narrow policy: the approved refund must equal the remaining refundable amount supplied by a trusted backend.

```python
def check_business_rules(answer, evidence):
    failures = []
    if answer["order_id"] != evidence["authorized_order_id"]:
        failures.append("wrong_order")
    if answer["refund_cents"] < 0:
        failures.append("negative_refund")
    if answer["decision"] == "approve":
        if not evidence["eligible"]:
            failures.append("ineligible_approval")
        if answer["refund_cents"] != evidence["remaining_refundable_cents"]:
            failures.append("wrong_refund_amount")
    elif answer["refund_cents"] != 0:
        failures.append("nonapproval_has_refund")
    return failures

evidence = {"authorized_order_id": "order-18", "eligible": True,
            "remaining_refundable_cents": 2500}
answer = {"order_id": "order-18", "refund_cents": 5000, "decision": "approve"}
assert check_business_rules(answer, evidence) == ["wrong_refund_amount"]
```

Adapt the policy to your system. Some businesses permit partial refunds or need additional authorization; the fixture's rule is not universal. Keep the authoritative data independent of the model output. Checking a generated amount against a second copy generated by the same model does not establish correctness.

## Create valid-but-wrong regression cases

Start with an answer humans consider correct, then mutate one semantic property while preserving the schema. Replace the order ID, increase the amount, change an eligible decision to a denial, or cite a document that exists but does not support the claim.

Use these mutations as negative controls. The format validator should accept them and the appropriate semantic check should reject them. If the whole pipeline accepts every mutated answer, the suite measures formatting rather than correctness.

Also include positive controls with harmless variations: equivalent wording, reordered citations, or an allowed alternative escalation route. These reveal overly strict checks that reject valid behavior. Keep mutation fixtures separate from your final held-out production sample; a system tuned only to known mutations may miss new error patterns.

## Use model judges for the remaining ambiguity

Some requirements need contextual interpretation, such as whether a summary preserves a qualification or whether a response answers the requested question. Give the evaluator the exact source snapshot and a narrow criterion. Require a verdict plus a concise evidence reference, then validate that the reference resolves.

Score factual support, completeness, and relevance separately when they can fail independently. A long answer may be complete but unsupported. A short answer may be fully supported but omit the one requested fact. An overall label can hide both distinctions.

Calibrate the judge against human labels, retain abstentions and invalid outputs, and examine disagreements. A structured judge response is still a model output; its own schema compliance does not establish that its verdict is correct.

## Compare releases with stable evidence

Run baseline and candidate against the same case revisions and grader versions. Keep transport errors, schema failures, semantic failures, and missing grades visible in the denominator policy. Show the proportion of schema-valid answers that fail semantic checks, as well as end-to-end successful requests.

Review critical slices such as identity changes, boundary amounts, conflicting documents, and missing evidence. Set acceptance requirements before running the candidate. A higher average semantic score should not compensate for an unauthorized order action.

When a regression appears, inspect the earliest incorrect dependency: retrieval, tool arguments, tool response interpretation, or final generation. Fixing the schema will not repair a wrong source. The practical goal is an evaluation pipeline that can say both that an answer is well formed and that the answer satisfies the task.
