# Prepare PostgreSQL Sequences for Logical Replication Failover

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: PostgreSQL, Logical Replication, Sequences, Failover, Identity Columns, Runbook

Description: Inventory, fence, and advance PostgreSQL sequences before promoting a logical subscriber so new writes cannot reuse replicated identifiers.

---

PostgreSQL logical replication sends the value stored in a `serial` or identity column, but it does not replicate the state of the sequence that generated that value. A read-only subscriber can therefore contain order ID 94000 while its local `orders_id_seq` is still near 1. Reads are correct. The first local insert after failover may not be.

Sequence preparation belongs in every logical switchover and failover runbook. The safe process is to fence the old writer, let table changes catch up, inventory every sequence, set the new writer's next values from authoritative evidence, and only then enable application writes.

## Understand the Two Independent States

Consider an identity column:

```sql
CREATE TABLE public.orders (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

There are two different pieces of state:

- `orders.id` values are ordinary table data and are logically replicated.
- The backing sequence's current value and `is_called` state belong to a sequence object and are not logically replicated.

Logical apply inserts the publisher's row value. It does not need to call the subscriber's `nextval()` to reproduce that ID. That is why replication can be healthy while the local sequence falls far behind.

Sequence gaps do not prove a fault. PostgreSQL does not reclaim a `nextval()` result when a transaction rolls back, and cached values or `INSERT ... ON CONFLICT` can also create gaps. The risk is reuse of a value, not non-contiguous numbering.

## Inventory Owned Sequences and Hidden Consumers

For one column, ask PostgreSQL for its owned sequence:

```sql
SELECT pg_get_serial_sequence('public.orders', 'id') AS sequence_name;
```

Despite its historical name, `pg_get_serial_sequence()` also identifies a sequence associated through an identity column. Inventory owned sequences across application schemas:

```sql
SELECT n.nspname AS table_schema,
       c.relname AS table_name,
       a.attname AS column_name,
       a.attidentity,
       pg_get_serial_sequence(
           format('%I.%I', n.nspname, c.relname),
           a.attname
       ) AS sequence_name
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
JOIN pg_attribute AS a ON a.attrelid = c.oid
WHERE c.relkind IN ('r', 'p')
  AND a.attnum > 0
  AND NOT a.attisdropped
  AND pg_get_serial_sequence(
          format('%I.%I', n.nspname, c.relname),
          a.attname
      ) IS NOT NULL
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relname, a.attnum;
```

This catches sequences owned by table columns. It does not find every free-standing sequence called explicitly from a function, trigger, expression, or application. Review all sequence objects as well:

```sql
SELECT schemaname,
       sequencename,
       data_type,
       start_value,
       min_value,
       max_value,
       increment_by,
       cycle,
       cache_size,
       last_value
FROM pg_sequences
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY schemaname, sequencename;
```

`pg_sequences.last_value` can be `NULL` when the caller lacks privileges or a sequence has not been read yet. For a known sequence, inspect its state directly on both publisher and subscriber:

```sql
SELECT last_value, is_called
FROM public.orders_id_seq;
```

Record sequence definitions too. An ascending increment-by-one, non-cycling sequence needs a different calculation from a descending, stepped, cycling, or range-allocated sequence.

## Do Not Repair a Live Target by Guessing from `max(id)`

This common command is unsafe while writers are active:

```sql
SELECT setval(
    'public.orders_id_seq',
    (SELECT max(id) FROM public.orders)
);
```

Between the `max(id)` scan and `setval`, another session can allocate or insert a value. A session may also hold cached values. A free-standing sequence might be shared by multiple tables, so one table's maximum is incomplete. Finally, `setval` changes are immediately visible and are not undone if the surrounding transaction rolls back.

The computation must happen after write fencing, not as an online housekeeping task.

## Planned Switchover Runbook

### 1. Fence the Old Writer

Remove the old primary from application routing and stop background jobs, direct SQL users, queues, and maintenance tools that can call `nextval()`. A read-only application flag is insufficient if another credential can still write.

Capture a final publisher WAL position after the last committed application write:

```sql
SELECT pg_current_wal_insert_lsn() AS final_publisher_lsn;
```

Logical replication progress uses publisher LSNs, but compare them through subscription state and your tested cutover procedure. Do not compare unrelated local WAL positions from two independent clusters.

### 2. Wait for the Subscription to Apply the Fence

On the subscriber:

```sql
SELECT subname,
       worker_type,
       received_lsn,
       latest_end_lsn,
       latest_end_time,
       last_msg_receipt_time
FROM pg_stat_subscription
WHERE subname = 'orders_sub';
```

Also verify the business rows written immediately before the fence. An LSN field alone does not prove that every expected table is in the publication, that apply did not hit a conflict, or that the schema is correct.

Once caught up, disable the subscription if the cutover design requires the former subscriber to become an independent writer:

```sql
ALTER SUBSCRIPTION orders_sub DISABLE;
```

Keep the old publisher slot under observation. Disabling a subscription does not automatically drop its remote slot, so WAL can accumulate while the topology is paused.

### 3. Calculate a Safe Next Value

For a standard ascending increment-by-one sequence, collect these values after the fence:

On the publisher:

```sql
SELECT last_value, is_called
FROM public.orders_id_seq;
```

On the subscriber:

```sql
SELECT max(id) AS subscriber_max_id
FROM public.orders;

SELECT last_value, is_called
FROM public.orders_id_seq;
```

The next value should be greater than every ID that must never be reused. A conservative standard-sequence bound considers at least the publisher's final sequence state, the subscriber's table maximum, and any IDs reserved outside the database.

Do not blindly add one to a descending sequence or one whose `increment_by` is not 1. Do not infer safety from table maximum when sequence numbers are used before an insert and exposed to external systems. Define the allocation policy for those values explicitly.

### 4. Restart the Sequence Under the Write Fence

Suppose the audited next safe value is 94218. On the subscriber that will become the writer:

```sql
BEGIN;

LOCK TABLE public.orders IN ACCESS EXCLUSIVE MODE;

ALTER SEQUENCE public.orders_id_seq
RESTART WITH 94218;

COMMIT;
```

`ALTER SEQUENCE ... RESTART WITH` makes the next `nextval()` return the specified value. PostgreSQL documents this operation as transactional and as blocking concurrent transactions from obtaining values from that sequence. The table lock also prevents table writes through ordinary paths during the adjustment.

The write fence is still essential. A sequence can be called directly without inserting into the table, and a sequence shared by multiple tables is not protected by locking only one table.

An equivalent `setval` pattern for a non-empty, standard sequence is:

```sql
SELECT setval('public.orders_id_seq', 94217, true);
```

With `is_called = true`, the following `nextval()` advances before returning. With `is_called = false`, it returns exactly the value passed to `setval`. Prefer one documented convention in the runbook and test empty tables so an off-by-one error does not become the first production collision.

### 5. Verify Before Opening Writes

Do not consume a production ID merely to inspect it. `currval()` is session-local and errors in a session that has not called `nextval()`. Instead, verify recorded state and then run a controlled insert that can remain as a canary or be rolled back with full awareness that its sequence value will still be consumed:

```sql
BEGIN;

INSERT INTO public.orders (customer_id)
VALUES (900000001)
RETURNING id;

ROLLBACK;
```

Confirm that the returned ID is above the audited boundary. A rollback does not put the value back, which is expected.

Repeat the process for every owned and free-standing sequence, then switch application routing. Monitor unique violations and keep the old writer fenced.

## Emergency Failover Has a Different Limit

If the publisher is unavailable, its final sequence state may be unknowable. Start from the subscriber's maximum replicated values, known external allocations, reserved key ranges, and an explicit safety margin appropriate to the key space:

```sql
SELECT max(id) AS max_replayed_id
FROM public.orders;
```

This prevents collision with rows present on the promoted subscriber, but it cannot reconstruct sequence values allocated on the failed publisher and never replicated as rows. If those values escaped to clients, reusing them may violate an external uniqueness contract even when the database accepts them.

A larger one-time jump can reduce that risk for a roomy `bigint` key space, but it is a business decision, not proof of the missing state. Record the gap and reconcile the failed node before any failback.

## Dumps Are Snapshots, Not Continuous Sequence Replication

PostgreSQL's logical replication restrictions suggest copying sequence state or determining a sufficiently high value during failover preparation. `pg_dump` can include sequence state in a logical dump, but a dump taken while the publisher continues allocating values becomes stale immediately.

Use dump-derived sequence state only under a write fence or as one input to a later calculation. Do not schedule periodic `setval` calls on a writable subscriber and call that failover readiness; racing sequence resets can move operational state in surprising ways and still miss the final cutover boundary.

## Design for Repeatable Role Changes

Every direction change needs sequence coordination. Before failing back, fence the current writer and advance sequences on the next writer from the now-authoritative state. Logical replication does not automatically turn a one-way subscription into conflict-safe bidirectional replication.

For frequent switching or intentional multiple writers, consider a key strategy that avoids one shared numeric allocator:

- non-overlapping numeric ranges per writer;
- large-step sequences with distinct offsets;
- UUIDs generated independently;
- an external allocation service with a defined availability model.

These strategies solve key allocation, not row conflict resolution. Two writers can still update the same logical entity incompatibly.

## Automate the Inventory, Keep the Decision Explicit

A useful preflight report contains:

- table and column owning each sequence;
- sequence definition, current value, and `is_called` on both nodes;
- publisher and subscriber table minima and maxima;
- whether any function, trigger, or second table calls the sequence;
- proposed next value and the evidence used to derive it;
- the operator who confirmed the old writer was fenced.

Generate the report before an incident and rehearse the commands. Do not build automation that issues dynamic `setval` or `ALTER SEQUENCE` commands against every discovered object without review. Descending, cycling, shared, and externally exposed sequences require individual policy.

## Conclusion

Logical replication can deliver every table row correctly while leaving every subscriber sequence unprepared for writes. Make sequence inventory part of topology design, fence the old writer, wait for table apply, calculate safe next values from authoritative state, and restart each sequence before routing writes. The ordering matters more than the particular command: no sequence adjustment is safe while two allocators can still run.
