## Issues Found
1. **Netplan `via: 0.0.0.0` for link-scope routes (two occurrences)** — The post used `via: 0.0.0.0` to express directly-connected subnet routes within the custom routing tables. `0.0.0.0` is not a valid gateway address; the idiomatic Netplan way to express a link-scope route is to omit `via` and set `scope: link`. Changed both `via: 0.0.0.0` entries (for `192.168.1.0/24` in the isp1 table and `10.0.0.0/24` in the isp2 table) to `scope: link`.

2. **`ip route get` argument order** — In the Step 4 verification block, the post used `ip route get from 192.168.1.100 8.8.8.8` (source before destination). While iproute2's flexible parser accepts both orderings, the canonical synopsis is `ip route get DESTINATION [from SOURCE]`, and the Debugging section later in the same post uses that form. Reordered the two `ip route get` lines to match the canonical form and to be consistent with the rest of the post.

## Review Notes
- The `/etc/network/if-up.d/policy-routing` startup-script approach only works on systems still using the legacy `ifupdown` package. Modern Ubuntu (18.04+) defaults to Netplan + systemd-networkd or NetworkManager, neither of which executes `if-up.d` hooks. The post does present Netplan as the recommended option and offers a systemd service as a renderer-agnostic alternative, so this is acceptable, but readers on default Ubuntu should prefer the Netplan or systemd-service paths.
- The systemd service example references `/usr/local/bin/setup-policy-routing.sh` but does not include the contents of that script. Readers are expected to reuse the body of the if-up.d example. This is a minor incompleteness, not a technical error.
- The fwmark example in "Interface-Based Routing" demonstrates the mechanism correctly, but for the stated use case (returning reply traffic out the same interface a NAT'd connection arrived on) it is incomplete on its own — production setups typically also need `CONNMARK --save-mark` in PREROUTING and `CONNMARK --restore-mark` in OUTPUT to mark reply packets generated by local services. The post frames the snippet as illustrative rather than a complete recipe, so this was left as written.
- Routing table IDs 1–252 reserved for custom use is correct for the traditional 8-bit table-id range; modern kernels support a 32-bit range via `rt_tables.d`, but the 1–252 range remains the safe, portable choice.
