## Issues Found
- The original External Secrets Operator configuration used the HashiCorp Vault provider as if it could read Vault database dynamic secrets directly. ESO's Vault provider documentation says it supports the KV secrets engine and directs other engines to the Vault generator. I replaced the `ClusterSecretStore`/`dataFrom.extract` examples with a `VaultDynamicSecret` generator and `dataFrom.sourceRef.generatorRef`.
- The ExternalSecret and ClusterSecretStore snippets used `external-secrets.io/v1beta1`. Current ESO examples use `external-secrets.io/v1`, so I updated the ExternalSecret manifests to `external-secrets.io/v1`.
- The Vault Kubernetes auth role and policy only covered PostgreSQL read-only/read-write paths while the post also shows MySQL and MongoDB roles. I expanded the policy paths and changed the auth role example to bind a `vault-auth` service account in the production namespace, matching the generator examples.
- The Deployment example had two `env` keys under the same container. In YAML/Kubernetes manifests this would cause one list to override the other or be rejected by stricter tooling, so the database URL and connection pool variables are now in a single `env` list.
- The Argo CD Application included `ignoreDifferences` for the generated Kubernetes Secret. In this pattern the Secret is generated by ESO rather than stored in Git as an Argo-managed manifest, so that diff customization is not required for the shown Application. I removed the unnecessary `ignoreDifferences` and `RespectIgnoreDifferences=true` entries.
- The Git manifest example was incomplete after switching to the generator pattern. I added the `vault-auth` ServiceAccount and `VaultDynamicSecret` manifest to the application manifest block.

## Review Notes
The Vault database engine commands for PostgreSQL, MySQL, and MongoDB match the current HashiCorp examples in structure and supported fields. The Reloader annotation and ESO metrics alert use documented names. In a production deployment, teams should still validate namespace and service account choices against their ESO RBAC and multi-tenancy model.
