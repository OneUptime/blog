# How to Add Idempotency to an Existing POST Endpoint Without Breaking Older Clients

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Idempotency, REST API, Backward Compatibility, API Design, PostgreSQL

Description: Roll out optional idempotency keys to an existing POST endpoint while preserving legacy behavior, defining replay semantics, and keeping protection intact through rollback.

---

An existing `POST /v1/orders` endpoint creates an order on every valid request. A mobile client times out, retries, and creates a second order. You want new clients to reuse an idempotency key, but requiring that header immediately would reject older applications.

Introduce an opt-in contract first: requests carrying a valid key receive documented idempotency behavior; requests without a key retain the existing behavior. Then migrate clients deliberately and use a new version or negotiated contract if the key eventually becomes mandatory.

## Preserve the meaning of requests without a key

Two identical legacy request bodies may represent two intentional orders. Deduplicating all keyless requests by payload or by a short time window changes the endpoint's semantics.

A random key generated by the server for each arriving request also cannot connect two attempts whose responses were lost. The client needs to create and persist one operation identity before its first attempt, then reuse that identity for retries. AWS describes the value of a caller-supplied request identifier for distinguishing repeated intent from a new request. [AWS safe retries with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

Publish a behavior matrix before implementing middleware:

| Request | Example contract |
| --- | --- |
| Header absent | Existing order-creation behavior |
| New valid key | Execute once and retain the outcome |
| Same key and protected inputs | Replay the retained outcome |
| Same key and changed protected inputs | Return a documented conflict |
| Same key while execution is unresolved | Wait within a bound or return an in-progress response |
| Empty, duplicated, or malformed header | Return a validation error |

Status choices such as `409` or `422` are part of your API's contract. Do not assume that sending a header alone changes POST semantics for arbitrary servers. [HTTP idempotent method semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods)

## Distinguish absence from invalid input

The following TypeScript function illustrates only the rollout gate, using Node-style raw header pairs. It deliberately accepts 1–128 ASCII letters, digits, underscores, or hyphens for this API; it is not a universal header grammar.

```typescript
type KeyPolicy = "optional" | "required";
type KeyDecision =
  | { kind: "legacy" }
  | { kind: "keyed"; key: string }
  | { kind: "invalid" };

export function decideKey(
  rawHeaders: string[],
  policy: KeyPolicy,
): KeyDecision {
  if (rawHeaders.length % 2 !== 0) return { kind: "invalid" };
  const values: string[] = [];
  for (let i = 0; i < rawHeaders.length; i += 2) {
    if (rawHeaders[i].toLowerCase() === "idempotency-key") {
      values.push(rawHeaders[i + 1]);
    }
  }
  if (values.length === 0) {
    return policy === "optional" ? { kind: "legacy" } : { kind: "invalid" };
  }
  if (values.length !== 1 || !/^[A-Za-z0-9_-]{1,128}$/.test(values[0])) {
    return { kind: "invalid" };
  }
  return { kind: "keyed", key: values[0] };
}
```

The restricted character set also rejects comma-joined values if an upstream intermediary merged duplicate headers. Verify actual ingress behavior instead of relying solely on the application parser. Node exposes received header pairs through `rawHeaders`. [Node HTTP IncomingMessage](https://nodejs.org/api/http.html#messagerawheaders)

An invalid key must not silently fall back to legacy execution. A new client would believe the request was protected while the server created an unprotected order.

## Put the guarantee around durable work

Authenticate and authorize every attempt, including replays. Derive tenant identity from trusted authentication state. Then scope the stored key by tenant and logical operation, and compare a fingerprint of validated business inputs.

For effects contained in one PostgreSQL database, claim the key, create the order, and store the replayable outcome in one transaction. A composite unique constraint arbitrates concurrent claims. An application-level lookup followed by an unprotected insertion does not. [PostgreSQL INSERT conflict handling](https://www.postgresql.org/docs/18/sql-insert.html)

Define the serialization format and fingerprint version. Differences in JSON member order should not create accidental mismatches if the contract compares semantic inputs. Omitted fields, defaults, currency, and explicit null values need deliberate treatment. Store the normalized inputs or sufficient fingerprint metadata to preserve that behavior across deployments.

If execution calls another service, use a durable outbound command and downstream idempotency or reconciliation. A local record saying `started` cannot prove whether a remote operation completed after a timeout.

## Specify the replay representation

Decide which status, body, and selected headers are retained. Preserve the original resource identifier and avoid rendering a replay from mutable current order state if your contract promises the original response.

Do not replay connection-specific headers, credentials, or session cookies indiscriminately. Re-evaluate authorization before disclosing a saved response, and apply current response security controls around the stored application result.

Document when execution starts and which failures become retained outcomes. Stripe's particular policy retains results after execution begins, while some validation and concurrent-request failures remain outside that cache. It is a useful example, not a requirement that every API copy those exact rules. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)

For browser clients, update the allowed request headers in CORS configuration. If clients read a custom replay-indicator response header, expose it as well. An HTTP test alone will not detect a browser preflight failure. [MDN CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

## Roll out the server before clients

Deploy storage and the optional-key path first. Confirm every replica serving the endpoint understands the contract before releasing clients that depend on it. A mixed fleet in which some nodes ignore keys creates intermittent duplicate effects.

Then update SDKs to persist one key with a logical operation, survive application restarts when retries must survive them, and reuse the same protected inputs. Generate a fresh key for a genuinely new operation. Track keyed adoption, invalid keys, conflicts, replays, and keyless traffic by a bounded client-version grouping.

A rollback must preserve protection for clients already using it. Route keyed traffic to a compatible implementation or reject it temporarily if protection cannot be maintained. Silently reverting to execution that ignores the key breaks the published guarantee. Keep existing idempotency records and their schema readable throughout the rollback window.

## Test compatibility and recovery together

Verify that two identical keyless requests still follow the old documented behavior. Verify that two matching keyed requests create one order, that concurrent attempts are arbitrated, and that changed inputs cannot create another order under the same key.

Drop the first response after commit, retry against another replica, and inspect the order and outbound-intent counts. Test the optional and required policies, empty and duplicate headers, cross-tenant keys, authorization changes, storage failures, and rollback to the oldest supported server version.

Finally, define retention before clients ship. After the documented recognition window, an old key may be treated as new or explicitly rejected. Clients must reconcile old uncertain operations instead of assuming unlimited protection. The migration is complete only when the client behavior, durable storage, ingress, and rollback procedure uphold the same contract.
