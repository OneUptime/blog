# How Portainer Kompose Deployments Worked (Removed in 2.17)

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Portainer, Kompose, Docker Compose, Kubernetes, Deprecated, History

Description: A historical overview of Portainer's Kompose-based Docker Compose to Kubernetes conversion feature, removed in Portainer 2.17, and what replaced it.

---

Portainer 2.16 and earlier included an integration with Kompose - a tool that converts Docker Compose files into Kubernetes manifests. This allowed operators to paste a Docker Compose definition and have Portainer deploy it to a Kubernetes cluster after automatic conversion. The feature was removed in 2.17. After that, Portainer's supported Kubernetes workflows centered on native manifests, Helm charts, and Git-based deployments.

## What Was Kompose?

Kompose is an open-source CNCF project that translates Docker Compose service definitions into Kubernetes Deployments, Services, and other objects. It handles the conceptual mapping between Compose and Kubernetes constructs.

## How Portainer Used Kompose

When deploying a stack to a Kubernetes environment in Portainer 2.16 and earlier, operators could:

1. Select the Kubernetes environment
2. Enable the "Kompose" toggle in the stack deployment UI
3. Paste their existing Docker Compose YAML

Portainer would run Kompose internally and deploy the resulting Kubernetes manifests.

A Docker Compose file like this:

```yaml
# docker-compose.yml

services:
  webapp:
    image: nginx:1.25
    ports:
      - "80:80"
    environment:
      - APP_ENV=production
  database:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - db-data:/var/lib/postgresql/data
volumes:
  db-data:
```

Would be converted by Kompose to Kubernetes objects similar to:

```yaml
# Generated by Kompose - Deployment for webapp
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    io.kompose.service: webapp
  name: webapp
spec:
  replicas: 1
  selector:
    matchLabels:
      io.kompose.service: webapp
  template:
    metadata:
      labels:
        io.kompose.service: webapp
    spec:
      containers:
        - env:
            - name: APP_ENV
              value: production
          image: nginx:1.25
          name: webapp
          ports:
            - containerPort: 80
              protocol: TCP
      restartPolicy: Always
---
# Service for webapp
apiVersion: v1
kind: Service
metadata:
  labels:
    io.kompose.service: webapp
  name: webapp
spec:
  ports:
    - name: "80"
      port: 80
      targetPort: 80
  selector:
    io.kompose.service: webapp
```

## Why Kompose Conversions Were Unreliable

The Kompose conversion had significant limitations that made it impractical for production use:

1. **Named volumes** - Kompose can translate them to PersistentVolumeClaims, but the semantics and storage lifecycle differ
2. **Networks** - Docker networks don't map directly to Kubernetes networking
3. **Healthchecks** - Kompose can convert Compose healthchecks into liveness probes, but readiness behavior often still needs manual work
4. **Dependencies** - `depends_on` has no Kubernetes equivalent; init containers or application-level retry logic is needed
5. **Secrets/configs** - Compose secrets map loosely to Kubernetes Secrets

## Why It Was Removed

- **Security risk** - Portainer removed the built-in Kompose path because Kompose had unresolved CVEs and a slow maintenance cadence
- **Conversion quality** - The generated manifests often required manual editing before they were production-ready
- **Wrong abstraction** - Kubernetes resources need to be designed for Kubernetes, not converted from Compose
- **Better workflow** - The recommended path is to write native Kubernetes manifests or use Helm charts from the start

## What Replaced It

After Kompose was removed, Portainer's supported Kubernetes workflows centered on native manifests, Helm charts, and Git-based deployments:

- **Manifest deployments** - Deploy raw Kubernetes manifests directly in Portainer
- **Helm chart browser** - Browse, install, and manage Helm charts from registered chart repositories
- **Helm values editor** - Customize Helm values in the Portainer UI
- **Git-based deployments and GitOps updates** - Deploy manifests from Git repositories and optionally keep them synced

For teams migrating Compose workloads to Kubernetes, the recommended approach is:

```bash
# Use Kompose externally as a starting point, then refine
kompose convert -f docker-compose.yml -o ./k8s-manifests/

# Review and manually adjust the generated manifests
# Add proper resource limits, readiness probes, and security contexts
# Then deploy via Portainer's manifest deployment feature
```

## Summary

The Kompose integration was a well-intentioned feature that tried to lower the barrier to Kubernetes adoption for Docker Compose users. Its removal acknowledged both the security risk of embedding an aging Kompose dependency and the fact that automated conversion produces second-rate Kubernetes manifests, while native Kubernetes workflows (Helm, manifests, and Git-based deployments) serve operators better in practice.
