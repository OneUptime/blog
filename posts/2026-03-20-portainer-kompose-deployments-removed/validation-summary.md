## Issues Found
- The Compose example used a top-level `version: "3"` key. Docker's current Compose documentation marks the top-level `version` element as obsolete, so it was removed.
- The "generated by Kompose" Deployment example was not valid Kubernetes because `.spec.selector.matchLabels` did not match `.spec.template.metadata.labels`, and it also used labels that did not reflect actual Kompose output. The example was corrected to a valid, representative Kompose-style Deployment and Service.
- The post stated that Compose healthchecks are not directly converted to Kubernetes liveness/readiness probes. Current Kompose behavior and documentation show healthcheck support, and an actual conversion produces a `livenessProbe`, so the wording was corrected to reflect that liveness conversion is possible while readiness often still needs manual work.
- The post implied Portainer 2.17 introduced manifest and Helm support as the replacement for Kompose. Portainer already supported native Kubernetes manifests before Kompose removal, so the wording was corrected to say that supported workflows after removal centered on manifests, Helm charts, and Git-based deployments.
- The named-volume limitation was slightly overstated. Kompose does convert Compose volumes to PersistentVolumeClaims, but semantics differ, so that explanation was tightened.
- The original removal rationale omitted Portainer's documented security reason for removing the embedded Kompose workflow. The post was corrected to note the unresolved CVE and maintenance-cadence concerns cited by Portainer.

## Review Notes
- Portainer's own 2.16.2 UI explicitly stated that it used Kompose to convert Compose manifests to Kubernetes-compliant manifests, and the 2.17.0 UI explicitly stated that Docker Compose format manifests for Kubernetes were no longer supported due to Kompose-related security risk and CVEs.
- Kompose's `convert` command and `-o` flag were verified against the official CLI help from the current release binary, and the example command in the post is valid.
- The article is inherently historical. The corrected post is accurate as a retrospective, but readers should still understand that Portainer's current Kubernetes UX and feature naming may differ from the 2.16/2.17-era UI described here.
