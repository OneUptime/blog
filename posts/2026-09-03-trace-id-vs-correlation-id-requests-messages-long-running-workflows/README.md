# Trace ID vs Correlation ID for Requests, Messages, and Workflows

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Correlation ID, Distributed Tracing, OpenTelemetry, W3C Trace Context

Description: Choose trace, correlation, message, and causation identifiers by lifecycle so synchronous requests and long-running workflows remain searchable and correctly modeled.

---

A trace ID and a correlation ID can have the same superficial purpose-finding related records-but they represent different relationships. Treating them as interchangeable makes traces too large, makes retries ambiguous, and couples business data to a telemetry implementation.

Use the trace ID for one distributed execution graph. Use a correlation ID for a domain-level conversation that may include several executions. Add message and causation IDs when asynchronous delivery needs precise lineage.

## Know the Identifier Roles

### Trace ID

In OpenTelemetry, a `SpanContext` contains a 16-byte trace ID and an 8-byte span ID. W3C `traceparent` serializes those identifiers across process boundaries. All spans in one trace share the trace ID; parent IDs and span links express relationships among operations.

A trace ID is best for an HTTP request and the work causally triggered within a practical trace duration. It is generated by tracing infrastructure, follows strict validity rules, and may be affected by trust-boundary and sampling policy. Application code should not derive it from an order number or accept it as proof of identity.

### Correlation or workflow ID

A correlation ID is an application contract. It might represent a checkout, claim, import, saga, or support case. Its syntax, ownership, retention, and rollover rules must be defined by the domain. It can connect multiple traces across hours or days and survive reprocessing after telemetry has expired.

It should be opaque and non-sensitive. A random ID avoids exposing customer or sequence information. Store the association in the system of record when the workflow must remain discoverable longer than observability retention.

### Message ID and causation ID

A message ID identifies one logical message or envelope and supports idempotency and delivery investigation. A causation ID identifies the request, operation, or prior message that caused it. These fields distinguish “part of the same case” from “directly caused by this event.”

Broker offsets and delivery tags are useful transport coordinates, not universal message IDs. A Kafka tuple of topic, partition, and offset identifies a stored record in one cluster. A RabbitMQ delivery tag is scoped to a channel. Neither should silently become the cross-system workflow identity.

## Choose by Lifetime and Relationship

Use this decision table:

| Question | Identifier |
| --- | --- |
| Which spans were part of this execution? | Trace ID |
| Which operation emitted this exact log? | Trace ID plus span ID |
| Which customer workflow spans several executions? | Correlation/workflow ID |
| Which envelope is being retried or deduplicated? | Message ID |
| Which earlier action directly caused this message? | Causation ID |
| Where is a Kafka record stored? | Cluster, topic, partition, offset |

One event can legitimately carry all of them. Redundancy is useful when every field has a documented meaning.

## Model Common Flows

For a synchronous chain-browser to API to inventory to database-continue one W3C trace through instrumented HTTP or RPC boundaries. If the browser supplies an application request ID, retain it only as a validated correlation attribute; do not replace the tracing library's trace ID.

For a short asynchronous continuation, the producer can inject trace context into the message, and the consumer can continue that trace. Give the message its own ID because it can be redelivered even though the trace relationship remains the same.

For a loan application that waits days for documents, use one stable workflow ID and multiple traces:

~~~text
workflow_id = wf_7H2K...

Trace A: submit application
  message_id = msg_101

Trace B: verify documents
  caused_by = msg_101
  message_id = msg_102

Trace C: issue decision
  caused_by = msg_102
~~~

Link each new trace to an available prior span context when useful, but do not depend on that link as the durable workflow database. Trace retention, sampling, and backend limits can remove it.

For fan-out, give every published message a distinct message ID. Retain the same workflow ID. If several messages are created in one batch, OpenTelemetry messaging conventions allow a creation context for each and links from the send or processing spans. Reusing one message ID for the whole batch obscures retries of individual items.

## Put Identifiers in the Right Places

Propagate tracing context with the configured OpenTelemetry propagator. It owns `traceparent`, `tracestate`, and, if enabled, `baggage`. Carry application identifiers in explicit protocol fields or message headers such as `correlation-id`, `message-id`, and `causation-id`.

In telemetry:

- put trace and span IDs in their native OTLP fields;
- add a low-cardinality service and environment resource identity to all signals;
- add workflow and message IDs to structured logs and relevant spans;
- avoid workflow IDs as ordinary metric labels, because unbounded values create one time series per workflow;
- use exemplars to associate selected metric measurements with trace and span IDs.

Baggage can make a workflow ID available downstream, but it is not automatically copied to spans, logs, or metrics. Instrumentation must add selected baggage values explicitly. Because baggage crosses service boundaries, allowlist it and remove it before calls to unrelated external services.

## Establish Generation and Trust Rules

Document who generates each ID and what happens when it is absent or invalid:

1. The tracing SDK generates a new span ID for every span and a new trace ID for each root span. A child span inherits the trace ID from its valid parent context, including an accepted remote context.
2. The workflow owner generates the correlation ID once and persists it.
3. The producing application generates a message ID before publish.
4. A retry of the same logical message preserves its message ID and increments attempt metadata.
5. A republished replacement envelope gets a new message ID and points to the old ID through causation or original-message metadata.

Never authorize access based on possession of any correlation value. Validate character set and maximum length, prevent log injection, and avoid sequential identifiers that disclose volume. At an external boundary, it can be appropriate to retain a caller's request ID for support while creating an internal workflow ID and a new trace.

## Test the Semantics, Not Just Presence

Create contract tests for HTTP, Kafka, RabbitMQ, scheduled jobs, retries, and dead-letter recovery. Assertions should answer:

- Does a synchronous child keep its trace ID and receive the correct parent span ID?
- Do separate workflows ever share a correlation ID accidentally?
- Does every new message get a unique message ID?
- Can a retry be distinguished from a new domain event?
- Can an operator find all traces for one workflow without making the metric store high-cardinality?
- Does a new trace preserve causal linkage without pretending a days-long parent span remained active?

These tests protect meaning when frameworks or instrumentation libraries change.

## Conclusion

Choose identifiers according to the relationship they encode. Trace IDs describe one telemetry execution graph, correlation IDs group a durable business conversation, message IDs identify asynchronous units, and causation IDs preserve direct lineage. Keeping these roles separate yields traces that remain understandable, logs that remain searchable, metrics that remain affordable, and workflows that remain investigable after individual traces expire.
