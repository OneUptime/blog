## Issues Found
- The original post framed manual WorkloadEndpoint creation as a normal Kubernetes operator task. Calico documentation says WorkloadEndpoint lifecycle is generally handled by the Calico CNI plugin or another orchestrator-specific plugin, and recommends viewing this resource type rather than manually managing it in typical Kubernetes deployments. I revised the introduction, note, and conclusion to make the guidance accurate.
- The manifest omitted useful Kubernetes WorkloadEndpoint fields shown in the official Calico sample, including `containerID` and `pod`. I added them to the example and added them to the field descriptions.
- The post described the example values as "sensible defaults." These values are environment-specific placeholders, not defaults. I changed the wording to require matching the real node, pod, interface, IP address, and profiles.
- The kubectl guidance did not explain that `projectcalico.org/v3` resources require the Calico API server or native v3 CRDs when managed through kubectl. I added that condition and kept calicoctl as the validation/defaulting path where server-side API validation is not available.
- The `kubectl describe workloadendpoint.projectcalico.org` example did not name a specific resource despite the surrounding text saying to describe a specific resource. I added the example resource name.
- The troubleshooting section suggested restarting `calico-node` when components do not pick up the resource. That is not a first-line correction for a manually mismatched WorkloadEndpoint. I changed it to verify that the resource values match a real endpoint, then inspect Felix and Typha logs.
- The log command assumed the `calico-system` namespace. Calico documentation also shows `calico-system`, while some manifest-based installs use `kube-system`. I added a caveat to use the namespace that matches the installation.
- The "Resource Naming Conventions" label was missing Markdown heading syntax. I corrected it to a third-level heading.

## Review Notes
The post is now technically accurate as an explanatory guide, but creating Kubernetes WorkloadEndpoint objects manually remains an advanced and uncommon operation. Future revisions could focus more on inspecting existing endpoints generated by Calico rather than applying new ones.
