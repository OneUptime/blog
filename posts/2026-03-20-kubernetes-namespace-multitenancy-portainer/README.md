# How to Implement Namespace-Based Multi-Tenancy in Portainer for Kubernetes

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Portainer, Kubernetes, Namespace, Multi-Tenant, RBAC, Access Control

Description: Configure Kubernetes namespace-based multi-tenancy through Portainer, assigning teams to specific namespaces with RBAC policies and resource quotas for complete tenant isolation.

## Introduction

Kubernetes namespaces provide the primary isolation boundary for multi-tenancy. Combined with Kubernetes RBAC and Portainer's namespace access controls, you can give each team or tenant access to only their namespace through the Portainer UI - without them needing kubectl access or knowledge of other namespaces. Portainer's RBAC-based namespace access controls are available in Business Edition. This guide covers creating namespaced environments, applying ResourceQuotas, and configuring Portainer team access for Kubernetes.

## Step 1: Connect Kubernetes Cluster to Portainer

```bash
# Install Portainer Agent in the Kubernetes cluster
# Example current LTS manifest; use the command generated by Portainer for your installation

kubectl apply -f \
  https://downloads.portainer.io/ce-lts/portainer-agent-k8s-lb.yaml

# Get the agent's LoadBalancer IP
kubectl get svc -n portainer portainer-agent

# Register the cluster in Portainer
# Portainer UI: Environment-related > Environments > Add environment > Kubernetes
# Environment URL: AGENT_LB_IP:9001
```

## Step 2: Create Namespaces per Tenant

```bash
# Create namespaces for each team
kubectl create namespace team-alpha
kubectl create namespace team-beta
kubectl create namespace team-gamma

# Optional labels for your own tenant metadata
kubectl label namespace team-alpha team=alpha tenant=alpha-corp
kubectl label namespace team-beta team=beta tenant=beta-inc
kubectl label namespace team-gamma team=gamma tenant=gamma-ltd

# Verify
kubectl get namespaces --show-labels
```

## Step 3: Apply Resource Quotas per Namespace

```yaml
# team-alpha-quota.yaml - Resource limits for Team Alpha's namespace
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    # Compute resources
    requests.cpu: "4"          # Total CPU requests allowed
    requests.memory: 8Gi       # Total memory requests
    limits.cpu: "8"            # Total CPU limits
    limits.memory: 16Gi        # Total memory limits

    # Object count limits
    pods: "20"                 # Max 20 pods
    services: "10"             # Max 10 services
    persistentvolumeclaims: "5" # Max 5 PVCs
    secrets: "20"              # Max 20 secrets
    configmaps: "20"           # Max 20 configmaps
    count/deployments.apps: "10" # Max 10 deployments
```

```bash
kubectl apply -f team-alpha-quota.yaml

# Apply LimitRange for default container limits
kubectl apply -f - <<EOF
apiVersion: v1
kind: LimitRange
metadata:
  name: team-alpha-limits
  namespace: team-alpha
spec:
  limits:
  - type: Container
    default:
      cpu: "500m"       # Default CPU limit per container
      memory: "512Mi"   # Default memory limit per container
    defaultRequest:
      cpu: "100m"       # Default CPU request
      memory: "128Mi"   # Default memory request
    max:
      cpu: "2"          # Max CPU limit per container
      memory: "4Gi"     # Max memory limit per container
EOF
```

## Step 4: Create RBAC for Tenant Users

If you also need a namespace-scoped Kubernetes identity for automation or CLI testing, create a ServiceAccount, Role, and RoleBinding in the tenant namespace.

```yaml
# team-alpha-rbac.yaml - RBAC for Team Alpha
apiVersion: v1
kind: ServiceAccount
metadata:
  name: team-alpha-sa
  namespace: team-alpha

---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: team-alpha-role
  namespace: team-alpha
rules:
  # Allow managing core namespaced resources
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps", "secrets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Allow managing deployments in the apps API group
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Allow viewing pod logs
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
  # Allow exec access if required
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create", "get"]
  # No access is granted outside team-alpha because this role is namespace-scoped

---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: team-alpha-binding
  namespace: team-alpha
subjects:
  - kind: ServiceAccount
    name: team-alpha-sa
    namespace: team-alpha
roleRef:
  kind: Role
  name: team-alpha-role
  apiGroup: rbac.authorization.k8s.io
```

```bash
kubectl apply -f team-alpha-rbac.yaml

# Request a short-lived token for Team Alpha's service account
kubectl create token team-alpha-sa -n team-alpha
```

## Step 5: Configure Portainer Namespace Access per Team

```bash
# Portainer UI: Environment-related > Policies > Create policy
# Policy type: Kubernetes > RBAC > Custom
# Users/teams: Alpha Corp
# Role: select a namespace-scoped role
# Namespaces: team-alpha
# Click Add Access, then Create policy
```

## Step 6: Verify Namespace Isolation

```bash
# Check quota usage for each namespace
kubectl describe quota -n team-alpha
kubectl describe quota -n team-beta

# Verify cross-namespace isolation
# As a cluster admin impersonating the team-alpha service account
kubectl auth can-i list pods \
  --as=system:serviceaccount:team-alpha:team-alpha-sa \
  -n team-beta
# no

# Check resource usage (requires Metrics Server)
kubectl top pod -n team-alpha
kubectl top pod -n team-beta

# List namespaces with their quota status
kubectl get resourcequota --all-namespaces
```

## Conclusion

Kubernetes namespace-based multi-tenancy combines several components: namespaces provide logical isolation, ResourceQuotas enforce compute limits, LimitRanges set per-container defaults, RBAC restricts which identities can act in each namespace, and NetworkPolicies (not covered here) provide network isolation. Portainer surfaces these namespaces in the UI, and Portainer Business Edition can map users and teams to specific namespaces through its RBAC features, providing a friendly interface for teams who don't need to learn kubectl. This architecture scales well - adding a new tenant means creating a namespace, applying quota policies, optionally creating namespace-scoped Kubernetes identities for automation, and configuring Portainer access for the team.
