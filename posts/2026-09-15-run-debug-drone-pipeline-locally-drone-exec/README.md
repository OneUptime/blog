# How to Run and Debug a Drone Pipeline Locally with `drone exec`

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Drone, CI/CD, Docker, DevOps, Troubleshooting

Description: Reproduce Docker pipeline failures locally with drone exec, explicit event metadata, isolated workspaces, and test secrets.

`drone exec` shortens the feedback loop for a failing Docker pipeline. It runs the steps with your local Docker daemon and streams their output. It does not ask your Drone server to start a build, so it cannot prove that webhooks, runner routing, or server-side secret policies work. Drone's [local runner guide](https://docs.drone.io/quickstart/cli/) describes this scope.

## Start with a reproducible checkout

Install the Drone CLI for your platform, then verify the tools and the Docker daemon:

```sh
drone --version
drone exec --help
docker version
```

Use a throwaway checkout at the failing commit. A local run mounts your current directory, including generated files and uncommitted changes, into step containers. A clean checkout avoids accidentally depending on yesterday's compiled output. It also prevents the pipeline from modifying your normal working files.

For example, run this `.drone.yml` from the root of a small Go module that has tests:

```yaml
kind: pipeline
type: docker
name: unit

steps:
  - name: test
    image: golang:1.25
    commands:
      - go test ./...
  - name: compile
    image: golang:1.25
    commands:
      - go build ./...
```

```sh
drone exec --pipeline=unit --timeout=10m .drone.yml
```

The selected image is an example toolchain; use the same tested tag or digest as the remote build. The [CLI reference](https://docs.drone.io/cli/drone-exec/) documents pipeline selection and timeout flags. A nonzero exit status means the local execution failed; capture that status when wrapping the command in another script.

## Narrow the failure without hiding dependencies

Execute the smallest meaningful set of steps:

```sh
drone exec --pipeline=unit --include=test .drone.yml
```

If `compile` needs files generated by an earlier step, include the producer too. An include filter does not manufacture missing artifacts. Running only a deployment step against stale local output can produce a convincing but irrelevant result.

Inspect the failing command and its prerequisites separately: working directory, image version, executable availability, input files, and network endpoint. Avoid adding a dump of the entire environment because that can reveal credentials.

## Supply metadata and secrets deliberately

Conditions depend on the event being emulated. Check your CLI's available flags, then supply the branch and event explicitly:

```sh
drone exec --pipeline=unit --event=push --branch=main .drone.yml
drone exec --pipeline=unit --event=pull_request --branch=main .drone.yml
```

These commands exercise different step conditions; they do not create real Git provider events. For metadata without a dedicated flag, use the supported environment mechanisms in your installed CLI and compare with the actual build's values.

A step can read an application test token using a named secret:

```yaml
environment:
  API_TOKEN:
    from_secret: integration_test_token
```

Create a local file outside the checkout with restrictive permissions, containing one dotenv assignment such as `integration_test_token=local-test-value`. Then pass its absolute path:

```sh
drone exec --secret-file=/tmp/drone-local.secrets --pipeline=unit .drone.yml
```

The secret's name must match `from_secret`, not the environment variable's target name. Use a disposable test credential. The CLI does not retrieve server-managed credentials or reproduce their access controls. Delete the local secret file after the test.

## Investigate differences that survive a local pass

| Local success hides | Remote check |
| --- | --- |
| Files left in your checkout | Reproduce from the exact commit in a fresh checkout |
| Local Docker credentials or cached images | Verify the runner's image-pull credentials and image policy |
| Different CPU architecture | Compare image manifests and the pipeline platform |
| Reachable local database | Check the runner network and service address |
| Missing server-side behavior | Test webhook processing, configuration extensions, and secret permissions remotely |

A Kubernetes pipeline needs its Kubernetes runner for a representative test. The local Docker executor is also different from a pipeline whose type is `exec`, which runs directly on a runner host. Check the [runner overview](https://docs.drone.io/runner/overview/) before assuming the names describe interchangeable execution environments.

Finally, run one controlled remote build with the fix. Record its commit, event, runner, and result so that a local pass leads to a verified correction in the environment that originally failed.
