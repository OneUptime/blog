## Issues Found
- The post used a `grafana/faro-collector` Docker image and OpenTelemetry Collector-style YAML that does not match the current recommended self-managed Faro setup. Replaced it with a Grafana Alloy Docker Compose example and a valid Alloy `faro.receiver` configuration that forwards logs/measurements to Loki and traces to Tempo.
- The SDK initialization used an object-shaped `instrumentations` configuration with keys such as `errors`, `console`, `webVitals`, `interactions`, and `fetch`. Current Faro SDK expects an array of instrumentation instances. Updated the example to use `getWebInstrumentations()` and `TracingInstrumentation`.
- The SDK examples used `session.trackSession`; current Faro uses `sessionTracking.enabled` and related options. Updated session configuration accordingly.
- The custom measurement example used `value` and `attributes`; current `pushMeasurement` uses `values` and optional `context`. Updated the snippet.
- Several custom event and metadata attributes used numbers, but Faro event and meta attributes are string maps. Converted those values to strings.
- The Web Vitals and dashboard examples referenced Prometheus metric names such as `faro_web_vitals_lcp_seconds` and `faro_errors_total` that Faro does not emit by default. Replaced the examples with Grafana Cloud alerting guidance and Loki-based dashboard starter queries.
- The sensitive-data filtering example treated `beforeSend` as receiving a payload object. Current Faro receives a transport item with `meta`, `payload`, and `type`. Updated the example to filter the correct shape.
- The React Router example referenced an undefined `previousPath`. Added `useRef` tracking so the example is syntactically coherent.
- The session replay section implied Faro could track DOM mutations for replay through configuration options that are not part of the current SDK. Reworded it as contextual event tracking and removed unsupported options.
- The API performance section used unsupported `fetch` instrumentation configuration. Updated it to use `TracingInstrumentation` and OpenTelemetry fetch custom attributes.

## Review Notes
Grafana Cloud Frontend Observability provides built-in dashboards and alerting rules. For self-managed Alloy/Loki setups, exact LogQL metric queries depend on the Loki labels and log format you choose, so the post now avoids hard-coded Prometheus metric names that are not generated by the default Faro path.
