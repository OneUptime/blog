# How to Add Labels to All Helm Resources with Post-Renderer in Flux

Author: [nawazdhandala](https://github.com/nawazdhandala)

Tags: Flux, HelmRelease, Kubernetes, GitOps, Helm, Post-Renderers, Labels, Kustomize

Description: Learn how to use Flux post-renderers to add custom labels to all resources generated by a Helm chart without modifying the chart itself.

---

## Introduction

Adding consistent labels to all Kubernetes resources is a common requirement for organization, cost tracking, compliance, and tooling integration. While many Helm charts support custom labels through values, not all charts expose every labeling option, and some resources within a chart may not inherit the labels you configure.

Flux CD solves this problem with common metadata and post-renderers. A post-renderer is a processing step that runs after Helm renders the chart templates but before the manifests are applied to the cluster. Flux includes built-in support for Kustomize-based post-renderers, and its HelmRelease `commonMetadata` field applies labels and annotations to every resource in a Helm release without modifying the chart or maintaining a fork.

This guide shows you how to configure common metadata and post-renderer patches to add labels to resources in a HelmRelease, with practical examples for common labeling scenarios.

## Prerequisites

Before you begin, ensure you have:

- A Kubernetes cluster with Flux CD installed
- A working HelmRelease in your cluster
- kubectl access to the cluster
- Basic familiarity with Kustomize

## How Post-Renderers Work

When Flux processes a HelmRelease, it follows these steps:

1. Fetch the chart from the source
2. Render the chart templates with the configured values
3. Pass the rendered manifests through any configured post-renderers
4. Apply the final manifests to the cluster

Post-renderers receive the full set of rendered Kubernetes manifests and can modify them using the Kustomize directives supported by Flux. In the HelmRelease `v2` API, the built-in Kustomize post-renderer supports `patches` and `images`. For labels and annotations that should be added to every rendered resource, use `spec.commonMetadata`.

## Adding Labels with commonMetadata

The simplest way to add labels to all resources is using the HelmRelease `commonMetadata` field:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: my-app
  namespace: default
spec:
  interval: 10m
  chart:
    spec:
      chart: my-app
      version: "2.0.0"
      sourceRef:
        kind: HelmRepository
        name: my-repo
        namespace: flux-system
  commonMetadata:
    labels:
      team: platform
      cost-center: engineering
      environment: production
```

This adds the labels `team: platform`, `cost-center: engineering`, and `environment: production` to every resource rendered by the chart. Flux applies these labels to all resources including Deployments, Services, ConfigMaps, and any other resource types in the chart.

## Understanding Label Propagation

When using `commonMetadata`, Flux adds the labels to the `metadata.labels` of every rendered resource. It does not add labels to workload selectors or Pod templates. That behavior is different from Kustomize `commonLabels`, which is not exposed as a HelmRelease post-renderer field in the Flux `v2` API.

If you need labels on nested fields, use explicit post-renderer patches for the specific resource types. This distinction is important because changing selectors on existing Kubernetes resources can fail or force resource replacement when selector fields are immutable.

## Adding Labels to Specific Resource Types

Sometimes you only want to label certain resource types or nested fields. Use the post-renderer target selector to narrow the scope:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: my-app
  namespace: default
spec:
  interval: 10m
  chart:
    spec:
      chart: my-app
      version: "2.0.0"
      sourceRef:
        kind: HelmRepository
        name: my-repo
        namespace: flux-system
  postRenderers:
    - kustomize:
        patches:
          - target:
              kind: Deployment
            patch: |
              apiVersion: apps/v1
              kind: Deployment
              metadata:
                name: not-used
              spec:
                template:
                  metadata:
                    labels:
                      monitoring: enabled
                      log-aggregation: enabled
          - target:
              kind: Service
            patch: |
              apiVersion: v1
              kind: Service
              metadata:
                name: not-used
                labels:
                  service-mesh: enabled
```

This adds monitoring-related labels to Deployment Pod templates and a service mesh label to Services.

If the label must also be part of a Service selector or a Deployment selector, patch those fields deliberately and test the change on a fresh install before using it on an existing release:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: my-app
  namespace: default
spec:
  interval: 10m
  chart:
    spec:
      chart: my-app
      version: "2.0.0"
      sourceRef:
        kind: HelmRepository
        name: my-repo
        namespace: flux-system
  postRenderers:
    - kustomize:
        patches:
          - target:
              kind: Deployment
            patch: |
              - op: add
                path: /spec/selector/matchLabels/monitoring
                value: enabled
              - op: add
                path: /spec/template/metadata/labels/monitoring
                value: enabled
          - target:
              kind: Service
            patch: |
              - op: add
                path: /spec/selector/monitoring
                value: enabled
```

This changes how Deployments and Services match Pods, so use it only when the chart's generated Pods will have matching labels.

## Multiple Label Sets for Different Purposes

You can organize labels by purpose in `commonMetadata`:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: my-app
  namespace: production
spec:
  interval: 5m
  chart:
    spec:
      chart: my-app
      version: "2.0.0"
      sourceRef:
        kind: HelmRepository
        name: my-repo
        namespace: flux-system
  commonMetadata:
    labels:
      app.kubernetes.io/managed-by: flux
      app.kubernetes.io/part-of: my-platform
      team: backend
      environment: production
      cost-center: eng-backend
```

## Verifying Labels

After applying your HelmRelease, verify that labels were added correctly:

```bash
kubectl get all -n default -l team=platform -o name
```

You can also inspect a specific resource to see all labels:

```bash
kubectl get deployment my-app -n default -o jsonpath='{.metadata.labels}' | jq .
```

## Conclusion

Flux provides a powerful way to add labels to all resources generated by a Helm chart without modifying the chart itself. Use `commonMetadata` when you need metadata labels on every rendered resource, and use post-renderer patches when you need targeted labels on specific resource types or nested fields. This approach keeps your labeling strategy consistent across all HelmReleases and decoupled from chart-specific configuration, making it easy to enforce organizational labeling standards across your entire cluster.
