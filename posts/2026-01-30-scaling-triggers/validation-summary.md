## Issues Found
- **KEDA AWS SQS scaler `identityOwner: operator`** (line ~450): The `identityOwner` parameter was removed from the KEDA AWS SQS scaler in KEDA 2.13. Operator-level IAM is now the default when no `TriggerAuthentication` is supplied; pod-level identity requires a `TriggerAuthentication` with `podIdentity`. Replaced the `identityOwner: operator` line with explanatory comments describing the current authentication options.
- **KEDA Prometheus scaler `metricName`** (line ~472): The `metricName` field was removed from the KEDA Prometheus scaler — it is now auto-generated by KEDA. Including it in current KEDA versions causes a validation/parsing error. Removed the `metricName: http_requests_per_second` line; the remaining `serverAddress`, `query`, and `threshold` fields are sufficient.

## Review Notes
- The `autoscaling/v2` HPA API is correct and stable since Kubernetes 1.23. The "Kubernetes 1.18+" claim for `behavior` is accurate (introduced in `autoscaling/v2beta2` in 1.18, graduated to stable v2 in 1.23).
- The HPA scaling formula `desiredReplicas = ceil[currentReplicas * (currentMetricValue / desiredMetricValue)]` is consistent with the diagram showing 80% CPU producing 8 replicas (assuming current 7 replicas at 65% target) — the example numbers are illustrative rather than mathematically precise, which is fine for a conceptual diagram.
- Memory `AverageValue: 500Mi` and CPU `Utilization: 70` targets are both valid for the `Resource` metric type in `autoscaling/v2`.
- The mixed `Resource` (CPU/memory) + `Pods` (custom) + `External` metric types are all valid; the HPA correctly picks the maximum desired replica count across metrics.
- The Prometheus Adapter `seriesQuery` / `metricsQuery` / `resources` / `name` block syntax is correct, including the `<<.Series>>`, `<<.LabelMatchers>>`, and `<<.GroupBy>>` template variables.
- The kube-state-metrics names `kube_horizontalpodautoscaler_status_current_replicas`, `kube_horizontalpodautoscaler_status_desired_replicas`, and `kube_horizontalpodautoscaler_spec_max_replicas` are correct.
- The `monitoring.coreos.com/v1` `PrometheusRule` schema (groups → rules → alert/expr/for/labels/annotations) is correct.
- The Prometheus Adapter Helm command uses `prometheus.url=http://prometheus-server.monitoring.svc` without a port — this works if the Service exposes port 80, which is the default for the `prometheus-server` Service in the kube-prometheus stack. Including `:9090` would also be valid depending on the Service configuration.
- KEDA CPU scaler requires the workload to have CPU `requests` defined, mirroring the HPA requirement — the post correctly emphasizes this in the "Missing Resource Requests" section.
- The KEDA cron scaler `start`/`end` use standard cron syntax with five fields and a `timezone` (IANA) string — both examples are syntactically correct.
