## Issues Found
1. **Missing `pkPinning: true` flag for public key pinning (corrected).**
   The post used the `react-native-ssl-pinning` library with SHA-256 public key hashes (`'sha256/...'`) inside `sslPinning.certs`, but omitted the required `pkPinning: true` flag. Without that flag, the library treats `certs` entries as bundled `.cer` certificate file names (certificate pinning mode), not public key hashes — so the documented public key pinning examples would not work. Fixed in three places:
   - `SSL_PINNING_CERTS` config object (`src/config/sslPinning.ts`) — added `pkPinning: true` to each host entry. These objects are spread (`...pinningConfig`) into the `pinnedFetch` call, so the flag now reaches the fetch options correctly.
   - The commented-out public-key-pinning alternative in `SSL_PINNING_CONFIG` (`src/utils/pinnedFetch.ts`) — rewrote the comment to show `pkPinning: true` at the top level of the fetch options alongside `sslPinning.certs` (the original comment also had incorrect nesting).
   - The `SSL_PINS` rotation example — added `pkPinning: true` for consistency since it uses `sha256/` hashes.

## Review Notes
- **iOS hash representation caveat (not changed):** The iOS Swift example computes its pin from `SecKeyCopyExternalRepresentation`, which returns the *raw* public key (PKCS#1 for RSA / ANSI X9.63 for EC), whereas the documented OpenSSL command (and OkHttp / Android Network Security Config) produces a hash of the DER-encoded **SubjectPublicKeyInfo (SPKI)**. As written, the iOS code is internally self-consistent (it hashes the server key the same way it stores its pins), but a hash generated by the post's OpenSSL command will **not** match the iOS-computed hash. To make the same pin work across all platforms, the iOS implementation must prepend the algorithm-specific ASN.1 SPKI header to the key bytes before hashing. This was left as-is rather than edited because a correct fix requires introducing key-algorithm-specific assumptions (e.g. RSA-2048 vs EC) not present in the original example. Readers using the native iOS path should be aware of this. The cross-platform `react-native-ssl-pinning` / OkHttp / Network Security Config paths all use SPKI hashes and are consistent with the OpenSSL command.
- **Deprecated iOS API:** `SecTrustGetCertificateAtIndex(_:_:)` is deprecated as of iOS 15 in favor of `SecTrustCopyCertificateChain(_:)`. It still compiles and works, so it was not changed, but new code should prefer the replacement.
- The OkHttp 4.x Kotlin code (`toMediaType`, `toRequestBody`, `response.code`, `response.body?.string()`, `Headers.forEach` destructuring) is current and correct.
- The Android `network_security_config.xml` (`<pin-set>`, `<pin digest="SHA-256">`, `cleartextTrafficPermitted`, `expiration`) and `AndroidManifest.xml` reference are accurate.
- The OpenSSL extraction commands produce a correct SPKI SHA-256 base64 hash and match OkHttp/Network Security Config pin format.
- Minor stylistic inconsistency (not a technical error): the debugging section's `secureRequest` snippet references a `RequestConfig` type while the earlier definition uses `PinnedRequestConfig`; this is a partial illustrative snippet ("... rest of implementation") and was left unchanged.
- Conceptual explanations (MITM, defense-in-depth, certificate vs public key pinning trade-offs, rotation strategy, backup pins) are accurate.
