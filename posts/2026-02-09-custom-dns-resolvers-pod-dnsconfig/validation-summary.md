## Issues Found
- The description of `ClusterFirst` said it "fallbacks" to upstream DNS. Updated it to state that cluster DNS handles the query path and forwards external queries upstream, which better matches Kubernetes DNS behavior.
- The `ClusterFirst` + `dnsConfig.nameservers` section implied an additional nameserver behaves like a general fallback. Clarified that Kubernetes appends the configured nameserver after the base nameservers generated from `dnsPolicy`.
- The environment-specific ConfigMap section implied `dnsConfig` can be populated directly from ConfigMaps. Clarified that ConfigMaps may document values, but Pod `dnsConfig` fields are static in the Pod spec.
- The external DNS example used a public DNS server as a fallback and included cluster search domains even though the configured nameservers would not resolve Kubernetes cluster service names unless they forward those zones. Removed the public fallback and clarified that the external DNS server must resolve or forward the required zones.
- The search domain section listed custom search domains before base cluster search domains under `ClusterFirst`. Updated the explanation to reflect Kubernetes' merge behavior: custom searches are appended to the base search domains generated by the selected DNS policy.
- The `ndots` comment incorrectly suggested lower values always make search domains happen sooner. Updated comments to explain that lower values make dotted names try absolute resolution sooner.
- The resolver options example included `inet6`, which is obsolete in modern glibc resolver behavior and misleading as "enable IPv6 queries." Removed it from the example and common options list.
- The DNS test pod used `dnsPolicy: None` with only public nameservers while expecting Kubernetes service DNS to resolve. Changed it to `ClusterFirst` so cluster DNS remains available and the test expectation is valid.
- The troubleshooting section incorrectly stated that `dnsConfig` is ignored with `dnsPolicy: Default`. Replaced it with guidance to recreate pods after changing `dnsConfig` and to use `None` only when replacing the base DNS configuration.
- The cluster service troubleshooting guidance said search domains alone were enough under `dnsPolicy: None`. Updated it to include the cluster DNS service IP as a nameserver plus the cluster search domains.
- The best practices list recommended generic fallback nameservers. Clarified that stub resolvers generally try another nameserver after timeouts, not after NXDOMAIN responses.
