## Review Notes
- `strategy.fail-fast` applies to jobs generated by that matrix and defaults to `true`; a required matrix row failure cancels queued and in-progress rows, while a row with job-level `continue-on-error: true` does not trigger that cancellation.
- The `needs` examples correctly model successful prerequisites. GitHub skips a dependent job after a failed or skipped prerequisite unless its condition overrides the default success check.
- The final gate correctly uses the documented `needs.<job_id>.result` values (`success`, `failure`, `cancelled`, and `skipped`). On the Ubuntu runner, the default shell's fail-fast behavior makes the gate step fail as soon as one `test` command returns nonzero.
- `if: ${{ !cancelled() }}` is GitHub's documented alternative to `always()` for work that should run after success or failure but should remain cancellable. The warnings about using `always()` for source retrieval or other failure-prone work are current.
- GitHub currently treats `success`, `skipped`, and `neutral` as successful required-check conclusions. A conditionally skipped job reports success, whereas a workflow omitted by branch, path, or commit-message filtering leaves its associated checks pending.
- Workflows supplying required checks to a merge queue must also handle the `merge_group` event.
