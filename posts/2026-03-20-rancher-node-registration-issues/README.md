# How to Troubleshoot Node Registration Issues in Rancher

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Rancher, Kubernetes, Troubleshooting, Node

Description: Diagnose and resolve node registration failures in Rancher, including token mismatches, network connectivity, and kubelet configuration issues.

## Introduction

When adding nodes to a Rancher-managed cluster, the node must successfully execute the registration command, run the node agent, and establish communication with both the Rancher server and the cluster's control plane. Failures at any of these steps prevent the node from joining. This guide walks through each failure point.

## Understanding the Node Registration Flow

1. Admin runs the registration command generated by Rancher on the target node.
2. For Rancher-provisioned RKE2/K3s clusters, `rancher-system-agent` contacts Rancher server and downloads the node plan.
3. The RKE2 or K3s agent starts kubelet, which registers with the Kubernetes API server.
4. `cattle-cluster-agent` connects the downstream cluster back to Rancher; older RKE clusters also run `cattle-node-agent` on each node.

## Step 1: Verify the Registration Command

```bash
# In Rancher UI: open the cluster's Registration page and copy the command shown there

# Use a freshly copied command for the correct cluster and node roles.
# The exact command varies by Rancher version and cluster type.
# Current Rancher custom-node provisioning uses the Rancher-generated registration command.
# Older RKE custom clusters used a Docker-based rancher-agent command.

# If Rancher's server URL or CA certificate changed recently, copy the command again.
# Rancher agent deployment tokens are typically long-lived unless revoked, so
# "token is invalid" usually means the command is stale, for the wrong cluster,
# or no longer matches the current CA/server settings.
```

## Step 2: Check Node Agent Logs

```bash
# For RKE2 agent nodes
sudo journalctl -u rke2-agent -f --no-pager --lines=200

# For older RKE custom clusters that use Docker-based rancher-agent
docker logs <rancher-agent-container-id> -f --tail=200

# For K3s agent nodes
sudo journalctl -u k3s-agent -f --no-pager --lines=200
```

Common error messages:

| Error | Cause |
|---|---|
| `Failed to connect to proxy` | Node can't reach Rancher server |
| `x509: certificate signed by unknown authority` | CA cert not trusted |
| `token is invalid` | Command is stale, token was revoked, or the command was copied from the wrong cluster |
| `node already exists` | Node name conflict (duplicate hostname) |

## Step 3: Test Network Connectivity from the Node

```bash
# The node must reach the Rancher server on port 443
curl -vkI https://<rancher-url>

# Join ports depend on the cluster type.
# RKE2 agents join through the supervisor on port 9345, and control-plane traffic uses 6443.
nc -zv <rke2-server-or-load-balancer> 9345
nc -zv <rke2-server-or-load-balancer> 6443

# K3s agents join through port 6443.
nc -zv <k3s-server-or-load-balancer> 6443

# Check if required ports are blocked by iptables or firewalld
sudo iptables -L INPUT -n -v | grep DROP
sudo firewall-cmd --list-all  # if using firewalld
```

## Step 4: Check for Hostname/Node Name Conflicts

```bash
# Kubernetes node names must be unique
kubectl get nodes
# By default, the node name comes from the hostname unless you explicitly set node-name

# On the new node, check hostname
hostname

# If there's a duplicate, either:
# 1. Change the hostname on the new node
sudo hostnamectl set-hostname new-node-hostname

# 2. Delete the old node entry from Kubernetes
kubectl delete node <conflicting-node-name>
```

## Step 5: Check for Swap and Firewall Issues

```bash
# On Linux, kubelet will not start with swap enabled unless configured otherwise
sudo swapon --show
# If swap is active and you're using the default kubelet behavior:
sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

# Check SELinux / AppArmor status (may block container runtimes)
sestatus        # SELinux
sudo aa-status  # AppArmor

# If bridge traffic is not reaching iptables, load br_netfilter and verify it
sudo modprobe br_netfilter
lsmod | grep br_netfilter

# Ensure sysctl settings are correct for iptables-based CNIs
sudo sysctl net.bridge.bridge-nf-call-iptables
# Expected: net.bridge.bridge-nf-call-iptables = 1
```

## Step 6: Debug the Kubelet Directly

```bash
# On an RKE2 server/control-plane node, confirm the cluster can see the node
sudo /var/lib/rancher/rke2/bin/kubectl \
  --kubeconfig /etc/rancher/rke2/rke2.yaml \
  get nodes

# RKE2 writes kubelet logs here
sudo tail -f /var/lib/rancher/rke2/agent/logs/kubelet.log

# Check kubelet configuration used by RKE2
sudo cat /var/lib/rancher/rke2/agent/kubelet.kubeconfig
```

## Step 7: Manually Clean Up a Failed Node

```bash
# Remove the node from Kubernetes
kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data
kubectl delete node <node-name>

# On Rancher-provisioned RKE2/K3s nodes, remove rancher-system-agent first
curl -fsSL https://raw.githubusercontent.com/rancher/system-agent/main/system-agent-uninstall.sh -o system-agent-uninstall.sh
sudo sh system-agent-uninstall.sh

# Then remove the Kubernetes distribution from the node
sudo rke2-uninstall.sh   # For RKE2 nodes
# OR
sudo k3s-agent-uninstall.sh  # For K3s agent nodes
# Use k3s-uninstall.sh on K3s server nodes

# Re-run the registration command from Rancher
```

## Conclusion

Node registration issues in Rancher are typically caused by network connectivity problems, an invalid or stale registration command, hostname conflicts, or missing system prerequisites. By methodically checking each layer - network, logs, hostname, and system prerequisites - you can quickly identify and resolve the issue and successfully join the node to your cluster.
