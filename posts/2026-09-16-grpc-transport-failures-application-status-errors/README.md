# How to Distinguish Transport Failures from Application Status Errors in gRPC Clients

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: gRPC, Go, Error Handling, Troubleshooting, Networking

Description: Interpret gRPC status codes without mistaking a status-compatible error for a server response, and use context, metadata, and traces to locate failures.

---

A Go client receives `rpc error: code = Unavailable`. That error might describe a failed connection, a proxy-generated response, or an application that deliberately returned `codes.Unavailable`. The status code is useful for recovery decisions, but it is not a complete record of where the failure originated.

Build diagnostics that distinguish observed facts from inferred causes. In particular, do not classify every status-compatible Go error as an application response and every other error as a network failure.

## Understand the Shared Error Model

gRPC presents application and library failures through the same status model. Applications may return codes that libraries also generate. A limited set, including `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `FAILED_PRECONDITION`, `ABORTED`, `OUT_OF_RANGE`, and `DATA_LOSS`, is documented as never generated by the gRPC library itself. That still does not identify which application or intermediary created the response. [gRPC status codes](https://grpc.io/docs/guides/status-codes/).

For the ambiguous codes, begin with this interpretation:

| Observation | What it establishes |
| --- | --- |
| `UNAVAILABLE` | This call could not complete; transport and application causes remain possible |
| `DEADLINE_EXCEEDED` | The caller did not obtain successful completion within the applicable deadline |
| `CANCELLED` | Cancellation occurred somewhere in the call lifecycle |
| `INTERNAL` or `UNKNOWN` | More evidence is needed; neither code proves a transport fault |
| Response messages followed by an error | Some response data arrived, but the overall RPC failed |

Avoid encoding error-message substrings such as “transport is closing” into permanent business logic. Use them as diagnostic clues alongside versioned logs and transport events.

## Record the Go Error Without Inventing Provenance

This helper deliberately records separate facts:

```go
package diagnostics

import (
    "context"

    "google.golang.org/grpc/codes"
    "google.golang.org/grpc/status"
)

type FailureObservation struct {
    Code             codes.Code
    StatusCompatible bool
    LocalContextErr  error
}

func observe(ctx context.Context, err error) FailureObservation {
    if err == nil {
        return FailureObservation{Code: codes.OK}
    }
    s, ok := status.FromError(err)
    return FailureObservation{
        Code:             s.Code(),
        StatusCompatible: ok,
        LocalContextErr:  ctx.Err(),
    }
}
```

`status.FromError` recognizes gRPC status errors, including wrapped compatible errors. Its boolean result is not a “response came from server application” flag. A plain local error yields `Unknown` with `ok == false`; a client-generated transport failure can yield a valid gRPC status. [gRPC-Go status package](https://pkg.go.dev/google.golang.org/grpc/status).

For ordinary generated Go client calls, errors are already compatible with the status package. Check raw local operations separately when the surrounding application also performs token retrieval, request construction, or result processing. [gRPC-Go client API](https://pkg.go.dev/google.golang.org/grpc#ClientConn.Invoke).

Capture `ctx.Err()` immediately after the failed call. A canceled local context is evidence about the caller's state at that moment, not proof that no backend work occurred. The context can also expire after a server response wins a nearby race.

## Collect Evidence Across the Call

Record the method, target, elapsed time, attempt count when available, remaining deadline at entry, and a correlation identifier. Capture response headers and trailers where the client API supports them.

An application-defined diagnostic trailer or structured error detail can associate a failure with server code. Its absence does not prove a transport failure: an interceptor may reject a call before adding it, a connection can break, or a proxy can replace the response.

Correlate the observations with server request logs and traces. Look for handler entry, dependency calls, commit completion, and terminal status. A missing server log can mean the request never arrived, but it can also reflect sampling, lost logs, or an incorrect correlation key.

If the server logged success while the client reported a deadline, investigate the time between completing work and the client receiving the terminal outcome. Do not label the server result false solely because the caller stopped waiting.

## Recognize Intermediary Responses

An HTTP proxy can fail before producing a valid gRPC response. When a response lacks `grpc-status`, clients use the defined HTTP-to-gRPC fallback mapping. For example, HTTP 502, 503, and 504 map to `UNAVAILABLE` in that situation. A received gRPC status takes precedence over this fallback. [gRPC HTTP status mapping](https://github.com/grpc/grpc/blob/master/doc/http-grpc-status-mapping.md).

That is why a status-14 spike may require proxy access logs, endpoint health, TLS negotiation, and upstream reset details. Repeating only application-level tests can miss a broken intermediate hop.

Compare a direct call with the production route using the same request and authentication. If only the proxied path fails, inspect that route before changing application status handling.

## Separate Recovery from Root Cause

A retry policy should depend on the operation's safety, the remaining deadline, and bounded attempts. It should not assume `UNAVAILABLE` means the server did no work.

For a read-only lookup, a bounded retry may be appropriate. For a payment or job submission, use an idempotency key or an operation-status lookup. A lost response can leave the outcome unknown even when the business transaction committed.

Built-in gRPC retries have specific commitment rules and do not automatically resume an already-delivering stream. Application retries also need to account for records consumed before failure. [gRPC retry behavior](https://grpc.io/docs/guides/retry/).

## Test the Classifier Against Different Origins

Use controlled failures that intentionally share a status code:

1. Return `codes.Unavailable` from a real server handler.
2. Connect to a deliberately unavailable test endpoint.
3. Let the caller deadline expire while a handler blocks cooperatively.
4. Return an HTTP 503 from a test intermediary without gRPC trailers.
5. Cancel a streaming call after receiving one message.

Assert the status and captured evidence, while allowing the recorded origin to remain unknown when the evidence cannot distinguish it. These tests prevent a future refactor from turning a useful observation into an unjustified claim.

The goal is a client that reacts safely and a diagnostic record that locates the failing hop. A single integer cannot do both jobs alone.
