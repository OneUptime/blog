# How to Deploy OneUptime on Kubernetes with Persistent Storage

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: OneUptime, Kubernetes, Helm, Persistent Storage, Self-Hosting

Description: Deploy the OneUptime Helm chart with explicit storage classes, durable database volumes, ingress settings, and production readiness checks.

---

The OneUptime Helm chart can install the application and its data services, but a successful `helm install` is not the same as a durable production deployment. The important choices are the storage class, database topology, volume sizes, ingress, secrets, backups, and scheduling constraints.

This guide targets chart behavior in OneUptime 12.0.33.

## Add the chart and inspect defaults

```bash
helm repo add oneuptime https://helm-chart.oneuptime.com
helm repo update
helm show values oneuptime/oneuptime > /tmp/oneuptime-values.yaml
kubectl get storageclass
```

Read the values for the chart version you will deploy. The chart's defaults are convenient starting points, not a capacity plan: the bundled standalone PostgreSQL and ClickHouse configurations are not highly available, resource requests and limits are not generally preset, and the default database volumes are small for sustained telemetry.

## Create a production values file

The following example makes the storage choices explicit while retaining the built-in database deployments:

```yaml
host: oneuptime.example.com
httpProtocol: https

global:
  storageClass: fast-retain

postgresql:
  enabled: true
  primary:
    persistence:
      enabled: true
      size: 100Gi

clickhouse:
  enabled: true
  persistence:
    enabled: true
    size: 1Ti

redis:
  master:
    persistence:
      enabled: false
```

The sizes are examples, not OneUptime requirements. Calculate ClickHouse space from daily ingest, compression, retention, replica count, and headroom. PostgreSQL holds configuration and operational state. Redis is used for cache, queues, and sessions and is not OneUptime's system of record, so persistence is optional.

Confirm that `fast-retain` exists, supports the access mode generated by the chart, expands volumes if you expect online growth, and uses an appropriate reclaim policy. A PersistentVolume protects data from a Pod restart, but it is not a backup.

## Decide on database availability

The chart supports several production patterns:

- built-in standalone PostgreSQL and ClickHouse for simpler installations
- CloudNativePG-managed PostgreSQL through the optional CNPG integration
- Altinity-managed ClickHouse with replicas and ClickHouse Keeper
- external managed PostgreSQL, ClickHouse, and Redis services

Enabling an operator is an architectural change, not just a replica-count toggle. Install and operate the required operator, choose anti-affinity and failure domains, validate backup support, and test recovery. The chart documentation shows the exact value keys, including `postgresOperator.cnpg.enabled` and `clickhouseOperator.altinity.enabled`.

For an external database, disable the corresponding bundled component and supply its connection settings through the chart's documented values and Kubernetes Secrets. Test TLS and network policy from a temporary Pod in the OneUptime namespace before installation.

## Install with a pinned version

Use a namespace and retain the exact inputs used for the release:

```bash
kubectl create namespace oneuptime
helm search repo oneuptime/oneuptime --versions | head
helm install oneuptime oneuptime/oneuptime \
  --namespace oneuptime \
  --version CHART_VERSION \
  --values values-production.yaml \
  --wait --timeout 20m
```

Replace `CHART_VERSION` with the chart version you reviewed. Do not store plaintext production credentials in the values file. Use the chart's secret inputs and your cluster's established secret-management workflow.

## Verify storage before sending telemetry

```bash
kubectl -n oneuptime get pods
kubectl -n oneuptime get pvc
kubectl -n oneuptime get events --sort-by=.lastTimestamp
helm -n oneuptime status oneuptime
```

Every required claim should be `Bound`, and database Pods should become ready without repeated mounts or restarts. Inspect each PVC's storage class, requested capacity, and backing volume. Then create a monitor, generate a small amount of telemetry, restart one application Pod, and confirm the data remains.

Before production traffic, also configure:

- resource requests and limits based on a load test
- Pod anti-affinity or topology spread for replicated stateful services
- PodDisruptionBudgets appropriate to the chosen database topology
- network policies for ingress and database paths
- snapshots or logical backups stored outside the cluster failure domain
- alerts for PVC fullness, database health, backup failure, and certificate expiry

## Plan expansion and restore

Kubernetes volume expansion depends on the StorageClass and CSI driver. Increasing a Helm value does not guarantee the existing PVC will resize, and shrinking a PVC is generally unsupported. Test the exact expansion procedure in the target cluster.

A replicated database and a persistent volume do not replace restore testing. Maintain PostgreSQL and ClickHouse backups, record the chart version and values, and restore into an isolated namespace on a schedule.

## Conclusion

A production OneUptime Helm deployment starts with explicit persistence and an honest database topology. Pin the chart, size ClickHouse for retention, verify PVC behavior, and pair durable volumes with independent backups and tested recovery.
