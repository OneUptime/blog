# How to Retry Argo Workflow Tasks with Exponential Backoff and Rate-Limit Delays

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Argo Workflows, Kubernetes, Retry Strategy, Exponential Backoff, Rate Limiting, Retry-After

Description: Configure bounded Argo Workflow retries with exponential backoff, conditional exit codes, delay caps, and application-level handling of dynamic HTTP Retry-After responses.

---

Retries are useful only when they reduce transient failure without multiplying load or repeating unsafe side effects. Argo Workflows provides a template-level `retryStrategy` for selecting retryable failures and spacing attempts with exponential backoff. It does not, however, dynamically replace the next delay with an HTTP response's `Retry-After` value.

A robust API-calling task therefore uses two layers:

1. **Inside the application attempt:** recognize HTTP `429`, parse `Retry-After`, and wait before calling the same API again.
2. **Around the Pod attempt:** let Argo retry infrastructure errors or a deliberate retryable exit code with bounded exponential backoff.

This separation preserves server-directed rate-limit delays while keeping Argo responsible for Pod lifecycle, failure history, and an overall retry budget.

## Start with a Bounded Argo Retry Strategy

Attach `retryStrategy` to the container or script template that can fail:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: retry-api-
spec:
  entrypoint: call-api
  templates:
    - name: call-api
      retryStrategy:
        limit: "5"
        retryPolicy: Always
        expression: >-
          lastRetry.status == 'Error' || lastRetry.exitCode == '75'
        backoff:
          duration: "5s"
          factor: "2"
          cap: "1m"
          maxDuration: "10m"
      container:
        image: example.com/report-client:1.4.0
        command: ["/app/report-client"]
```

This policy says:

- the original attempt can be followed by at most five retries;
- an Argo `Error`, such as applicable executor/infrastructure errors, is retryable;
- an application `Failure` is retried only when the main process exits with code `75`;
- other application exit codes stop immediately;
- the first backoff is five seconds and subsequent delays multiply by two;
- no individual revised delay exceeds one minute;
- the backoff strategy has a ten-minute maximum duration budget.

With these values, the uncapped delay sequence begins `5s`, `10s`, `20s`, `40s`, `80s`. The `cap` changes the fifth delay to `60s`. `maxDuration` is not another per-delay cap; it bounds the retry/backoff duration as described by Argo's field reference.

Quote duration and count values as shown. Argo's fields accept `IntOrString` or duration strings in several places, and explicit strings avoid YAML typing surprises when templates are generated by another tool.

## Choose the Retry Policy Deliberately

Argo distinguishes node phases:

- `OnFailure` retries main-container failures;
- `OnError` retries Argo controller errors and failures in infrastructure containers such as init or wait;
- `OnTransientError` retries errors Argo classifies as transient, including matches configured through `TRANSIENT_ERROR_PATTERN`;
- `Always` allows both failures and errors.

When both `retryPolicy` and `expression` are present, Argo logically combines them: both must permit the retry. The default policy also differs depending on whether an expression is present in current Argo releases. Make the policy explicit so an upgrade or reader does not have to infer it.

The example uses `Always`, then narrows it with:

```text
lastRetry.status == 'Error' || lastRetry.exitCode == '75'
```

`lastRetry.exitCode`, `lastRetry.status`, `lastRetry.duration`, and `lastRetry.message` are strings in retry expressions. Comparing the exit code to `'75'` avoids an unnecessary cast. Use `asInt(...)` if you need numeric ranges.

## Reserve Exit Codes for Retry Decisions

Define an application contract:

| Exit code | Meaning | Argo action in this policy |
| ---: | --- | --- |
| `0` | Completed | Succeed |
| `64` | Invalid input or permanent client error | Fail without retry |
| `75` | Temporary upstream or rate-limit exhaustion | Retry |
| other | Unexpected application defect | Fail without retry |

Exit code `75` is a convention chosen for this Workflow, not an Argo-reserved code. Document whichever code you choose and keep it consistent across images.

This is more reliable than matching free-form error text. `lastRetry.message` can help with controller-reported conditions, but log wording and message prefixes can change. A process you control should communicate retryability through a stable exit code.

## Honor `Retry-After` Inside the Task

HTTP `Retry-After` can contain either a number of seconds or an HTTP date. The following Python script handles both, retries a few times inside one Pod, and exits `75` if the local rate-limit budget is exhausted:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: rate-limited-api-
spec:
  entrypoint: request
  arguments:
    parameters:
      - name: api-url
        value: https://api.example.com/v1/reports

  templates:
    - name: request
      retryStrategy:
        limit: "5"
        retryPolicy: Always
        expression: >-
          lastRetry.status == 'Error' || lastRetry.exitCode == '75'
        backoff:
          duration: "5s"
          factor: "2"
          cap: "1m"
          maxDuration: "10m"
      script:
        image: python:3.13-alpine
        command: [python]
        env:
          - name: API_URL
            value: "{{workflow.parameters.api-url}}"
          - name: IDEMPOTENCY_KEY
            value: "{{workflow.uid}}"
        source: |
          import datetime
          import email.utils
          import math
          import os
          import random
          import sys
          import time
          import urllib.error
          import urllib.request

          RETRYABLE_EXIT = 75
          PERMANENT_EXIT = 64
          MAX_SERVER_DELAY = 300
          LOCAL_ATTEMPTS = 3

          def retry_after_seconds(raw_value):
              if not raw_value:
                  return None

              value = raw_value.strip()
              if value.isdigit():
                  return int(value)

              try:
                  retry_at = email.utils.parsedate_to_datetime(value)
                  if retry_at.tzinfo is None:
                      retry_at = retry_at.replace(
                          tzinfo=datetime.timezone.utc
                      )
                  now = datetime.datetime.now(datetime.timezone.utc)
                  return max(
                      0,
                      math.ceil((retry_at - now).total_seconds()),
                  )
              except (TypeError, ValueError, OverflowError):
                  return None

          def wait_for_rate_limit(response_header, local_attempt):
              requested = retry_after_seconds(response_header)
              if requested is None:
                  requested = min(2 ** local_attempt, 30)

              bounded_delay = min(max(requested, 1), MAX_SERVER_DELAY)
              # Positive jitter reduces synchronized retries without shortening
              # the bounded requested delay or exceeding the application cap.
              delay = min(
                  bounded_delay
                  + random.uniform(
                      0,
                      min(1.0, bounded_delay * 0.1),
                  ),
                  MAX_SERVER_DELAY,
              )
              print(
                  f"rate limited; waiting {delay:.2f}s before local retry",
                  file=sys.stderr,
                  flush=True,
              )
              time.sleep(delay)

          url = os.environ["API_URL"]
          idempotency_key = os.environ["IDEMPOTENCY_KEY"]

          for local_attempt in range(LOCAL_ATTEMPTS):
              request = urllib.request.Request(
                  url,
                  method="POST",
                  data=b"{}",
                  headers={
                      "Content-Type": "application/json",
                      "Idempotency-Key": idempotency_key,
                  },
              )

              try:
                  with urllib.request.urlopen(request, timeout=30) as response:
                      body = response.read().decode("utf-8")
                      print(body)
                      raise SystemExit(0)
              except urllib.error.HTTPError as exc:
                  if exc.code == 429:
                      if local_attempt + 1 == LOCAL_ATTEMPTS:
                          print(
                              "local 429 retry budget exhausted",
                              file=sys.stderr,
                          )
                          raise SystemExit(RETRYABLE_EXIT)
                      wait_for_rate_limit(
                          exc.headers.get("Retry-After"),
                          local_attempt,
                      )
                      continue

                  if 500 <= exc.code <= 599:
                      print(
                          f"upstream server error: HTTP {exc.code}",
                          file=sys.stderr,
                      )
                      raise SystemExit(RETRYABLE_EXIT)

                  print(
                      f"permanent HTTP error: {exc.code}",
                      file=sys.stderr,
                  )
                  raise SystemExit(PERMANENT_EXIT)
              except (urllib.error.URLError, TimeoutError) as exc:
                  print(f"temporary network error: {exc}", file=sys.stderr)
                  raise SystemExit(RETRYABLE_EXIT)
```

The script sends an idempotency key based on `workflow.uid`. That key remains stable across Argo retry attempts, so an API that supports idempotency can recognize a repeated operation. Adapt the key scope to the endpoint: a looped task usually needs the item or node identity as part of the key.

The five-minute `MAX_SERVER_DELAY` is an application policy. If the server asks for longer, decide whether to wait, suspend the Workflow, or fail for later resubmission. Silently ignoring a large `Retry-After` and hammering the API is not a retry strategy.

## Why Argo Backoff Cannot Directly Use `Retry-After`

The native backoff block is declarative:

```yaml
backoff:
  duration: "5s"
  factor: "2"
  cap: "1m"
  maxDuration: "10m"
```

Its fields are configured before an attempt runs. Retry expressions can inspect `lastRetry.status`, `exitCode`, `duration`, and `message`, but the official field model does not provide a dynamic expression for the next `backoff.duration`. A failed attempt cannot publish an arbitrary response header and substitute it into the already-configured delay reliably.

Do not invent syntax such as:

```yaml
# Not a supported dynamic Retry-After mechanism.
backoff:
  duration: "{{lastRetry.outputs.parameters.retry-after}}"
```

Instead, honor the header while the process owns it. If waiting inside a Pod is too expensive for long delays, model the delay explicitly with a suspend template or an event-driven callback rather than holding or rapidly recreating Pods.

## Prevent Retry Storms

Pure exponential backoff still synchronizes many failures that start together. If 500 loop items receive a 429 at once, they can all wake at 5, 10, and 20 seconds.

Use multiple controls:

- add positive jitter in the application;
- set Workflow or template `parallelism` so the fan-out cannot issue hundreds of simultaneous calls;
- use an Argo semaphore for a shared upstream quota;
- honor provider rate-limit headers;
- cap local and Argo attempts;
- make each request idempotent;
- alert on retry volume and final exhaustion.

A semaphore limits concurrent holders, not requests per second. If each task makes many fast calls, implement a real client-side rate limiter or central queue as well.

## Set Three Different Limits

A safe policy has three independent bounds:

1. **Attempt count:** `retryStrategy.limit` controls retries after the original attempt.
2. **Delay growth:** `backoff.cap` prevents one exponential delay from growing without bound.
3. **Elapsed budget:** `backoff.maxDuration`, template timeout/deadline, and Workflow deadline constrain total time.

For example:

```yaml
retryStrategy:
  limit: "6"
  retryPolicy: Always
  expression: >-
    lastRetry.status == 'Error' || lastRetry.exitCode == '75'
  backoff:
    duration: "10s"
    factor: "2"
    cap: "2m"
    maxDuration: "15m"
timeout: 20m
```

The node timeout must leave enough time for useful attempts and backoff, but it should still provide an outer safety boundary. Argo's field reference notes an important interaction between `activeDeadlineSeconds` and retry `maxDuration`; test the final policy with the installed release instead of assuming two independent timers simply add together.

Never use an empty strategy casually:

```yaml
retryStrategy: {}
```

Argo's retry walkthrough documents that this retries until completion. An upstream outage can therefore create unbounded work unless another deadline stops it.

## Retry Only Safe Operations

Before retrying, classify the operation:

- **Safe by definition:** reads and idempotent state reconciliation;
- **Safe with a key:** create/payment/job APIs that enforce idempotency keys;
- **Unsafe without reconciliation:** requests that can perform the side effect and then time out before returning a response.

For an ambiguous timeout, query the external system by idempotency key before sending the mutation again. Argo knows that a Pod failed; it cannot know whether a remote service committed the request just before the connection broke.

Keep permanent failures out of the retry path:

- malformed input;
- authentication or authorization failure;
- unknown resource;
- schema validation error;
- deterministic business rejection.

Retrying these wastes time and can hide the signal behind many identical Pods.

## Inspect Retry Behavior

Argo displays retry attempts as nodes. Start with:

```bash
argo get -n workflows <workflow-name>
argo logs -n workflows <workflow-name> --grep 'rate limited|error'
```

Inspect node phases, messages, exit codes, and timing:

```bash
kubectl get workflow -n workflows <workflow-name> -o json \
  | jq -r '
      .status.nodes[]
      | select(.displayName | contains("request"))
      | [
          .displayName,
          .phase,
          (.outputs.exitCode // "-"),
          .startedAt,
          .finishedAt,
          (.message // "")
        ]
      | @tsv
    '
```

Check that:

- exit `75` produces another attempt;
- exit `64` ends immediately;
- delays grow and stop at `cap`;
- the retry count stops at `limit`;
- a large `Retry-After` follows your explicit application policy;
- the final Workflow status and error message remain actionable.

Also distinguish application retries from Argo's optional automatic Pod restart feature for infrastructure failures before the main container enters `Running`. When enabled in the controller, it solves a different failure phase and can also affect how many Pod executions you observe.

## Production Checklist

- Set `limit`; do not rely on an empty retry strategy.
- Set `retryPolicy` explicitly when using an expression.
- Use a stable retryable exit code instead of log-text matching.
- Configure `duration`, `factor`, `cap`, and `maxDuration` for a finite budget.
- Parse both `Retry-After` seconds and HTTP dates.
- Add jitter and concurrency controls to avoid synchronized retries.
- Use idempotency keys for side-effecting requests.
- Do not retry permanent 4xx or validation failures.
- Align node and Workflow timeouts with the intended retry budget.
- Emit metrics for attempts, rate limits, exhausted retries, and total latency.

Argo's backoff is the outer orchestration policy. The API client remains responsible for understanding protocol-specific rate limits and the safety of repeating its operation.
