# Cost per Service, Deployment, or Environment: Building Useful Platform Unit Economics

Author: [nawazdhandala](https://www.github.com/nawazdhandala)

Tags: Platform Engineering, FinOps, Unit Economics, Cloud Cost, Allocation, Metrics

Description: Build platform unit costs by reconciling a defined cost pool with stable, decision-relevant service, deployment, and environment units.

---

“The platform costs £4 million a year” is a budget fact, not an efficiency measure. Cost per service, deployment, or environment connects that spend to the demand the platform serves.

The formula is simple:

```text
unit cost = attributable platform cost / valid units delivered
```

The hard work is deciding what belongs in the numerator, what qualifies in the denominator, and which unit answers a real decision.

## Begin with the Decision

Different units answer different questions:

| Unit | Useful question | Major limitation |
| --- | --- | --- |
| Active service | Is the shared platform becoming more efficient as its managed estate grows? | Services vary greatly in size and complexity |
| Deployment | What does the delivery path cost for each completed production release? | High deployment frequency can mechanically lower the number |
| Environment | What does it cost to provide and operate a defined environment class? | Long-lived and ephemeral environments are not comparable |
| Workflow execution | Is a particular self-service capability cost-efficient? | It ignores value outside that workflow |
| Team onboarded | What is migration and enablement cost? | It is mostly useful during growth or migration |

Do not put all units in one blended score. Select one primary unit for a decision and supporting units for diagnosis.

## Define the Cost Pool

Create a platform cost ledger with explicit inclusion rules:

- cloud infrastructure used by platform control and data planes;
- observability, CI/CD, security, catalog, and developer-tool licenses;
- platform-team labor;
- contractor and managed-service cost;
- shared support and on-call cost;
- depreciation or amortized capital cost where finance requires it;
- allocated shared organizational services;
- direct costs generated by platform-managed workload execution.

Separate:

```text
fixed platform cost
variable platform cost
pass-through workload cost
one-time transformation cost
```

A database used by an application is usually pass-through workload cost, not platform operating cost, even if the platform provisioned it. Keep both visible rather than inflating the platform numerator.

Agree with Finance on loaded labor rates, allocation periods, capitalization, currency conversion, credits, commitments, and tax treatment. Reconcile the ledger to the general ledger or approved cost source each period.

## Create a Cost Allocation Hierarchy

Use direct attribution before allocation:

1. **Direct:** resource or license belongs to a service, workflow, or environment.
2. **Causal driver:** allocate shared cost using a measured driver such as executions, runner minutes, storage, or active tenants.
3. **Reasonable shared basis:** allocate genuinely common cost by active services, teams, or another stable unit.
4. **Unallocated:** retain cost that cannot be assigned defensibly.

Do not hide unallocated cost by forcing it into a convenient team bucket.

Example:

```text
runner compute       -> build or deployment minutes
artifact storage     -> stored bytes and retrieval
policy service       -> evaluated requests
support labor        -> sampled effort by workflow
portal and catalog   -> active managed services
platform leadership  -> shared platform pool
```

Document every driver and update it only through a versioned policy.

## Define the Unit Precisely

### Active service

Specify:

- catalog identity;
- ownership requirement;
- what activity qualifies;
- treatment of shared libraries and jobs;
- inactivity period;
- duplicate and retired records.

```text
active service =
  cataloged production service with an owner
  and at least one qualifying runtime or delivery event in 90 days
```

### Deployment

Define production, success, rollback, retry, multi-region rollout, and one pipeline releasing several services. Count logical deployments rather than every internal job.

### Environment

Separate classes:

- long-lived production;
- long-lived nonproduction;
- ephemeral preview;
- disaster recovery;
- training or sandbox.

An ephemeral namespace lasting two hours should not be averaged with a regulated production environment without weighting or segmentation.

## Calculate and Reconcile

Assume a monthly platform pool:

```text
cloud and vendors       £180,000
platform labor          £260,000
shared allocation        £40,000
one-time migration       £70,000
pass-through workload   £450,000
```

For steady-state operating unit cost, exclude but report the last two:

```text
operating platform cost = £480,000
```

If the month has 1,200 active services:

```text
cost per active service = £480,000 / 1,200 = £400
```

If the delivery capability is allocated £144,000 and completed 18,000 valid production deployments:

```text
delivery-platform cost per deployment
= £144,000 / 18,000
= £8
```

The service and deployment figures use different cost pools. Adding or comparing them without that context is invalid.

Reconciliation check:

```text
directly allocated
+ driver-allocated
+ shared allocated
+ unallocated
= total in-scope platform cost
```

## Report Distributions and Classes

An average can be dominated by large workloads. Report:

- total cost and unit count;
- average unit cost;
- median and percentiles where per-unit allocation exists;
- unit cost by service or environment class;
- fixed and variable portions;
- allocated and unallocated percentages;
- one-time cost separately;
- trend with comparable definitions.

Avoid publishing precise per-team costs when shared allocation is mostly assumption. Label measured, allocated, and estimated values.

## Interpret Unit-Cost Movement

A lower unit cost can mean:

- fixed cost spread across more useful demand;
- actual automation or rate improvement;
- less support effort;
- more efficient architecture;
- denominator inflation from duplicate or trivial events;
- reliability or quality being underfunded.

A higher unit cost can mean:

- investment ahead of adoption;
- migration cost;
- stricter security or resilience;
- reduced demand;
- real inefficiency.

Always pair cost with outcomes:

- platform SLO and error-budget health;
- task success;
- developer satisfaction;
- self-service rate;
- delivery stability;
- policy compliance.

The FinOps Foundation frames unit economics as connecting technology cost and usage with meaningful value or demand data. The unit should help a decision, not merely make cost look smaller.

## Forecast Marginal and Average Cost Separately

Average cost includes existing fixed capacity:

```text
average cost = total cost / total units
```

Marginal cost estimates the additional cost of one more unit or a demand increment. It helps answer:

- What will onboarding 200 services add?
- What does one more preview environment cost?
- When will another runner pool or license tier be required?

Model cost steps explicitly. A license may be flat until a threshold, while compute scales continuously and support requires another engineer only after a capacity range.

## Avoid Unit-Economics Traps

- **Cost per deployment as a productivity target:** teams can split deployments to improve the denominator.
- **Ignoring failed work:** failed and retried executions still consume cost.
- **Mixing pass-through spend with platform operations:** workload size looks like platform inefficiency.
- **Using catalog count without hygiene:** abandoned records make unit cost look better.
- **Allocating every penny with false precision:** assumptions disappear behind decimals.
- **Comparing unlike units:** regulated environments and previews have different service levels.
- **Optimizing cost without guardrails:** reliability and developer experience deteriorate.
- **Treating cost avoidance as cash:** a forecast avoided is not an expense removed from the ledger.

## Operate the Model as a Product

Assign owners for:

- cost source reconciliation;
- service and workflow identity;
- allocation rules;
- unit definitions;
- data-quality monitoring;
- quarterly review with Engineering and Finance.

Version the model and restate history only when the benefit outweighs the confusion. Make queries and assumptions reviewable.

Useful platform unit economics do not require perfect allocation. They require a reconciled cost pool, a defensible unit, transparent assumptions, and outcome guardrails. That is enough to see whether platform investment scales with the value-producing work it supports.
