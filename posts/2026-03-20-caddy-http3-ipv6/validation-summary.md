## Issues Found
- The Ubuntu/Debian install commands omitted `curl` and the current `chmod o+r` steps from Caddy's official install instructions. I added those commands and split `update` and `install` into separate steps to match the supported flow.
- The basic HTTP/3 section implied that explicit IPv6 binding is required. Caddy binds to all interfaces by default, so I rewrote that line to make the explicit bind example optional rather than necessary.
- The reverse proxy example claimed the upstream was HTTP/2 while using `http://[::1]:8080`. Per Caddy's docs, cleartext HTTP/2 upstreams should use `h2c://`, so I changed the upstream to `h2c://[::1]:8080`.
- The verification command used `curl --http3`, which can fall back to earlier HTTP versions. I changed it to `curl --http3-only` so it actually verifies HTTP/3.
- The admin API comment described config inspection as HTTP/3 status. I corrected the wording to reflect that the endpoint shows configured HTTP servers, not live protocol status.
- The `ip6tables` example placed `-j ACCEPT` before the comment match. I reordered the rule to valid `iptables` syntax.
- The JSON example lacked a host matcher for `example.com`. I added a top-level host match and made the route terminal so it aligns with Caddy's Automatic HTTPS activation model for JSON config.

## Review Notes
- The IPv6-only `:443` example is valid because it manually loads a certificate with `tls ...`; automatic certificate management in Caddy requires a hostname or IP address in the config.
- `default_bind` only affects servers generated by the Caddyfile. Per Caddy's docs, the automatic HTTP redirect server created at runtime does not inherit `default_bind`.
